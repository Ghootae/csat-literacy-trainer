# 체크포인트: 진단 v5.10 첫 사용 — 수정 사항 메모

사용자가 진단평가(`/diagnostic`, 판정 v5.10)를 직접 쓰며 남긴 수정 사항. **기록만 한다. 사용자와 나중에 논의한 뒤 해결한다**(사용자 2026-11-10). 논의 전에 고치지 않는다.

## 1. 근거 생략 버튼 문구 (화면 문구)

- 사용자 원문: "'확실해요' -> '확실(근거 불필요)', '잘은 모르겠지만 정답 같음'->'잘 모르겠음(근거 입력 안함)'"
- 위치: `packages/app/src/client/diagnostic/AnswerScreen.tsx` 101·102행 버튼 글자. 같은 이름이 `packages/app/src/client/diagnostic/types.ts` 20행 주석과 인계 `docs/handoffs/2026-11-09-judgment-split-option-na.md`(2-1절, 표)에 있다.
- 동작(확신 구분 `SURE`/`UNSURE`)은 그대로, 글자만 바꾼다.

## 2. 답 입력 화면의 "이 지문 답 다 냈어" 버튼 위치

- 사용자 원문: "'이 지문 답 다 냈어'는 지문 마지막 문항에서만 제시. '다음 문항'의 위치를 대치"
- 이해: 마지막 문항이 아니면 "다음 문항"만 보이고, 지문의 마지막 문항에서는 "다음 문항" 자리에 "이 지문 답 다 냈어"가 대신 나온다.
- 위치: `packages/app/src/client/diagnostic/AnswerScreen.tsx` 107·108행. 지금은 두 버튼이 늘 함께 보인다. "다음 문항"은 마지막 문항에서 비활성, "이 지문 답 다 냈어"는 모든 문항 답이 유효할 때 활성(`allValid`).
- 논의 거리: 마지막 문항에서 앞 문항 답이 비어 있으면(`allValid` 거짓) 버튼을 어떻게 보일지.

## 3. 근거 입력의 "결론" 자동 입력 버튼이 없음

- 사용자 원문: "결론 자동 입력 버튼이 사라진 듯" (캡처: 기호 줄 → ↔ & = ≠ ↑ ↓ ex) 만 보임)
- 확인한 사실: "결론" 버튼(`rationale-conclusion`, 고른 선지·발문으로 "따라서 ○번은 …" 문장을 붙임)은 lab에만 있다. `packages/app/src/client/ProblemLabApp.tsx` 310~315행에서 `RationaleSymbolBar`의 자식으로 넘긴다(커밋 996c38c7). 진단 화면(`diagnostic/AnswerScreen.tsx` 99행, `FeedbackScreen.tsx` 164행)은 기호 줄만 쓰고 결론 버튼을 넘기지 않는다. git 이력상 진단 화면에 결론 버튼이 있던 적은 없다. 사라진 것이 아니라 처음부터 연결되지 않은 것이다.
- 논의 거리: 진단 답 입력·교정 답 입력에 결론 버튼을 넣을지, 넣는다면 교정(정정) 단계에서도 보일지(lab은 교정 중에는 결론 없음).

## 4. 답 입력 화면: 입력창 안 작은 버튼(제출·근거 미입력)과 문항 이동 활성 조건

- 사용자 원문: "근거 입력 후, '제출' 버튼(입력 창 내부에 작게)을 누르면 '이전문항, 다음 문항'이 활성화 되는 방식으로. '확실해요'-> '근거 미입력(확실)', '잘은 모르겠지만 정답 같음' ->'근거 미입력(잘 모르겠음)'으로 바꾸고 입력창 내부의 작은 버튼으로" (캡처: 의식 지문 13번, 근거 입력창 아래 기호 줄, 그 아래 두 확신 버튼, 맨 아래 이전 문항·다음 문항·이 지문 답 다 냈어)
- 이해:
  - 근거 입력창 **안에** 작은 버튼 셋: "제출", "근거 미입력(확실)", "근거 미입력(잘 모르겠음)".
  - 셋 중 하나를 눌러야 그 문항의 "이전 문항"·"다음 문항"이 활성화된다(그 전에는 비활성).
- 지금 동작(`packages/app/src/client/diagnostic/AnswerScreen.tsx` 95~109행): 확신 버튼 둘은 기호 줄 아래 별도 줄(`diag-omit-row`). "이전 문항"은 첫 문항에서만, "다음 문항"은 마지막 문항에서만 비활성이고 답 입력 여부와 무관하게 오갈 수 있다. 문항별 "제출" 버튼은 없다(지문 단위 "이 지문 답 다 냈어"만).
- **1번과의 관계**: 확신 버튼 문구가 1번("확실(근거 불필요)"·"잘 모르겠음(근거 입력 안함)")과 다르다. 4번이 나중 메모라 4번 문구가 대체하는 것으로 보이나 논의 때 확인한다.
- 논의 거리: 선지를 고르지 않은 상태에서 제출을 막을지, 제출 뒤 근거를 고치면 다시 제출해야 하는지, "이전 문항"도 제출 전 비활성인지(되돌아가기 막힘), 2번(마지막 문항에서 "이 지문 답 다 냈어"가 "다음 문항" 자리 대체)과의 결합.

## 5. 소거법 근거의 판정 (판정 규칙, 논의 필요)

- 사용자 원문: "예를 들어, 긍정 발문의 경우, 근거로 '3번을 제외한 나머지는 확실히 말이 안되므로 3번이 정답'이라고 입력했을 때, 어떻게 판정할지 논의 필요"
- 성격: 화면이 아니라 판정 규칙 문제. 학생 근거가 정답 선지 자체의 지지가 아니라 다른 선지를 배제한 결과(소거)일 때.
- 확인한 사실: 판정 지시문 v5.10(`packages/pipeline/experiments/problem-solving/source-direct-problem-feedback-v5.10.md`)과 결정 기록에 소거 근거를 직접 다루는 규칙은 찾지 못했다("소거"·"나머지 선지" 검색 0건, 관련 문장은 301행 "학생이 아직 말하지 않은 다른 선지의 대상을 새로 …" 정도). 실제 판정 결과는 아직 시험하지 않았다.
- 논의 거리: 소거 근거를 '충분'·'부족'·별도 범주 중 무엇으로 볼지, 정답의 질 3단계(D-0213)에 어떻게 넣을지, 배제 이유 없이 "확실히 말이 안 된다"만 쓴 경우와 선지별 배제 이유를 쓴 경우를 나눌지, 부정 발문에서도 같은 기준인지.

## 6. 중간 화면: "피드백 시작" 대신 문항 목록에서 리뷰할 문항 고르기 (논의 필요)

- 사용자 원문: "그냥 '피드백 시작'을 누르는게 아니라, 문제들을 나열하고, 리뷰할 문제를 선택하는 형식으로 하기로 하지 않았나? 예를 들어, 문제 4. 정답(근거 충분, 리뷰 대상 아님 ->비활성화), 문제 5. 오답(리뷰 대상 -> 활성화), 문제 6. 정답(근거 불충분, 리뷰 대상 아님 -> 비활성화), 문제 7.(정답, 오류->리뷰대상-> 활성화). 어디까지 리뷰대상으로 하기로 했지?" (캡처: 경마 지문 중간 화면, 4·5·6·7 칸, 5만 테두리, "피드백 시작" 버튼 하나)
- 확인한 사실:
  - **리뷰 대상**은 [D-0213](../decisions/D-0213-diagnostic-judgment-split-option-na.md) 2·3·5번과 그 "추가" 절로 정해져 있다. 리뷰(교정 대화)를 여는 것: 오답(범주 6, "확실해요" 오답은 근거를 한 번 묻고 리뷰), 근거가 틀린 정답(범주 3, 선택–근거 불일치 포함). 열지 않는 것: 근거 있는 정답(1), 근거 약한 정답(2), 확신 정답(4), 판정 불가 정답('확인 못 함'). 확신 없이 맞힌 정답(5)은 리뷰가 아니라 힌트 → 근거 → 판정 → 충분이면 끝, 부족·오류·판정 불가면 마지막 설명.
  - 사용자 예시의 활성/비활성(4 충분 비활성, 5 오답 활성, 6 부족 비활성, 7 오류 활성)은 D-0213과 맞는다.
  - **"문항 목록에서 리뷰할 문항을 고르는 형식"은 결정 기록·인계 문서에서 찾지 못했다.** D-0213 7번 "문항별 피드백 열기"는 대기 줄이기(그 문항 판정이 끝나면 그 문항 피드백을 연다)이고, 인계 1부(`docs/handoffs/2026-11-09-diagnostic-option-na-part1.md` 82·89행)도 중간 카드의 "피드백 시작" 버튼 하나가 커서 0번 문항을 연다고 적었다. 지금 피드백은 지문 문항을 순서대로 모두 거친다(리뷰 없는 문항도 그 문항 화면을 지나감).
- 논의 거리: 목록에서 고르는 형식으로 바꿀지(리뷰 대상만 활성), 리뷰 대상이 아닌 문항(근거 약한 정답 등)의 마지막 설명은 어디서 볼지, 범주 5(힌트 흐름)는 목록에서 활성으로 둘지, 판정 중인 문항 표시, 고르지 않은 리뷰 대상을 건너뛸 수 있는지.

### 6-1. 지문 결과 화면 개편안 (사용자 시안, 6번에 이어짐)

- 시안 그림: `docs/review/diagnostic-passage-result-mock-2026-11-10/`(1 가림, 2 한 문항 공개, 3 모두 공개·등급 공개). 예시는 경마 4~10번 가상 결과.
- 사용자 원문 요지:
  1. 문제 풀이 결과가 먼저 나오고, 결과 설명은 가려 둔다.
  2. 정오·근거 강도에 따라 문제 버튼 색을 나눈다.
  3. 등급은 바로 공개하지 않고 결과를 모두 본 뒤 보인다("나의 현재 등급은?").
  4. 문제 버튼을 누르면 그 문제 결과가 공개된다(그림 2).
  5. 문제 결과를 모두 보면 등급이 공개된다(그림 3, 1~9등급 눈금).
  6. 오른쪽 피드백 버튼을 누르면 그 문제 검토 화면으로 간다. 검토를 마치면 그 버튼은 "검토 완료했어. 수고했어"로 비활성화되고, 다음 검토할 문제를 고른다.
- 시안에서 읽은 것(사용자 확인 전):
  - 문제 버튼 색: 진한 초록 = 정답(근거 충분·근거 약함·근거 없이 확실·판정 불가), 연한 초록 = 정답(근거 오류·잘 모르겠지만), 빨강 = 오답.
  - 줄마다: "정답(정답률 n%). 근거 설명. (내부 범주)" / 오답은 "오답(오답 선지 선택 n%)". 정답률·선택률은 메가스터디 수치(D-0203, 세트 E 자료에 있음).
  - 오른쪽 버튼: 회색 = 칭찬 문구(리뷰 대상 아님: 4·5·6·7), 주황 = "근거를 다시 검토해보자"·"아깝지만 정답이 아니야. 다시 검토해보자."(리뷰 대상: 8 근거 오류, 9 잘 모르겠지만, 10 오답). D-0213 리뷰 대상(오답·근거 오류)에 범주 5(잘 모르겠지만, 힌트 흐름)를 더한 것과 같다.
- 확인할 것(논의 때): 괄호 속 내부 범주 표기를 학생에게도 보일지, 회색 버튼을 누르면 무엇을 하는지(마지막 설명?), 등급 공개 조건이 "모두 봄"만인지 "검토도 다 함"까지인지, 다음 지문으로 가는 버튼 위치·조건, 판정 중인 문항 표시, 정답 중 근거 오류·잘 모르겠지만을 연한 초록 하나로 묶는 것, 지금 순차 피드백 흐름(커서)을 문항 선택형으로 바꾸는 서버 변경 범위.
- 사용자 답(2026-11-10):
  - 괄호 속 내부 범주는 개발자 모드(`?dev=1`)에서만 보인다.
  - 회색 버튼(리뷰 대상 아님)은 아무 동작 없음, 비활성 표시.
  - 등급 공개 조건은 "문제 결과를 모두 봄"까지(검토 완료는 조건 아님).
  - "다음 지문" 버튼은 오른쪽 아래. 검토를 마치고 결과 화면으로 돌아왔을 때 활성화.
  - 판정이 끝나지 않은 문제의 줄: "정답(20%). 아직 분석 중이야" 형식.
  - 등급 그래프: 범위(예: 2~4등급)가 아니라 **확률이 가장 높은 등급 하나**("3등급")로 쓰고, 1~9등급 눈금 위에 등급별 확률을 진하기로 칠한 띠(시안 그림 3).
- 코드 확인: 위치 추정(`packages/pipeline/src/diagnostic-position/position.ts` `estimateAbility`)은 능력값 사후분포를 격자 401점으로 이미 계산하고 평균·10%·90% 지점만 돌려준다. 등급별 확률은 격자 점마다 등급을 매겨(`nationalPosition` → `gradeOfPercentile`) 가중치를 더하면 새 외부 자료 없이 얻을 수 있다. 두 선택과목(평균 내는 방식)의 합치기 규칙은 정해야 한다.

- 정답 판정 실패(`CHECKING`)는 리뷰 대상이 아니라 학생이 검토 화면에서 판정 재시도(`RESUME`)할 길이 없어짐(배경 자동 재시도는 그대로).
- 남은 것: 공개 전 등급 숨김은 지문 결과 응답에만 적용, `/progress`·`result` 응답에는 등급이 실림(API 직접 열면 보임). 최종 결과 화면 위치 표시는 범위 그대로.

## (구현) 등급 띠 연속 그라데이션 — D-0219

- 코드 에이전트 직접 구현(작은 작업). 위치 계산에 실수 등급·등급 축 확률(`grade.density`) 추가, 화면 띠를 연속 그라데이션 + 커서 확률 말풍선으로 교체. 말풍선이 띠 끝에서 카드 밖으로 나가고 큰 등급 글자를 가리던 것을 고침(가장자리 정렬, 띠 위 여백 40px).
- 시험: 위치·진단·화면 vitest 통과, Playwright 진단 3건 통과, `npm test` 기존 실패 2건 외 통과.
- 같은 날 변경(D-0219 "변경" 절): 원점수 → 실수 등급 PCHIP 정정, 띠는 9개 등급 확률을 코사인 곡선으로 이음, 큰 글씨 아래 "n등급일 확률이 p%로 가장 높아". 사용자가 실수 범위("1.6–4.6등급")는 정보가 없다고 판단해 범위 표기는 쓰지 않는다.
- 남은 일: 위치 API의 `grade.density`는 화면에서 안 씀(정리 여부 미정).
