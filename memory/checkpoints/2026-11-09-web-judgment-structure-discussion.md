### 2.6 코드 에이전트의 v5.9 질문 규칙 계획 검토 (11-09 02:09)

### 2.8 사용자 제안 2: 판정 구조 개편 (11-09 02:29)

사용자 안:

- 문항마다 sol을 한 번(필요하면 두 번) 호출해 판정, 질문, 학생 응답 분석, 정답 설명, luna용 상세 가이드를 함께 만든다.

- luna는 리뷰 대화를 맡고, sol의 가이드에 따라 질문에 맞게 답했는지만 판정한다.

웹 대화의 평가:

- 좋은 구조다(큰 모델이 계획하고 작은 모델이 실행).
  - luna의 일을 "답했나"로 좁혀 약점(긴 지시문 따르기)이 드러날 자리를 없앤다.
  - 정답-부족 리뷰를 없애 가장 큰 불만을 바로 없앤다.
- 비용이 실제로 줄어드는 곳:
  - luna가 리뷰를 맡는 건 지금도 같다.
  - 줄어드는 건 sol 호출을 합치는 데서다. 문항당 2회(판정+설명)가 1회가 된다. 2회로 나누면 sol 전환안과 비슷하다.
  - 사고 진단까지 합치면 더 준다. 다만 사고 진단은 독립 교차 확인 역할을 했으니 합칠지는 따로 정한다.
- 설계 시 정할 것 6가지:
  1. 가이드에 합격 기준을 넣는다(기대 답, 통과로 볼 답, 무시할 차이. 예: "방향만 맞으면 통과, 1~2dB 무시"). luna 출력은 맞음/틀림/모름 + 인용 한 칸만 두고, 흐름은 서버가 정한다(틀리면 sol이 미리 쓴 힌트 → 또 틀리면 정답 설명).
  2. 뿌리가 같은 오류는 sol이 계획 단계에서 묶고 순서를 정한다(오디오 17).
  3. 정답 설명은 미리 쓰고, 리뷰 결과를 받는 한두 문장만 뒤에 붙인다.
  4. 전 문항을 동시에 보내고, 리뷰 대상 중 먼저 끝난 것부터 시작한다(진단에 동시 실행 8 설정이 있다). 정답-오류는 분석이 끝나야 알 수 있다.
  5. 예상 밖 답이면 luna는 "모름"으로 넘기고, 서버가 정답 설명으로 마무리한다(필요할 때만 sol 재호출).
  6. 판정 부분은 v5.8(+171행 수정)을 재사용하고 출력 칸만 더한다. 새로 쓰면 회귀 기록이 0으로 돌아간다.
- 큰 결정: 지금은 진단·lab·본 서비스가 같은 피드백 부품을 쓴다(D-0204). 새 구조의 적용 범위와 일정을 정해야 한다.

### 2.9 사용자 제안 3: 정답·오답 이분화 판정 (11-09 02:48, 가장 최근 안)

  - 헛경보(없는 오류로 리뷰를 엶)는 비용이 크지만 sol이 거른다.
  - 놓침(있는 오류를 못 잡음)은 정답은 맞혔으니 비용이 작다.
- 기록상 사실: 이번 진단에서 luna가 정답 문항에 준 '오류'는 3건이다.
  - 경마 5, 오디오 17: 실제 오류(진짜 오류 2건 모두 잡음).
  - 의식 16: 헛경보(P2).
  - 표본이 작다.
- 비용: 이번 진단 기준 sol 호출 4회(오답 1 + luna 오류 3). 근거가 있는 13문항을 모두 sol로 판정하면 13회.
- 정할 것 5가지:
  1. **결과 보고서의 정답 구분(사용자 결정 필요).** luna의 지나친 '부족'은 리뷰를 열지 않지만 보고서에는 남는다("적절한 근거 4개" 재발).
     - (가) 보고서에서 정답을 "정답 / 정답이지만 근거 오류"로만 나눈다 → luna 171행 실험 불필요.
     - (나) 충분/부족 구분을 유지한다 → luna에도 171행 수정이 먹히는지 시험해야 한다.
  2. 판정 불가(UNKNOWN, 예: 플라 8)도 sol로 보낸다.
  3. sol은 luna 판정을 보지 않고 처음부터 판정한다(끌려가지 않게).
  4. 운영 중에 luna가 "오류 없음"으로 본 정답을 가끔 뽑아 sol로 따로 돌려, 놓치는 비율을 점검한다.
  5. 리뷰 없는 정답 문항의 정답 설명은 학생이 원할 때만 만든다(사용자 코멘트 E2 "정답 설명도 선택"과 연결).
- 이 구조에서는 사용자에게 보이는 질문을 모두 sol이 쓴다(오답 + sol이 확인한 정답-오류). 그러므로 **v5.9 질문 규칙 시험은 sol만으로 충분**하다.
