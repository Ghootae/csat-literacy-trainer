# 교정 성공 뒤 학생이 '다시 선택' 또는 '코칭 보기'를 고른다

## 결정

사용자 결정(2026-10-10, "그 형태로 결정 기록해줘")에 따라 [D-0059](./D-0059-problem-feedback-clarifications-consolidated.md)의
교정 이후 흐름을 다음처럼 고친다. 오류 파악·오류별 교정 질문·누적 판정 규칙은 그대로다.

### 오답 선택

1. 오류 파악 → 오류별 교정 질문 → 교정 답변 판정(현행).
2. 교정 성공(관련 오류 모두 수정): 확인 문구와 두 버튼을 보여 준다.
   > "핵심 오류를 잘 고쳤어요. 처음에 ②를 고르게 된 생각 중 어디가 잘못됐는지 알 것 같다면 다시 선택해 볼까요?"
   > [다시 선택] [코칭 보기]
   - [다시 선택]: 기존 재선택 1회 규칙. 맞히면 근거 판정, 또 틀리면 정답 공개·설명 후 종료. 세 번째 선택은 없다.
   - [코칭 보기]: 정답 공개 + 어디가 잘못된 생각이었는지 + 왜 정답인지 설명 후 종료. 학생 스스로 해결하지 못한 것으로 기록한다.
3. 교정 실패: 정답 공개 + 어디가 잘못된 생각이었는지 + 왜 정답인지 설명 후 종료(현행 코칭 종료와 같은 자리).

### 정답 선택이지만 근거에 명시적 오류

1. 오류 파악 → 오류별 교정 질문 → 교정 답변 판정(현행).
2. 교정 성공: 확인 문구와 두 버튼.
   > "근거의 핵심 오류를 잘 고쳤어요. 처음 근거에서 어디가 잘못됐는지 정리한 설명을 볼까요?"
   > [설명 보기] [마치기]
   - 근거 확인/미확인 기록은 현행대로 판정기의 충분성 판정을 따른다(정답 세션은 관대하게, [D-0104](./D-0104-problem-evaluator-model-routing-by-choice.md)).
3. 교정 실패: 어디가 잘못된 생각이었는지 설명 후 종료.

## 근거

- 사용자 문제 제기(2026-10-10): "오류만 고친다는 게 실제 자료를 보니 문제가 좀 있다." 표면 장력 S2에서 원인("큰 경우요")만 고친 학생이
  선지 ②를 가르는 관계(다시 잘 나왔다면 수는 작아졌다)를 이었는지 알 수 없었다([사이클](../../docs/review/v5-repair-cycles-surface-mrna-2026-10-10.md)).
- 사용자는 처음에 교정 성공 뒤 예/아니오 자기 확인을 제안했다. Claude가 "예"는 실제 이해를 확인하지 못한다고 지적했고,
  사용자가 [다시 선택]/[코칭] 버튼 형태로 바꿨다. 재선택 결과가 이해를 행동으로 확인하고, 모르는 학생은 찍지 않고 설명을 받는다.
- 버튼 이름 '[정답 선택]'은 다시 고를 선지가 정답이라는 뜻으로 읽힐 수 있어 '[다시 선택]'으로, 선지 번호는 ①~⑤ 표기로 다듬었다(Claude 제안, 사용자 수용).

## 범위와 상태

- 정책 결정만 기록했다. 서버 상태 머신(`packages/pipeline/src/problem-solving/feedback-v4.ts`)·UI·문구 구현은 별도 설계·승인 대상이다.
  코칭 요청 명령, 교정 성공 뒤 대기 단계, 정답 세션의 [설명 보기]/[마치기] 처리가 새로 필요하다.
- [D-0105](./D-0105-correction-question-covers-choice-deciding-relation.md)(선지 정오를 가르는 관계까지 한 질문으로)는 이 흐름에서 재선택이 같은 빈틈을 걸러 주므로
  필수 규칙에서 권장 수준으로 낮출 수 있다. 사용자 확인 전까지 D-0105는 기록된 그대로 둔다.
- 재선택 시 근거 요구·감점 등 D-0051·D-0059의 다른 규칙은 바꾸지 않는다.

## 재검토 조건

- 실제 학생 사용에서 [코칭 보기] 선택이 대부분이어서 재선택을 통한 확인이 거의 일어나지 않을 때
- 재선택 정답률이 찍기 수준으로 낮아 교정 성공 판정의 신뢰도가 의심될 때
