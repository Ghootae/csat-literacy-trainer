# 원리 적용형: 기출 구조 분류 검토와 생성 파일럿(P1)을 병행, 같은 기준표 사용

## 결정

### A. 기출 구조 분류 검토 (설계 초안 `docs/experiments/principle-application-structure-2026-11-09/DESIGN-DRAFT.md`)

1. **범위**는 8지문 31문항이다(〈보기〉 없음 21, 〈보기〉 10, 어휘 제외).
   - E1 4지문: 법인·표면 장력·오디오·플라스틱
   - 개발자 화면 4지문: 공손룡·도파민·정보 비대칭·mRNA
2. **〈보기〉 문항도 넣는다.** 모든 집계는 〈보기〉 유무를 나눠 낸다.
3. **판정 절차:**
   - opus 하위 에이전트 2명이 독립 블라인드로 판정한다. 문항 순서는 판정자마다 다르게 한다.
   - 판정자에게는 가설, 표면 장력 결론, E1 결과, 지도를 주지 않는다. 정답 번호는 준다.
   - 코드 에이전트는 불일치만 원문으로 확인하고 사례로 보고한다. 판정은 바꾸지 않는다.
4. **지도 대조(H4)**는 판정 뒤 별도 단계로 한다.
5. **판정 묶음에 기출과 함께 섞는 것:**
   - E1 생성 v3(A′·B) 20문항
   - 파일럿 P1 생성 문항
   - P1 쪽 판정 묶음에는 같은 4지문의 기출 〈보기〉 문항 4개(법인 13·표면 장력 16·오디오 17·플라스틱 10)를 비교 기준으로 넣는다.
6. **주 결과는 문항 수준이다.**
   - 세트마다, 원리 적용 선지가 2개 이상인 문항의 수와 발문 유형을 〈보기〉 유무별로 낸다.
   - 선지 비율은 보조값으로 낸다. 문항 하나를 빼고 다시 센 값도 함께 낸다.
   - H2(한 상황 공유)는 수치 기준을 두지 않고 사례 나열로 낸다.

### B. 기준표 (A와 P1이 같은 것을 쓴다: `JUDGE-STRUCTURE-v1.md`)

7. **`APPLIED` 경계:** 두 질문이 모두 "예"일 때만 `APPLIED`다.
   - (1) 규칙·식·정의의 변수나 조건에 대상의 값을 넣어, 지문에 쓰여 있지 않은 결과를 도출하는가?
   - (2) 그 값이 달랐다면 결과도 달라지는가?
   - 범주 상속(A는 B의 일종이고 B는 P이니 A도 P)은 (2)에서 빠져 `COMBINED`의 `INHERIT`가 된다.
   - **특정 대상**은 〈보기〉·발문·선지에서 이름·수치·사례로 하나로 정해진 대상, 또는 지문이 상황만 깔아 둔 대상이다. 일반 조건문은 수치가 있어도 특정 대상이 아니다.
     - 그래서 일반 조건문을 이은 사슬은 `COMBINED`의 `CHAIN`이다.
     - 일반 수치 계산은 `DERIVED_LOGIC`의 `QUANTIFY`다.
     - 웹 검토 2차(11-09, 사용자가 붙여 넣음)에서 정했다.
8. **`basis` 범주와 판정 순서:** `STATED` → `COMBINED`(`COMPARE`·`CHAIN`·`INHERIT`·`OTHER`) → `DERIVED_LOGIC`(정의·규칙의 대우·경계·조건 뒤집기, 구체 대상 없음) → `APPLIED` → `OTHER`.
   - `DERIVED_LOGIC`은 본 집계에서 제외한다.
9. **추가 기록:**
   - `situationOrigin`에 `PASSAGE_SETUP`을 둔다. 지문이 규칙과 함께 상황을 제시했지만 결과는 말하지 않은 경우다.
   - 선지마다 `onItemSituation`을 적는다(발문·〈보기〉가 정한 상황 위에 있는가).
   - 문항마다 발문 유형 5종을 적는다(내용 일치 / 특정 개념·㉠ 이해 / 두 대상 비교 / 〈보기〉 적용 / 서술·읽기 방법). 발문 유형은 코드가 미리 붙인다.

### C. 원리 적용형 생성 파일럿 P1 (제안서 `docs/handoffs/2026-11-09-principle-application-generation-pilot-proposal.md`)

10. **A와 병행한다.** 단, 기준표(B)를 먼저 고정한 뒤 실행한다.
11. **대상과 구성:**
    - E1 4지문에 지문마다 2문항씩, 모두 8문항을 만든다.
    - a: 〈보기〉 없음, 상황은 지문 안에서 고름
    - b: 〈보기〉 있음, 지문 밖의 새 사례
    - 생성은 `gpt-6.1-sol` 3단계다: 규칙 뽑기 → 상황·계산표 → 단계를 비튼 오답과 집필.
12. **제안서에서 고치는 점:**
    - (나) 통과 조건: 정답 선지가 `APPLIED`이고, `onItemSituation`이 참인 선지 가운데 `APPLIED`가 2개 이상이어야 한다.
    - (다) "같은 상황 위 4개 이상"은 판정자의 `onItemSituation`으로 센다. 생성기가 스스로 적은 `onSituation`은 대조용으로만 쓴다.
    - 기출 재현 검사:
      - 코드 에이전트가 생성 문항을 같은 지문의 기출과 대조한다. 상황이나 정답 결론이 겹치면 표시하고 통과 집계에서 따로 센다.
      - 표면 장력 문항 a는 기포 합체를 쓰지 않는다. 기포 합체는 기출 15번의 상황이다.
13. **〈보기〉 문항(b)을 넣는다.** D-0206 14′를 이 파일럿 범위에서 연다. 제약은 둘이다.
    - 〈보기〉에 지문 밖의 법률·사실을 들이지 않는다.
    - 〈보기〉의 수치·조건이 서로 맞는지는 풀이 검증에서 함께 본다.
14. **성공 기준은 "8개 중 5개 통과"다.**
    - 통과 조건은 (가) 풀이 검증 일치·오류 없음, (나), (다), (라) 사용자 "깊다" 넷이다.
    - 숫자보다 어느 단계에서 떨어졌는지(제안서 5절 표)를 더 중시한다.
    - (라)는 블라인드가 아니다(사용자가 기출 15번을 이미 봄). 보고서에 이 한계를 밝힌다.
15. **외부 전송**은 dry-run 뒤 호출 수와 비용 추정을 적어 따로 승인받는다. 이 결정은 전송을 승인하지 않는다.
    - E1 v3 실측은 16요청 $0.59였다. P1은 약 20요청, $1~1.5로 추정한다.

## 근거

- 사용자(2026-11-09) 범위·방식 결정: "8지문으로 진행하자", "(나)로 진행하자"(〈보기〉 포함·분리 집계), "(다)로 진행하자"(판정 방식), "다로 가자"(지도 대조 별도).
- 웹 검토 `docs/handoffs/2026-11-09-principle-application-structure-review-web.md`
  - 표면 장력 3문단 첫 문장이 "라플라스 식은 두 기포가 합쳐지는 경우를 이해하는 데에도 도움이 된다"여서, 원안의 경계("지문이 그 규칙으로 다루지 않은 대상")로는 가설의 출처인 15④가 빠진다. 코드 에이전트가 원문으로 확인했다.
  - 이로써 브리프·초안의 정의를 정정한다.
- 코드 에이전트 보완:
  - 법인 13①, 정보 비대칭 13②와 법인 12④는 "유무 대입"으로도 "범주 상속"으로도 읽힌다. 그래서 (2) "값이 달랐다면 결과도 달라지는가"를 더한다.
  - 〈보기〉 문항을 합쳐 집계하면 〈보기〉 문항만으로 문항 기준이 충족된다. 그래서 나눠 낸다.
- 웹 제안 P1과 코드 에이전트 검토(구멍 ①~⑤)에 대해, 사용자가 웹 추천(병행·경계 합치기·②~④ 반영·〈보기〉 포함·5/8 유지)을 붙여 넣고 나머지 두 가지(웹 기준표 항목 수용, 분리 집계·v3 20문항)에 "둘 다 추천대로 진행하자".
