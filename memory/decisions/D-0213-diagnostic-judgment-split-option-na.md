# 진단 판정 흐름 (나): 정답의 질 3단계, 근거 없는 응답 버튼 둘, 정답 판정 sol(진단만), 문항별 피드백 열기

## 결정

사용자(Ghootae) 결정, 2026-11-09. 웹 스레드 논의 결과([인계 문서](../../docs/handoffs/2026-11-09-judgment-split-option-na.md), [경로 트리](../../docs/reports/problem-solving-path-tree-2026-11-09.html), [웹 논의 체크포인트](../checkpoints/2026-11-09-web-judgment-structure-discussion.md))를 코드 에이전트가 코드와 대조해 검토하고, 그 검토에서 나온 질문에 사용자가 답했다.

가장 중요한 기준(사용자): "정답과 근거를 냈는데 다시 고치라고 하면 짜증나서 나가 버린다."

1. **진단 오픈은 2026년 11월 안.** 큰 구조 개편(sol이 계획하고 luna가 리뷰만 하는 구조)은 다음 버전으로 미룬다.
2. **(나) 정답의 질 3단계.** 근거 있는 정답 / 근거 약한 정답 / 근거가 틀린 정답. 리뷰(교정 대화)는 오답과 근거가 틀린 정답에만 연다. 근거 약한 정답은 리뷰 없이 넘어간다. 결과 화면의 단계 수는 표시 설정 하나로 2단계((가): 부족을 근거 있는 정답에 합침)로 바꿀 수 있게 한다. 판정 기록에는 충분·부족·오류를 늘 남긴다. (가)는 사용자 직접 풀이에서 짜증이 나면 쓰는 대비책이다.
3. **정답인데 선택–근거 불일치(MISMATCH)면 범주 3(근거가 틀린 정답) + 리뷰.** 서버는 이미 이 경우 `selection-mismatch` 오류를 붙여 리뷰를 연다(`packages/pipeline/src/problem-solving/feedback.ts:514-518`). 결과 범주도 판정기의 충족 판정(contentAssessment)만이 아니라 불일치를 함께 보고 정한다. (코드 에이전트 검토에서 나온 빠진 경로. 사용자가 추천에 동의.)
4. **판정 불가(UNKNOWN) 정답은 정답의 질 숫자에서 빼고 '확인 못 함'으로 개수만 보인다.** 인계 문서의 "범주 1 + 보류 표시" 제안은 채택하지 않는다(근거 같지 않은 근거가 '근거 있는 정답'이 되는 것을 막기 위해).
5. **근거 없는 응답 버튼 둘.** 지금의 "근거 미제출" 버튼을 "확실해요" / "잘은 모르겠지만 정답 같음"으로 나눈다.
   - 확신 정답(범주 4): 판정·사고 진단·마지막 설명 없음. 기록은 따로 남긴다. **결과 화면에서도 근거 있는 정답에 합치지 않고 개수만 보인다**(인계 문서 2-1절의 "화면에서 합침"을 정정, 2-2절 확정). 합치면 근거를 쓴 학생만 '근거 약한 정답'을 받을 수 있어 근거 쓰기가 손해가 된다.
   - 확신 없이 맞힘(범주 5): sol이 힌트 하나를 따로 생성(짧은 전용 호출, "답 입력 마침" 때 뒤에서 시작) → 학생이 근거를 씀 → sol 판정 → 충분이면 끝, 부족·오류면 마지막 설명(리뷰 없음). 건너뛰기를 둔다. 범주는 첫 응답 기준이라 리뷰 결과와 상관없이 5로 남는다.
   - 확신 오답: 지금처럼 근거를 한 번 묻는다.
   - 범주 4·5는 정답의 질 숫자에서 빼고 개수만 보인다.
6. **정답 판정 모델 sol은 진단에서만 시험한다.** 진단의 정답 선택 판정(재선택 포함)과 그 뒤 마지막 설명을 sol로 바꾼다. 본 서비스와 개발자 경로(`/problem/lab`)는 지금 배정(정답 luna, D-0104·D-0107)을 유지하고, 적용 여부는 진단 시험 뒤 따로 정한다. 교정 판정(luna)은 바꾸지 않는다.
7. **대기 줄이기.** 먼저 할 것: (가) 문항 판정이 끝나면 그 문항 피드백을 연다(지금은 지문 전체 판정 끝). (나) 지문 결과 카드를 바로 보여 준다. 정답 수를 먼저 띄우고 근거 결과는 판정이 끝나는 대로 채운다. 답 저장(draft) 때 미리 판정하기는 대기를 잰 뒤 결정한다. 미리 판정하더라도 "답 입력 마침" 전에는 결과를 응답에 넣지 않는다.
8. 기존 보고서의 "근거가 약한 정답도 교정 대화로 돌아간다" 제안(`REPORT-learner-analysis-usage-web-result.md` 3절)은 폐기한다.

## 근거 (코드 대조, 코드 에이전트 2026-11-09)

- 정답 + 부족은 이미 리뷰가 없다. 부족(INSUFFICIENT)에는 오류 목록이 없고(`feedback.ts:438`), 오류가 없는 정답은 마지막 설명 제안으로 끝난다(`:525`). 예외는 3번의 불일치뿐이다.
- 모델은 마지막 선택의 정오로 고르고(`packages/pipeline/src/problem-solving/feedback-evaluator.ts:91-102`), 이 상수는 진단·lab·본 서비스가 함께 쓴다(D-0204). `options.model`은 교정 판정까지 덮어쓰므로, 진단만 바꾸려면 선택 판정 모델만 바꾸는 설정이 필요하다.
- 범주 5 흐름에 필요한 변경: 근거 형식에 두 버튼 구분 추가(지금 정답 + 근거 없음은 곧바로 `unknown()` 종료), `AWAITING_RATIONALE` 안내 문장 분기(지금 "정답이 아니야… 감점" 고정), 힌트 뒤 정답 + 오류는 리뷰 대신 마지막 설명. 힌트 뒤 판정은 미리 돌릴 수 없어 학생이 sol 판정 한 번을 기다린다(측정 필요).
- 지문 결과 카드는 지금 판정 하나라도 PENDING이면 전체가 pending이다(`packages/app/src/server/diagnostic/controller.ts:297`). 피드백은 지문 전체 판정이 끝나야 열린다(`checkPassageReady`).

## 열린 것

- 힌트 규칙(결론·정답 번호 말하지 않기, 맞대 볼 곳만 가리키기 제안)과 힌트 뒤 근거의 '충분' 기준, 힌트를 베낀 근거 처리.
- 비용 재추정: 충분 정답·확신 정답은 마지막 설명을 만들지 않으므로 인계 문서 5절 추정(정답 1문항 +$0.062)보다 낮다.
- 질문 규칙 v5.9 시험은 sol만으로 줄인다(인계 문서 4절). 초안 검토 1은 사용자 보류.

## 추가 (같은 날, 사용자 결정): 171행 수정의 버전과 오픈 기준

- 171행 수정은 v5.9(질문 규칙)에 섞지 않고 **v5.10 = v5.9 + 171행 수정**으로 따로 시험한다. v5.9는 판정 불변을 전제로 설계했으므로, 섞으면 판정 변화의 원인을 가를 수 없다.
- v5.10 기대 판정(양방향, 관대 반례 포함)은 v5.9 시험과 병행해 준비한다.
- v5.10 회귀에는 오답 판정(lab 6문항)과 "잘은 모르겠지만" 힌트 뒤 근거 사례를 넣는다. 힌트 지시문이 아직 없으므로 힌트 뒤 근거 사례는 직접 만들어야 한다(코드 에이전트 메모).
- **오픈 전에 v5.10이 준비되지 않으면 정답의 질 2단계((가)) 표시로 연다.** 171행이 남은 채로 '근거 약한 정답'을 학생에게 단계로 보이지 않기 위해서다. 판정 기록에는 충분·부족·오류를 그대로 남긴다(2번).
- 힌트 뒤 근거 사례는 힌트를 힌트 규칙대로 손으로 쓰고, 그 힌트를 본 가상 근거로 만든다(사용자 동의, 방안 나). 힌트 지시문이 구현되면 실제 힌트로 만든 사례를 회귀에 더한다(방안 가, 차후).

## 추가 (2026-11-09, 사용자 결정): 힌트 뒤 판정 불가 갈래

- 근거: v5.10 H 시험([보고](../../docs/reports/REPORT-v59-v510-run-human.md) 2-3). 힌트 뒤 "여전히 틀림" 근거가 선지에 닿지 않으면(의식 15·경마 4) sol은 3회 모두 판정 불가(UNKNOWN)를 냈다. 판정기는 원문 불일치를 짚었으나 D-0108(국소 오류만 판정)대로 전체 판단 오류로 보지 않았다. 선지를 정하는 사실이 틀린 의식 12는 오류 3/3.
- 결정 (가): 기대 판정을 판정 불가로 고친다. 규칙(D-0108)은 바꾸지 않는다. 이유: 선지와 상관없는 틀린 말에도 리뷰를 열면 정답을 고른 학생에게 "다시 고치라"고 하는 일이 되고(짜증 기준), 선지를 정하는 사실의 오류는 이미 오류로 잡힌다.
- 범주 5 힌트 흐름(위 23행 "충분이면 끝, 부족·오류면 마지막 설명")에 **판정 불가도 마지막 설명(정답 설명 공개)** 갈래를 더한다. 학생은 도움을 청했고 원문을 잘못 읽은 상태이므로 오류와 같은 화면을 본다. 힌트 흐름 인계(2부)에 이 줄을 넣는다.
