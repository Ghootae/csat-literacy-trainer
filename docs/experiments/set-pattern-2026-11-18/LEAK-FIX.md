# 노출 수리 단계 (leak-fix) 설계와 시험 — 2026-11-20

Ghootae 아이디어(2026-11-20): 규칙대로 생성 → 검토 → 〈보기〉가 정답 판정 사실을 대놓고 말하면 → 드러나지 않게 바꾼다. 공통 규칙 C1 보강(판정 관계 직접 진술 금지)과 함께 간다. 규칙 = 덜 새게, 이 단계 = 샌 것을 잡기.

## 1. 왜 따로 단계를 두나
- 생성 지시문에 원칙이 20개 넘어 하나하나가 묻힌다(K-S8은 일부만 먹힘).
- 한 가지만 맡은 사후 검사·수리는 잘 지켜졌다(v5.2 eval-repair: 수리 필요 13/16 → 2/16).
- 코덱스가 매번 짚은 결함이라 찾기 쉽다.

## 2. 위험과 막는 조건
위험: 11/12 3c 가독성 사후 교정에서 조건이 바뀌거나 빠져 정답 근거가 흔들렸다(bogi-writing-style). 지우기만 하면 풀 수 없거나 정답 시비가 생긴다.
조건:
1. 지우지 않고 **단서로 바꾼다**(행동·날짜·발화·값). 학생이 한 단계 추론으로 그 사실을 되찾을 수 있어야 한다.
2. 그 밖의 조건·값·인물·사건은 하나도 늘리거나 줄이지 않는다. 선지·정답 번호·발문은 그대로(선지가 바뀐 〈보기〉 표현을 인용하면 그 낱말만 맞춘다).
3. 바꾼 뒤 **정답을 모르는 별도 호출이 다시 푼다.** 정답이 그대로이고 하나로 정해지면 채택, 아니면 원본 유지(되돌림).
4. 억지 퍼즐 금지: 단서는 실제 상황에서 자연스럽게 기록될 정보여야 한다(일지, 대화, 날짜, 측정값).

## 3. 단계 (스크립트 leak-fix.mjs, eval-repair.mjs 뒤에 붙임)
- L1 노출 찾기 (정답·answerIntent를 앎): 정답과 경쟁 선지를 판정하는 데 쓰이는 사실 중, 〈보기〉 문장을 그대로 옮기기만 하면 되는 것(판정 관계: 지시 대상, 선후·이미, 같음·다름, 누구의 입장과 같음)을 찾아 문장 번호와 함께 적는다. 없으면 "없음" → 끝.
- L2 바꾸기 (같은 호출 또는 다음 호출): 찾은 문장만 위 조건 1·2·4대로 고친 〈보기〉와, 바꾼 문장 전후 대조표, 학생이 거칠 추론 한 줄.
- L3 다시 풀기 (정답 모름, 별도 호출): 고친 문항을 풀고 선지별 근거·정답 유일성.
- 서버 판정: 정답 일치 + 유일 + 〈보기〉 길이 변화 ±20% 안 → 채택. 아니면 원본.
- 출력: items-leakfix.json(채택본), leakfix-log.md(문항별 찾은 문장·바꾼 문장·추론·채택 여부), usage.json.

## 4. 시험 (첫 자동 실행 칸)
- 대상: 이미 두 평가자에게 '중'을 받은 8문항 = out-case-hs2 4(공시 A·B, 공손룡 A·B의 V1) + out-view-hs2 4(의미 A·B, 정보 A·B의 V1). 새 생성 없음.
- 블라인드: 지문마다 "고치기 전/고친 후"를 다른 문항처럼 섞고 같은 지문 기출 1문항 포함. 채택되지 않은(원본 유지) 문항은 빼고 수만 기록.
- 판정: codex exec 두 번(새 세션). 비교: 같은 문항의 전→후 등급 변화.
- 통과: 고친 문항 중 두 평가자 모두 '수능 같음'이 1개 이상이고, 등급이 내려간 문항이 없으면 → leak-fix를 생성기 기본 단계로(run 뒤 eval-repair → leak-fix). 등급 변화가 없으면 → 병목은 노출이 아니라 다른 곳(구조 설계)으로 보고 기록 후 멈춤 지점.
- 추정 비용: 문항당 L1·L2 1회 + L3 1회 ≈ $0.2~0.3 → 8문항 약 $2, 상한 $3.
