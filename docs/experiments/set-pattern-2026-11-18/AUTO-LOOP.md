# 고난도 칸 자동 실행 절차 (CLI용, 2026-11-20)

Ghootae 결정(2026-11-20): 생성 → 블라인드 → 코덱스 판정 → 집계는 CLI가 이어서 한다(복사·전달 없애기). **판정이 끝날 때마다 멈추고** 보고서를 남긴다. 다음 방향(규칙 수정, 다른 방법, 다음 칸)은 Ghootae가 정한다. (수정 2026-11-20 밤: 처음엔 규칙 수정·재실행까지 자동이었으나, Ghootae가 결과를 보고 "규칙 추가 대신 사후 노출 수리" 같은 더 나은 방향을 낸 사례가 있어 방향 판단은 사람에게 둠.) 웹 스레드는 칸이 끝날 때 보고서를 읽고 다음 칸·방향을 논의한다.

기본 자료: PROGRESS-hard.md(진척), STRATEGY-hard-cells.md(칸별 전략·순서), REVIEW-*.md(칸별 기록), deep-item-v5-2026-11-18/(생성기·kind 규칙).

## 0. 공통 규칙
- 파일을 git checkout·stash·restore로 되돌리지 않는다. 실행 전 kind 파일에 필요한 원칙이 있는지 grep으로 확인하고, 없으면 멈춘다.
- 사람 판정은 쓰지 않는다. 평가는 코덱스 두 평가자만.
- 생성한 쪽(gpt-6.1-sol 파이프라인)과 평가하는 쪽(codex)은 늘 다르게 둔다. 규칙을 고친 사람(CLI)이 평가하지 않는다.
- 비용: 단계마다 호출 수 × 단가로 미리 추산하고, 끝나면 usage.json 합산으로 실제 비용을 기록한다. 최소 실행이 기본(필요한 지문·버전만, ONLY=V1|V2 + KEEP_OUT 재사용). 수리가 돌면 문항당 약 $0.8(r3 실측), 추산은 이 값으로.
- 생성 규칙(rules-*, kind-*, polish-checklist, readability-guide, 수리 단계 기준)의 추가·수정은 웹 스레드에서 논의한다. 수정안이 나오면 웹 스레드 Claude가 함께 읽히는 규칙 묶음 전체와 대조 기출로 충돌·모순을 검토해 REVIEW-rules-<날짜>-<주제>.md를 남긴다. 그 결과로 다시 논의해 Ghootae가 결정한 문안만 CLI가 반영한다.

## 1. 한 칸 루프
1) 준비: 지문(passages/<id>)과 대조용 기출 〈보기〉 문항(같은 지문)을 확인. 없으면 만들고, 지도가 없으면 멈춤 지점 ①.
2) 생성 파이프라인 (2026-11-20 개정): **생성 → 노출 수리 → 정답 시비 수리 → 블라인드 → 판정.**
   - 생성: run.mjs (MODE=A 다음 MODE=B, B는 같은 회차 A를 피하게) → eval-repair.mjs REPAIR=1.
   - 노출 수리: leak-fix.mjs (IN=repair/items-final.json, OUT_DIR=<문항>/leakfix).
   - 정답 시비 수리: dispute-fix.mjs (IN=leakfix/items-leakfix.json, OUT_DIR=<문항>/dispute). **주의: 검사기 보정 미통과(2026-11-20, REPORT-dispute-fix.md: 기출 1/4 오탐, 목표 1/2 탐지).** 다시 보정하기 전까지는 '채택'만 쓰고, '잡힘'·'되돌림'은 블라인드 판정 때 참고 메모로만 쓴다(원본은 그대로 블라인드에 넣음). 예방은 규칙으로 한다: rules-common C22(판정을 지문 정의의 모호한 부분에 걸지 않음, 2026-11-20 Ghootae 결정). 다음 칸에서도 채점의 ㉳(정답 시비) 표시가 2문항 이상 반복되면, 두 시선 합의 검사기(정답 아는 찾기 + 정답 모르는 풀이자가 같은 선지를 짚을 때만 잡힘)를 다시 검토한다.
   - 생성 모델 기본값: **gpt-6.2-sol**(run·eval-repair·leak-fix·dispute-fix, REPORT-cell-gen62.md). 6.1로 돌릴 때만 GEN_MODEL=gpt-6.1-sol. 판정은 codex gpt-6.1-sol(5) 참고)이라 생성 모델과 다르다.
3) 검사기 보정: 같은 지문 기출을 eval-repair.mjs로 검사만. 기출이 "수리 필요"로 잡히면 그 갈래는 검사기 결과를 참고만 한다(관점 갈래가 그랬음, 2026-11-20).
4) 블라인드: 지문마다 생성 문항 + 기출 1문항, 순서 무작위, 출처 표시 없음. 발문은 통일하되 기출 선지가 원래 발문에 묶여 있으면(비판형 등) 원래 발문 유지. 결함 목록 ㉮~㉴는 BLIND-view-hs.md와 같게. 단 ㉴는 "학생이 내려야 할 판정(누가 긍정·부정하는지, 어느 쪽과 같은지)까지 〈보기〉가 말함"으로 적는다. 비판형 발문에서 비판의 전제를 주는 것은 ㉴가 아니다.
5) 평가: 코덱스를 비대화형으로 두 번 따로 실행(각각 새 세션, 이전 맥락 없음). 각자 답·등급(수능 같음/중/수능 아님)·한 줄 이유·결함 표시를 고정한 뒤 KEY와 대조. 결과 REPORT-<칸>-eval1.md, -eval2.md.
   - 실제 명령(2026-11-20 확인, codex-cli 0.160.1, ChatGPT 계정 로그인): 블라인드 파일만 든 임시 폴더를 평가자마다 따로 만들고(정답표 격리)
     `codex exec -m gpt-6.1-sol -s read-only --skip-git-repo-check --ephemeral -C <임시폴더> -o <임시폴더>/answer.md - < CODEX-PROMPT-<칸>.md`
     (`--ephemeral` = 세션 기록 없이 매번 새 세션, `-o` = 마지막 답 저장, `-s read-only` = 파일 쓰기 금지, 두 평가자는 병렬 실행 가능, 약 1분). 답은 표 + ```json 블록으로 받아 코드 에이전트가 KEY와 대조.
   - 판정 모델: **gpt-6.1-sol**(생성 모델과 같음). ChatGPT 계정 codex에서 기본 gpt-6.2-astra, gpt-6.2-sol, gpt-6.2-luna, gpt-6.1-luna, gpt-6.1-astra, gpt-6.1은 모두 "not supported"로 거부됨. 보고서마다 이 점을 한 줄 적는다. ChatGPT 계정이라 판정 토큰 과금 없음.
6) 집계: 정답 일치 수, 문항별 두 등급, 결함 표시 빈도, 기출 등급. 기출이 둘 다 '수능 같음'이 아니면 평가가 이상한 것 → 멈춤 지점 ②.
7) 판정:
   - **L2 통과** = 생성 문항이 모두 두 평가자에게 '중' 이상 + 두 평가자가 모두 '수능 같음'을 준 생성 문항이 1개 이상.
   - **거의 통과** = 모두 '중' 이상이지만 둘 다 '수능 같음'인 문항 없음.
   - **미달** = '수능 아님'이 하나라도 있음.
8) 멈춤: 판정 한 회가 끝나면 규칙을 고치지 말고 멈춘다. REPORT-cell-<칸>-r<회차>.md에 ① 등급표 ② 반복된 결함 원인(2문항 이상) ③ 다음 선택지 2~3개(각각 무엇을, 비용, 무엇을 확인하는지)와 추천 하나를 쓴다. Ghootae가 고르면 그 회차를 이어서 돌린다.
9) 기록: PROGRESS-hard.md 해당 칸(단계·근거·다음), REVIEW-<칸>.md에 회차별 결과, 실제 비용. 칸이 끝나면 커밋·푸시(메시지에 칸 이름·결과 등급·바꾼 규칙).

## 2. 멈춤 지점 (Ghootae에게 묻고 기다림)
① 새 지문이나 새 지도가 필요할 때(비용 추가) ② 기출이 '수능 같음'을 못 받아 평가 자체가 의심될 때 ③ 한 칸 비용이 상한을 넘을 때(칸당 기본 $6) ④ 개정 2회 뒤에도 '거의 통과'에 못 미칠 때 ⑤ 공통 규칙(rules-common)이나 생성기 코드를 바꿔야 할 때

## 3. 칸 순서 (STRATEGY 3절)
② 관점 L2(끝남, 거의 통과) → **첫 자동 칸 = 노출 수리 시험(LEAK-FIX.md 4절)** → ③ 그래프(보류, ⑥ 경제 묶음에서 재시험. 명세 JSON → SVG, 코드 작업 있음 → 멈춤 지점 ⑤로 먼저 보고) → ④ 사회 A형 시험 → ⑤ 생성 지문 L3 → ⑥ 경제 표·그래프 → ⑦ 과학 관점·실험.

## 4. 칸이 끝날 때 보고 (웹 스레드로 가져갈 것)
REPORT-cell-<칸>.md 5~10줄: 결과 등급, 회차별 변화, 남은 결함, 바꾼 규칙, 실제 비용, 다음 칸.

## 5. 웹 스레드가 하던 일을 루프 안에서 하는 법 (2026-11-20 추가)
루프를 돌리는 Claude Code가 아래를 직접 한다. 웹 스레드는 칸 보고서를 읽고 칸 사이 방향만 정한다.

**가. 결과 읽고 진단 (집계 뒤)**
- 두 평가자의 "판정을 가른 이유"를 문항별로 모아, 같은 원인이 2문항 이상에서 나온 것만 결함으로 잡는다.
- 원인은 "무엇이 정답을 쉽게 만들었나"로 쓴다(예: 〈보기〉가 지시 관계를 직접 말함, 안 쓰이는 사건, 인물의 입장 선언). 등급 숫자만 보고 규칙을 만들지 않는다.

**나. 규칙 후보 적기**
- CLI는 규칙 파일을 직접 고치지 않는다. 보고서에 후보(원칙 한두 문장 + 근거 문항·평가자 지적)만 적는다. 결정된 문안이 오면 그대로 넣고 grep으로 확인한다.
- 후보 형식(웹이 문안을 쓸 때의 참고): 원칙 한두 문장 + 점검 질문 + 다른 소재 예시 1개. 시험 지문·생성 문항의 소재를 예시로 쓰지 않는다(오염). 새 번호를 붙이기 전에 같은 kind 파일·rules-common에 비슷한 원칙이 있는지 찾는다.
- 관점만 돌릴 때는 kind-case가 안 읽히고, 사례만 돌릴 때는 kind-view가 안 읽힌다. 두 갈래에 다 맞는 교훈이면 양쪽에 적는다.

**다. 실행 전 점검 (웹이 실제로 잡았던 실수들)**
- 고친 파일을 저장한 뒤 다시 읽어 새 원칙이 들어갔는지 grep으로 확인(두 번 되돌려진 적 있음).
- 블라인드: 기출 선지가 원래 발문에 묶여 있으면(비판형 등) 원래 발문 유지. 요청문(CODEX-PROMPT)의 문항 수가 실제와 같은지. KEY의 정답이 각 items-final.json과 같은지. 출처를 드러내는 표기(ⓐ 같은 지문 표시, 원래 번호)가 남지 않았는지.
- B형이 피할 A형은 같은 회차 결과인지.

**라. 기록과 보고**
- PROGRESS-hard.md 해당 칸 + REVIEW-<칸>.md에 회차별: 등급표, 결함 빈도, 진단 한 줄, 바꾼 규칙, 실제 비용.
- 칸이 끝나면 REPORT-cell-<칸>.md(5~10줄)와 project-files 쪽 사본은 웹 스레드가 읽어서 맞춘다.

**마. 루프가 하지 않는 것 (웹·Ghootae 몫)**
- 칸 순서 바꾸기, 새 갈래·새 지문 유형 도입, 통과 기준 바꾸기, rules-common·생성기 코드 변경, 칸 사이에 쌓인 규칙 정리(중복·충돌 점검), 규칙 수정·충돌 검토.
