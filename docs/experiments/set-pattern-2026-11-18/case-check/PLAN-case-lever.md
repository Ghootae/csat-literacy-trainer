## 1. 왜 순서인가
- run.mjs는 1-search(지문 문장 쌍 → 헷갈리는 거짓 진술) → 2-select(4개) → 3-assemble(〈보기〉를 입힘) 순서다. 거짓이 〈보기〉보다 먼저, 지문 안에서 정해진다.
- 3-assemble에는 이미 GN1("지문의 개념 정의·일반 원칙을 반대로 말하는 것으로 거짓을 만들지 않는다")이 있다. 그런데도 도덕적 운 문항의 결정 선지 80%가 원리형이었다. 규칙 문장만으로는 안 된다는 뜻이다. 그래서 순서와 출력 칸을 바꾸고, 서버가 확인한다.

## 2. 바꾸는 것 (사례 갈래 + RULES_V=6 + CASE_FLOW=lever일 때만)
1-search·2-select는 그대로 둔다(같은 실행의 다른 버전이 쓴다). 사례 버전의 3-assemble 지시에서 출제 과정 1·2단계를 아래 순서로 바꾼다.
- **가. 원리 카드(2~4장):** 원리(지문 원문 인용), 판정자, 갈림 변수. 정의만 있고 갈림 변수가 없는 원리는 고르지 않는다. 재료 B·S의 거짓 진술은 "어느 구역에서 원리를 고를지" 참고로만 쓰고, 선지로 옮기지 않는다.
- **나. 〈보기〉 + 갈림 사실 표:** 〈보기〉를 먼저 쓴다. 표의 한 줄은 〈보기〉 문장 인용, 변수 값, 판정자별 판정이다. 〈보기〉 문장은 모두 표에 쓰인다. 같은 말인데 값이 다른 '헷갈리는 짝'을 하나 이상 둔다.
- **다. 선지:** 선지는 표의 한 줄(또는 두 줄)을 쓴다. 원리는 지문대로 쓰고, 거짓은 그 줄의 사실 값을 잘못 읽은 결론으로 만든다. 잘못 읽는 쪽은 헷갈리는 짝에서 고른다.
- **라. 정답(마지막):** 부정 발문이면 헷갈리는 짝·두 줄 결합에서 나온 거짓을 정답으로 고른다. 긍정 발문이면 거짓 4개가 서로 다른 줄을 잘못 읽게 한다.
- **JSON 칸:** principleCards, leverTable, choiceLevers(선지별 facts, 거짓이면 misread·corrected).

## 3. 서버 확인 (classify-v6.mjs checkLeversV6, 3-assemble 직후)
| 번호 | 확인 | 어기면 |
|---|---|---|
| L1 | leverTable의 fact가 〈보기〉에 실제로 있는 문장인가 | 오류 |
| L2 | 〈보기〉 문장이 모두 표의 어느 줄에 쓰였나 | 경고 |
| L3 | 선지마다 facts가 있고, 모두 표의 fact인가 | 오류 |
| L4 | 결정 선지(부정 발문 정답 / 긍정 발문 오답)마다 misread가 있나. 긍정 발문이면 오답 4개가 서로 다른 fact를 3개 이상 쓰나 | 오류 |
| L5 | 원리 카드가 2장 이상인가 | 경고 |
- 오류가 있으면 그 오류 목록을 붙여 3-assemble을 한 번만 다시 부른다(3-assemble-r). 그래도 남으면 기록만 하고 진행한다(이번은 측정).
- 3b 다듬기·3c 가독성 뒤에는 L1만 다시 보고 기록한다. 다듬기로 인용이 어긋날 수 있다. leverTable·choiceLevers는 그래프 명세처럼 3단계 것을 버전별로 붙여 둔다.
- 공통 규칙·갈래 규칙·전략 파일은 고치지 않는다. CASE_FLOW가 없으면 지금 동작 그대로다.

## 6. 걱정되는 점
1. 오답이 "〈보기〉를 대충 읽었나" 시험으로만 흘러 너무 쉬워질 수 있다. 헷갈리는 짝 칸으로 막고, 평가 이유에서 확인한다.

3. 다듬기 단계가 인용 문장을 바꿀 수 있다. 3c 뒤 L1을 기록해 본다.
