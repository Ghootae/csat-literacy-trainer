## 1. graphPlan을 손으로 적은 것

수정안 3절 형식: `focus / variables(x, y, others) / relation(quote, para) / graphType / shape / why`. relation.quote는 지문 `full_text`에서 그대로 찾아 복사했고 모두 지문에 그대로 있음을 확인했다(공백 정리 후 부분 문자열 검사).

**s1. 옥신 (75)**
```
"graphPlan":{"focus":"옥신 농도가 늘 때 기관마다 생장 반응이 달라지는 모양을 ⓐ~ⓒ에서 읽고 지문의 시작 농도·최고 생장점·억제 전환에 맞는지 가린다",
 "variables":{"x":"옥신의 농도(M)","y":"생장 반응 정도(0 위 촉진, 아래 억제)","others":["기관(눈·뿌리·줄기 → ⓐ~ⓒ)"]},
 "relation":{"quote":"생장 반응이 시작되는 옥신의 농도는 기관별로 다르며, 옥신의 농도가 일정 범위까지 증가할 때는 생장 촉진의 정도가 높아지지만, 최고 생장점을 지난 이후에는 생장 촉진의 정도가 낮아지다가 일정 농도에 이르면 생장이 억제된다.","para":3},
 "graphType":"두 양의 관계 평면","shape":"봉우리(0에서 시작 → 최고 생장점 → 0 아래로)",
 "why":"한 농도 축 위에서 기관마다 시작·최고점·억제 전환 농도가 다른 것을 한 평면에 겹쳐야 비교된다"}
```

**s2. 히스테레시스 (33)**

 "variables":{"x":"시간","y":"수치(혈장 약물 농도·약효 공통)","others":["측정 대상(혈장 약물 농도 / 약효)"]},
 "relation":{"quote":"왜냐하면 약효는 일반적으로 목표 조직의 약물 농도에 비례하는 것으로 보기 때문이다.","para":6},
 "graphType":"시간·위치 진행","shape":"봉우리 2계열(둘 다 0에서 시작, 최댓값 시점 Ⓐ < Ⓑ, 중간에 교차)",
 "why":"같은 시간 축에서 두 양의 최대 시점이 다름을 보려면 두 곡선을 한 평면에 놓아야 한다"}
```

**s3. 독점 (44)**
```
"graphPlan":{"focus":"한계수입=한계비용인 생산량(Q₁)과 그 생산량에서 수요곡선이 정하는 가격(P₂)을 읽기",
 "variables":{"x":"생산량(Q)","y":"가격(P)","others":["곡선 종류(수요·한계수입·한계비용)"]},

### 1-a. graphPlan을 막힘없이 채울 수 있었나

| 칸 | 75 옥신 | 33 약물 | 44 독점 | 80 ETF |
|---|---|---|---|---|
| focus | 쉬움 | 쉬움 | 쉬움 | 쉬움 |
| variables x·y | 쉬움 | 쉬움 | 쉬움 | 쉬움 |
| variables others | **어려움**: 기관(눈·뿌리·줄기)은 〈보기〉 글이 말하고 그림엔 ⓐ~ⓒ로만 나옴. 지문은 기관별로 다르다고만 말함 | 쉬움 | 쉬움 | 쉬움 |
| relation 인용 | 쉬움(3문단에 모양까지 그대로) | **어려움**: 히스테레시스 정의가 〈보기〉에만 있고 지문엔 모양 문장이 없음. 6문단의 '비례'로 대신함 | 보통: 두 문장(2문단 양 관계, 3문단 교점) 중 하나만 고름 | 보통: 한 문장이 길고 모양이 아니라 '괴리 발생 가능'만 말함 |
| graphType | 쉬움 | 쉬움 | 쉬움 | 쉬움 |
| shape | **어려움**: 계열 3개가 같은 '봉우리'이나 시작 농도·높이·0 통과 위치가 다름. 한 칸 shape로는 이 차이가 안 적힘 | 보통: '봉우리 2, Ⓐ<Ⓑ'는 말로 적힘 | 쉬움 | **어려움**: 불규칙 곡선이라 "그 밖"과 말로 적을 수밖에 없고 서버 확인(graphSpec 계열 shape와 같음)이 할 일이 없음 |
| why | 쉬움 | 쉬움 | 쉬움 | 쉬움 |

해석: 채우기 어려운 곳은 (1) 모양을 정하는 문장이 지문이 아닌 〈보기〉에 있는 경우(33), (2) 한 plan에 shape가 하나뿐인데 계열마다 모양이 다른 경우(75·44·80), (3) 문항이 가리키는 '다른 변수'가 지문 본문이 아니라 〈보기〉 글에 있는 경우(75). 이 셋은 수정안 3절의 "지문이 방향만 말하고 모양을 정하지 않으면 〈보기〉의 측정 결과로 준다" 규칙과 맞닿는다. 칸 이름·구조를 바꿀 근거가 되는지는 웹 판단.
또 CENSUS의 하위 에이전트 인용 14개 중 4개(33·40·44·80)는 지문 문장을 줄이거나 풀이를 붙여 **지문에 그대로는 없는 인용**이었다(옥신 75 등 10개는 그대로 있음). 서버가 "relation.quote가 지문에 그대로 있음"을 검사하면 모델이 문장을 요약해 쓸 때 걸러진다는 뜻이다(수정안 5절 확인 항목의 필요성을 뒷받침하는 측정).

1. 기호로 적힌 세로축 눈금과 수평 기준선(44의 P₁·P₂, 75의 +·−). `yAxis.values`는 숫자만 받고, 수평 점선도 0이 아닌 숫자 눈금에서만 생긴다.
2. 곡선 위 점이 없는 곳의 수직 점선(75에서 ⓒ 곡선 위 M₂ 수직선 → 점 ⓝ을 더해 흉내 냄, 점·기호가 남음).
3. 곡선 이름 표시: 곡선 끝에 첫 낱말만 찍혀 끝점이 같으면 겹치고(80) 오른쪽 끝에서 잘린다(44).
4. 배경 격자(80).
5. 선 굵기 구분(75). 실선·점선 구분이 범례에 안 나옴(80).
6. 기출엔 없지만 수정안이 말한 '두 계열 사이 구간 표시'는 지금 형식에서 곡선과 가로축 사이만 가능하다(`shade`). 기출 14개엔 곡선 사이 색칠이 없고, 구간 표시는 31번의 화살표 구간 1개뿐이다.

## 5. 코드를 고친다면 어느 함수의 무엇을 (고치지는 않음)

`docs/experiments/deep-item-v5-2026-11-18/graph/render.mjs` 기준:

| 함수 | 고칠 것 | 이유 |
|---|---|---|
| `validateSpec` | series 항목에 `shape`를 받는 분기 추가(`points` 또는 `shape` 중 하나). `refs`·`guides` 필드 검증 | 수정안 (가) |
| (새) 모양 → 점 생성 함수 | shape 성질(방향·빠르기·꺾임·끝·계열 사이)로 점 목록을 만드는 서버 계산. 계열 사이 관계(같은 절편·배수·합·정렬)·값 수준을 입력으로 | 손 시험에서 계열 정렬·값 수준이 모든 어려움의 중심 |
| `renderSvg` | ① `guides` 배열 추가: 수평·수직 기준선(위치는 값 또는 기호, 라벨 가능) ② 곡선 이름 배치(끝점 겹침 회피, 오른쪽 잘림 방지) ③ 점 계열(선 없이 점) ④ 격자 옵션 ⑤ 선 굵기·실선/점선 범례 ⑥ 교점 기호 자동 부여(계열 사이 교점을 `analyze`의 `cross`에서 받아 찍기) | 4절 1~5, 22·51 |
| `renderSvg`의 `shade` | 두 계열 사이·기준선과 계열 사이 구간 지원(수정안 도구 ③) | 수정안. 기출 근거는 약함 |
| `analyze`/`readingText` | 눈금 label 뒤 `xAxis.unit` 이어붙임 제거(`M₁M`·`t₁t` 방지). 기호 눈금(수평 기준선)을 읽기 판에 적기 | 2절 |
| `run.mjs`(다음 단계) | graphPlan 칸 + 서버 확인(축 이름 = variables, quote가 지문에 그대로 있음, shape 일치). shape를 계열마다 두는 구조 검토 | 1-a(계열마다 shape 다름) |

## 6. 열린 질문 (웹 판단)
