## 2. 무엇이 잘 됐나

- **graphPlan이 Ghootae 순서대로 쓰였다.** A는 문항 주제(두 시장의 탄력성·부족량 비교) → 겨냥 변수(가격·수량) → 관계 평면 → 모양(지문 2문단 "가격이 오르는 동안 수요량은 줄고 공급량은 늘어")으로 갔다. 그림은 계획대로 네 선이 한 점 E에서 만난다. 지난번(조세 귀착) 같은 '세액·시점 값 선'으로 새지 않았다.
- **새 도구를 실제로 썼다.** A는 기호 눈금 P₁~P₃, 세로 기준선, 교점 표시 E를 선지가 부르는 곳에 두었다. 평가자 8명 중 그림을 탓한 사람 0, 6명이 '수능 같음'.
- **좌표·교점 결함은 나오지 않았다.** 그래프 2차(서버가 모양에서 점 계산)를 시작할 조건이 생기지 않았다.
- 수리 단계가 그래프·계획을 바꾸지 않았다(축 이름 어긋남 0). 비용 $1.08.

## 3. 무엇이 문제였나 (B형)

### 3-1. 렌더러 버그 (원인 확인함, 코드 몫)
B의 '병' 선 끝점(1, 120)에는 표시 기호가 없다. 그런데 읽기 판이 "병: ⓔ(100) → ⓑ"라고 적었다. `readingText`의 `label` 함수가 같은 가로 위치의 표시를 찾을 때 **다른 계열의 표시(갑의 ⓑ)까지 집어 온다.** 같은 파일의 `where` 함수는 이 경우를 "같은 가로 위치"로 따로 처리하는데 `label`만 빠졌다. 평가자 8명 전원이 이 불일치를 잡았고 B의 평가 이유 8건이 모두 이것이다. 문항이 아니라 우리 렌더러가 B 점수를 깎았다.
- 함께 고칠 것: 표시도 눈금도 없는 끝점 높이(병 120)를 읽을 수 없다. 끝점 값이 세로 눈금에 없고 표시도 없으면 validateSpec 경고를 낸다(그리기는 그대로).

### 3-2. 문항 설계 쪽 관찰 (규칙은 만들지 않음)
- B는 가로축을 '수요의 가격 탄력성'으로 잡고 점 두 개짜리 직선 세 개를 그렸다. 사실상 표 한 장(갑·을·병 × 탄력성 0.5·1)을 선으로 이은 것이라, 그래프여서 얻는 것이 적다.
- 계획에는 모양 근거를 '지문'으로 적었지만, 인용한 5문단 문장은 탄력성 정의일 뿐 '우상향'을 말하지 않는다. 실제 모양은 〈보기〉 수치에서 나왔다(shapeFrom은 '보기'가 맞다). 서버는 인용이 지문에 있는지만 보므로 이것을 못 잡는다.
- 한 번 본 일이라 규칙을 더하지 않는다(WORKING-RULES 5 과적합 경계). 같은 일이 재생성에서 또 나오면 그때 kind-graph 점검 질문 후보로 올린다. 후보 문안: "이 그래프가 같은 내용을 표로 줄 때보다 나은 점은? / 인용한 문장이 모양(방향·만남)을 직접 말하는가?"

### 3-3. 작은 것 (고치지 않음, 기록)
- A의 범례에서 A 수요·A 공급이 같은 실선, B 둘이 같은 점선이라 범례만으로 수요와 공급을 못 가른다(곡선 이름이 끝에 있어 풀이엔 지장 없음).
- A의 가로축이 가격, 세로축이 수량이다. 경제 교과서 관례(세로 가격)와 반대지만, 지문이 "가격이 오르는 동안 수량이 …"로 가격을 원인처럼 말해 graphPlan으로는 맞다. 평가자도 탓하지 않았다. 관례를 규칙으로 넣지 않는다(기출은 허용 목록이 아니라는 Ghootae 관점).
