# 타이틀 판정 — 압축 판별이 실제로 되는가

- 날짜: 2026-08-10 / 모델: `claude-opus-4-8` / effort `medium`
- 질의: `packages/pipeline/fixtures/title-queries/{nietzsche-p1,photosynthesis-p5}-hand.json` (손으로 작성)
- CLI: `npm run title -- <반복횟수>`
- 원시 출력: `title-compression-2026-08-10.log`

## 무엇을 물었나

최종 타이틀 단계에서 두 능력을 나눠 보기로 했다.

```
관계 통합    영역들을 하나의 중심 관계로 연결했는가   → 기본 성공 조건
위계적 압축   그것을 상위 표상으로 압축했는가          → 보너스
```

사용자 지적이 이 분리의 근거다: **"'적당한' 추상화란 것의 기준이 인간에게도 매번 달라질 수
있는 지점이니까."** 그래서 압축은 게이트가 아니라 보상으로 두기로 했다. 다만 보상조차
흔들리면 같은 답에 다른 등급이 나온다 — **이 실험은 그 흔들림을 잰다.**

## 설계 — 압축 판별을 스키마가 아니라 질의로

`compressed` 같은 필드를 출력 스키마에 넣으면 캐시 지문이 달라져 **회귀 3세트를 통째로 다시
재야 한다.** 질의로 두면 프롬프트도 스키마도 그대로다.

```
qT1  scope      이 문단은 무엇에 관한 글인가?          과대추상 차단
qT2  relation   최상위 관계는?          (critical)    기본 성공 조건
qT3  argument   상위 관계로 압축했는가?                 보너스
```

`qT3`의 수용 기준이 이 실험의 핵심이다:

```
판정 대상은 내용의 정확성이 아니라 조직 방식이다.
  내용이 모두 맞아도 조직이 나열이면 미보존이다.
하나의 중심 서술(주절 하나)에 나머지가 수식·근거로 종속되면 인정
대등하게 이어지면(~이고, ~하며) 미보존
길이는 기준이 아니다
```

**이 시스템에서 유일하게 조직(형식)을 보는 판정이다.** 다른 모든 축은 의미를 본다
(`expressionProfile`은 explicit/implicit을 기록하지만 점수축이 아니다). 타이틀에서만
예외인 이유는 **타이틀의 목적 자체가 추상화 행위**여서, 형식이 곧 능력의 증거이기 때문이다.

문단 둘을 함께 쟀다 — 니체는 **대립**, 광합성 P5는 **인과**다. 한 문단에서만 되면 질의
구조가 관계 유형에 의존한다는 뜻이므로 일반화할 수 없다.

### 핵심 질문의 답 — **된다**

```
연결(~이고, ~하며)  →  미보존   니체 3/3
압축(상위 표상)     →  보존     두 문단 6/6
경계(주절+종속)     →  보존     두 문단 6/6
```

**연결과 압축이 갈린다.** 사람도 흔들릴 것으로 본 경계 사례(주절 하나 + 근거 종속)에서도
6/6으로 일관되게 압축으로 판정했다.

### "기대와 다름" 4건 중 3건은 **기대값이 틀렸다**

**① 니체 나열 → qT2 보존.** 문장이 셋으로 나뉘었어도 대립 관계 자체는 들어 있고, `qT2`
수용 기준이 "표현 형식은 묻지 않는다"이다. 판정이 맞고 기대가 틀렸다. 그리고 이 결과가
**두 질의의 분업을 보여준다** — 관계는 있으나(`qT2` 보존) 조직은 나열(`qT3` 미보존).

**② 두 "나열" 프로브의 성격이 달랐다.** 니체 쪽은 관계가 들어 있고 P5 쪽은 사실만
늘어놓았다. 같은 이름을 붙였지만 다른 것을 재고 있었다 — 프로브 작성 실수다.
`나열-관계있음` / `나열-관계없음`으로 나눠 두 문단 모두에 넣었다.

**③ 모순인데 `qT3` 보존.** `qT3`는 조직만 보므로 내용이 틀려도 압축 형태면 보존이 맞다.
설계대로다. 다만 **보상은 `관계보존`일 때만 계산해야 한다** — 모순 응답에 압축 보상이
붙으면 안 된다.

### 진짜 불안정은 1건

```
P5 연결   qT3: · O ·   3회 중 1회 갈림
"…만들고, …농축하며, 그 결과 C3보다 효율이 높다"
```

**"그 결과"**가 있어 인과 종속으로 읽힐 여지가 있다. 사람도 갈릴 자리다.

**나머지 27칸은 전부 일관되고 기대와 일치했다.**

## 비용 — 타이틀 채점은 영역 채점의 절반이다

```
              출력토큰    지연     1건 비용
타이틀 채점        636   10.0s   $0.0402
영역 채점        2,015   22.0s   $0.0824
```

앞서 "질의가 적으니 싸다"고 추정했고 실측이 그것을 확인했다. 3단계 설계가 채점을 2회로
늘리지만 **비용은 2배가 아니라 1.5배**다.

## 판단

```
qT2 관계 통합   14/14 일관         → 기본 성공 조건으로 쓸 수 있다
qT3 압축        13/14 일관         → 보상으로만. 게이트로 쓰면 안 된다
               (남은 1건은 연결/압축 경계)
```

사용자 지적이 기계에서도 **정확히 그 자리에서** 확인됐다 — 연결과 압축의 경계에서만
갈리고, 명확한 사례에서는 안 갈린다. **게이트로 쓰지 않기로 한 결정이 옳았다.** 통과
조건이었다면 P5 연결 응답을 낸 학생이 같은 답으로 어떤 날은 막히고 어떤 날은 통과한다.

**보상은 점수로 둔다** (사용자 결정). 흔들림이 1/28로 작고, 필요하면 표시로 내리는 것이
쉽기 때문이다 — 보상 누적은 아직 구현 전이라 지금은 규칙만 정하는 단계다.

## 부수 발견 — 합의문 R2의 내부 모순

R2 본문은 "**충족된** 코어 슬롯들을 아우르는가"라고 쓰는데, 바로 아래 반-게이밍 제약표는
그것을 게이밍 벡터로 지목한다:

```
| 덜 맞출수록 쉬워짐 | 분모가 "충족 슬롯"이라 1개만 충족한 학생은
                     1개만 포괄하면 만점 비율 | 분모를 **코어 슬롯 전체**로 고정 |
```

`packages/core/src/domain/scoring.ts`의 `TitleEvaluation`은 제약표 쪽(전체 고정)을 따른다.

**3단계 설계가 이 충돌을 거의 해소한다.** 영역을 다 고친 뒤 타이틀을 쓰므로 대부분
충족 슬롯 = 전체 슬롯이다. 다만 영역당 수정 1회를 쓰고도 실패한 학생은 미충족 영역을 가진
채 타이틀 단계에 온다.

**전체 고정을 유지한다.** 그때는 정답이 이미 공개된 뒤이므로 학생은 모든 슬롯을 알고 있고,
"덜 맞출수록 쉬워짐"은 실재하는 게이밍이다. R2 본문의 "충족된"은 타이틀을 영역 수정 **전에**
쓰던 옛 설계의 잔재로 본다.
