# 고위험 3개 지문 canary 결과

## 1. 전체 맥락

24개 지문의 140개 문단을 전부 실행하기 전에, 볼록렌즈·준거가격·지진파 및 내진설계의
16개 문단을 고위험 canary로 실행했다. 2차 수리까지 포함한 최종 계획 해시는
`sha256:3e3d5b07bd11f5b2233b5561bc9b71c8275fc4f58a38803ab26c196ecb507848`이다.

## 2. 수행한 작업에 대한 목적

문단 골드 3단계 생성, 명제 Bundle 보존, 독립 의미 감사, 부분 수리와 재감사가 실제 API에서
끝까지 작동하는지 확인하고, 실패하면 나머지 21개 지문의 실행을 차단하는 것이 목적이었다.

## 3. 작업 과정

Terra Medium과 `service_tier: default`로 16개 문단의 생성을 시작했다. 생성 후보가 만들어진
문단만 독립 감사에 전달했다. 각 호출 전에는 4달러 canary 비용 상한을 검사했고, 응답마다
실제 토큰 비용을 저장했다. 감사 결과가 `REPAIR_REQUIRED`인 문단에는 수리와 재감사를
수행했다. 1차 재감사에서도 문제가 남은 세 문단에만 2차 수리와 재감사를 수행했다.

## 4. 작업 결과

- 1차 실행 실제 API 응답: 53회
- 1차 실행 누적 비용: 약 1.2226달러
- 1차 수리와 재감사까지 누적 API 응답: 86회
- 2차 수리와 재감사까지 최종 API 응답: 92회
- 최종 누적 비용: 약 2.4021달러
- `AGENT_AUDITED`: 13문단
- `REVIEW_REQUIRED`: 3문단
- 나머지 21개 지문: 실행하지 않음
- canary 결정: `STOP`

1차 실행에서 12개 문단이 미통과한 직접 원인은 다음과 같았다.

- 생성 요청 타임아웃: 3문단
- 감사 요청 타임아웃: 1문단
- 감사가 의미 문제를 찾아 수리가 필요했지만 수리 Structured Output 스키마가 API 계약에
  맞지 않아 호출 전에 거부됨: 8문단

감사기는 실제로 다음과 같은 의미 문제를 찾아냈다.

- 단순 병렬 관계를 인과·근거 관계로 과도하게 연결
- 조건부 설명을 단정적인 원인으로 확대
- PS시 정의의 잘못된 계보
- 비점 격차 증가와 정의 명제의 혼동
- 최소 착란원의 명명 대상 변경
- 중심 이야기와 중심축의 필수 의미 누락

수리 스키마와 타임아웃을 수정한 뒤 기존 응답을 재사용해 canary를 재개했다. 13개 문단은
감사에 통과했다. 다음 3개 문단은 1회 자동 수리 후에도 좁은 의미 쟁점이 남아 2차 수리와
재감사를 수행했다.

- 볼록렌즈 3문단: 자오면의 성질과 기능을 근거 관계로 과도하게 연결한 간선 1개
- 준거가격 5문단: 거래효용의 발생·상승 구분, 전략의 작동 목적, 조건 양상 3개
- 지진파 2문단: PS시의 거리별 변화까지 피해 저감의 직접 수단으로 연결한 간선 1개

2차 수리는 위 쟁점을 수정했지만, 독립 재감사는 세 문단 모두에서 다시 좁은 쟁점을 찾았다.

- 볼록렌즈 3문단: 병렬 속성을 단방향 `구체화` 간선으로 남겨 둠
- 준거가격 5문단: 조건절을 `신뢰하는 경우가 있다`라는 존재·가능 진술로 바꿈
- 지진파 2문단: 원문에 없는 `PS시 활용의 구체적 방식`을 보조 개념에 남김

두 차례 수리 이력과 각 단계의 정확한 JSON은 `canary-review/`에 별도로 보존했다.

## 5. 결과 해석

독립 감사는 형식 문제가 아니라 미세한 의미 확대와 조건 양상 변경까지 찾아냈다. 최초 감사에서
수리가 필요했던 11개 중 8개는 1차 수리로 통과했고, 나머지 3개는 두 번 수리해도 새 쟁점이
남았다. 자동 수리를 더 반복하면 표현 수정이 계속 이어질 가능성이 있다.

재개 실행 중 기존 수리 Bundle을 재조립할 때 실행 ID가 달라지는 문제가 두 차례 드러났지만,
이때 새 API 호출은 발생하지 않았다. 원래 수리 응답의 API response ID로 당시 Bundle을 정확히
재현하도록 고쳤고, 11개 기존 재감사 입력 해시가 모두 일치함을 무료로 확인한 뒤 2차 수리를
실행했다.

사용자 요청에 따라 여기서 중단했다. 나머지 124개 문단에는 API 호출을 하지 않았으며, 세
미통과 문단을 추가로 자동 수정하지도 않았다. 다음 판단은 16개 직접 검토 자료를 읽은 뒤
내린다.

이후 사용자–에이전트 협업으로 세 문단을 최소 수정했고, 사용자가 카나리 16개를 모두 승인했다.
최종 승인 manifest는 자동 경로 13개를 `AUTOMATIC_AGENT_AUDITED`, 협업 경로 3개를
`SEMIAUTOMATIC_USER_AGENT_APPROVED`로 구분한다. 이 후속 승인은 자동 canary gate의 당시
`STOP` 기록을 덮어쓰지 않고 별도의 승인 계보로 보존한다.
