# 충실도 검사기 (2026-11-16)

생성 지문이 고른 구조(설계도)대로 쓰였는지 자동으로 잰다. 인수인계 handoffs/2026-11-15-catalog-generator-v2-and-goals.md 3.1절의 구현이다.

쉽게 말하면 이렇다. 설계도를 모르는 검사관(구조 추출기)이 완성된 지문을 보고 평면도를 그린다. 그 평면도를 설계도(목표 하위 구조)와 겹쳐 보고, 맞는 곳, 덧붙은 곳, 빠진 곳, 바뀐 곳을 표시한다. 덤으로 기출 문장을 베낀 곳이 없는지, 분량이 기출 범위인지도 본다.

## 1. 단계

| 단계 | 하는 일 | 방식 | 목표 구조를 아는가 |
|---|---|---|---|
| A 추출 | 지문의 구조를 뽑는다(목적, 논리, 문단 기능, 움직임, 만나는 곳, 비워 둔 곳) | 모델. 기출 158세트에 쓴 structure-catalog/prompts/1-extract.md 그대로, effort high | 모른다 |
| B 라벨 | 문단마다 통일 어휘(기능 40개)를 붙인다 | 모델. structure-catalog/prompts/2b-relabel.md + vocab.json 그대로, effort medium | 모른다 |
| C 배열 대조 | 라벨 배열을 목표 array와 정렬한다. 단일 하위 구조 37개 전체와도 정렬해 가장 가까운 구조 5개를 낸다 | 코드(align.mjs) | 안다 |
| D 비교 | 평면도와 설계도를 겹쳐 요소별·축별로 판정하고 종합 판정을 낸다 | 모델. prompts/compare.md, effort high | 안다 |
| E 겹침·분량 | 기출 158세트 본문과 연속 15자 이상 겹치는 곳, 글자·문장 수 | 코드 | — |

A·B가 기출과 똑같은 지시문을 쓰므로, 생성 지문의 평면도는 기출의 평면도와 같은 눈금으로 그려진다. 목표 구조는 C·D에서만 쓴다.

### D의 판정 네 가지

- **따름**: 배열 요소가 모두 맞고, 축이 모두 같고, 짜임을 바꾸는 덧붙음이 없다.
- **대체로 따름**: 이 하위 구조를 같은 유형의 다른 하위 구조와 가르는 요소와 축은 맞다. 어긋남이 한 곳 이하다.
- **절반**: 앞이나 뒤 한쪽은 따르지만, 가르는 요소·축이 하나 이상 다르거나 짜임을 바꾸는 덧붙음이 있다.
- **따르지 않음**: 뼈대가 다르다.

덧붙음은 "짜임을 바꾸는가"를 따로 표시한다. 한두 문장짜리 연결은 바꾸지 않는 덧붙음이다. 목표와 다르게 쓰인 부분이 다른 1차 유형을 닮았으면 그 유형도 적는다(예: 입장 대립 글에 요건 → 판정 방식이 섞인 경우).

### C(코드 대조)를 믿을 수 있는 정도

라벨 글자만 보고 정렬하므로 참고용이다. 기출로 시험했다(align-selftest.mjs, API 없음).

- 하위 구조에 속한 단일 기출 92편의 라벨 배열을 37개 단일 하위 구조와 정렬하면, 자기 하위 구조가 1위인 경우 55편(60%), 3위 안 74편(80%), 1위의 1차 유형이 맞는 경우 70편(76%)이다. 무작위로 고르면 1위가 될 확률은 3% 정도다.
- array가 이 기출들에서 나왔으므로 낙관적인 숫자다. 생성 지문에서는 이보다 낮다고 본다.
- 그래서 판정은 D가 내고, C는 D에 참고로 넘기고 보고서에 함께 싣는다.
- 참고로 "가장 가까운 기출 한 편"을 찾는 방식도 시험했는데, 같은 하위 구조를 찾은 경우가 71편 중 8편뿐이라 뺐다.

### E(겹침)의 기준

- 공백을 지우고 연속 15자 이상 같은 곳을 찾는다. 구조 목록의 extract.mjs 원문 복사 검사와 같은 길이다. 기출 문단 경계를 넘는 조각은 만들지 않는다.
- 같은 조각이 기출 3세트 이상에 나오면 "흔한 표현"으로 따로 표시한다(예: 상투적인 이음말). 판매용 "베끼지 않았다" 보증에는 흔한 표현을 뺀 숫자를 쓴다.
- 겹친 부분은 생성 지문 쪽 문장으로 보고서에 싣는다. 기출 원문은 따로 저장하지 않는다.

## 2. 실행

저장소 루트에서 실행한다. OPENAI_API_KEY와 ~/Projects/suneung_db가 필요하다.

```
node docs/experiments/fidelity-check-2026-11-16/fidelity.mjs <지문.md> [이름]
```

- 목표 구조: 환경 변수 TARGET(예: TARGET=S7-2)이 우선, 없으면 지문 옆 structure.txt, 둘 다 없으면 가장 가까운 구조만 낸다(D 생략).
- 결과: out/<이름>/ 아래 extract.json, labels.json, align.json, compare.json, overlap.json, REPORT.md, _usage.json.
- 다시 돌리기: 같은 이름으로 돌리면 A·B 결과를 다시 쓴다(비용 절약). FORCE=1이면 처음부터, FORCE_COMPARE=1이면 D만 다시.
- 비용 없이 확인: NO_API=1이면 겹침과 분량만, SKIP_COMPARE=1이면 D를 건너뛴다.
- 비용: 지문당 0.1달러 안팎으로 본다(A가 대부분. 기출 추출이 158세트 8달러였다).

## 3. 보정 (첫 실행)

판정이 사람 판단과 맞는지 먼저 본다. 아래 기대는 앞 스레드의 사람 판단이고, 모델에는 주지 않는다.

| 이름 | 지문 | 목표 | 사람 판단 | 맞았다고 볼 결과 |
|---|---|---|---|---|
| r3a | passage-gen-v2-2026-11-13/out-r3a/C-1/final-passage.md | S7-1 사례 재대조 | 대체로 따른다 | 따름 또는 대체로 따름 |
| r3b | passage-gen-v2-2026-11-13/out-r3b/C-1/final-passage.md | S7-2 복수 논거 재검토 | 절반쯤 따른다. 입장을 차례로 쌓는 부분은 따르고, 설계도에 없는 "공통 조건" 문단과 끝의 수치 사례를 덧붙였다. 요건 → 판정 방식(S6)이 섞였다 | 절반. 덧붙음에 공통 조건과 끝의 수치 사례가 짜임을 바꾸는 것으로 잡힌다 |
| r2 | passage-gen-v2-2026-11-13/out-r2/C-1/final-passage.md | 없음 (구조 목록 없이 생성) | — | 가장 가까운 구조가 무엇으로 나오는지 참고로 본다 |

보정 결과를 보는 법:
- r3a와 r3b가 둘 다 맞으면 3.2(구조를 주고 생성하기)에 그대로 쓴다.
- r3b가 "대체로 따름" 이상으로 나오면 비교가 너그럽다. 덧붙음을 놓쳤는지(평면도 문제), 잡았는데 짜임을 바꾸지 않는다고 봤는지(비교 문제) 나눠 본다.
- r3a가 "절반" 이하로 나오면 비교가 엄하다. 어느 요소·축에서 걸렸는지 보고 사람이 맞는지 판단한다.
- 한 번 어긋났다고 비교 지시문에 문구를 더하지 않는다. 원인이 평면도(A·B)인지 비교(D)인지부터 가른다.
- 모델 판정은 흔들릴 수 있다. 판정이 경계에 걸리면 FORCE_COMPARE=1로 한 번 더 돌려 같은지 본다.

## 4. 재지 못하는 것

- 문장의 질, 사실의 정확성, 문항을 낼 여지.
- 수능다움 전체. 이 검사기는 "고른 구조대로 썼는가"만 잰다. 구조 자체가 수능다운지는 구조 목록이 기출에서 나왔다는 데 기댄다.
- 추출·라벨·비교 모두 모델 판단이라 틀릴 수 있다. 처음 몇 편은 사람이 REPORT.md를 확인한다.
- (가)(나) 세트: P 유형 array는 표기가 제각각이라 C(코드 대조)에서 뺐다. D(비교)는 돈다.

## 5. 정한 것 (바꿀 수 있음)

- D는 평면도끼리 비교한다. 생성 지문 원문은 D에 넣지 않는다. 원문을 보면 비교 모델이 내용에 끌려 짜임 판단이 흐려질 수 있고, "설계도를 모르는 검사관의 평면도"라는 원래 생각과도 맞다. 평면도가 틀려서 판정이 틀리는 일이 잦으면 원문을 넣는 쪽으로 바꾼다.
- 비교 지시문의 예시 값은 r3a·r3b와 겹치지 않게 비워 두었다(규칙의 예는 의뢰 주제와 다른 주제로 든다는 원칙).
