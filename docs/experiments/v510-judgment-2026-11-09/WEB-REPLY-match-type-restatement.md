# 웹 답신: 선지 되풀이 근거와 "관대 문항" 기준

- 날짜: 2026-11-09 · 작성: 웹 스레드("정답·오답 판정 구조 논의 이어가기") · 받는 쪽: 코드 에이전트
- 답하는 문서: [`WEB-BRIEF-match-type-restatement.md`](./WEB-BRIEF-match-type-restatement.md)
- 성격: 논의 결과 + 권고. Ghootae가 명시적으로 확정한 것과 웹 권고를 구분해 적었다. 결정 기록(D-NNNN)은 코드 에이전트가 Ghootae 확인 뒤 쓴다.

## 0. 한눈에 보기

1. **Ghootae 의도(확인됨):** 구조상 근거가 원문이나 선지와 비슷할 수밖에 없는 문항에서는, 근거가 선지를 거의 되풀이해도 '충분'으로 본다. 쟁점은 "그런 문항을 무엇으로 가르나"다.
2. **웹 권고 1 (구조): 판정과 표시를 나눈다.** 판정기(sol)에게 조건부 규칙을 주지 않는다. sol은 근거의 **형태**만 출력하고, 최종 충분/부족은 **서버**가 문항 표시를 보고 정한다.
3. **웹 권고 2 (기준): 발문이 아니라 정답 선지의 성질로 가른다.** Ghootae도 "발문만으로 제대로 구분되겠냐"는 의문을 냈다. 세트 E는 choice-link 골드에 이미 정보가 있어 규칙으로 뽑을 수 있다.
4. 의식 15는 골드 기준으로 **관대하지 않은 쪽**(코드 에이전트 추천과 같은 결론, 이유는 다름).

## 1. 구조: 판정기는 형태만, 서버가 최종 판정 (웹 권고)

- v5.10 SELECTION 출력에 칸 하나를 더한다. 예: `evidenceForm: SOURCE_ANCHORED | CHOICE_RESTATED | NON_DISCRIMINATING`(원문 사실을 짚음 / 선지를 되풀이함 / 맞지만 정답을 가르지 못하는 사실). 이름과 값은 코드 에이전트가 정한다.
- 판정기 입력에는 관대 문항 표시를 **넣지 않는다**. 지시문에 "일치형이면 되풀이도 충분" 같은 조건부 규칙도 넣지 않는다.
- 서버 규칙:
  - 관대 문항 + `CHOICE_RESTATED` → 충분(화면: 근거까지 정확한 정답)
  - 관대 아님 + `CHOICE_RESTATED` → 부족(화면: 근거 약한 정답)
  - 내용 오류(CONTRADICTED 등)는 형태와 상관없이 기존대로 오류
- 이렇게 하는 이유:
  1. 브리프 6절의 위험("sol이 조건부 규칙을 안 지키거나, 비일치형까지 너그러워짐")이 생기지 않는다. 원칙 "프롬프트 규칙보다 출력 필드 + 서버 검증"과 맞다.
  2. 관대 문항에서는 "원문 사실"과 "되풀이"가 겉으로 구별되지 않는다(브리프 2절). 하지만 이 구조에서는 관대 문항이면 둘 다 충분이라, sol이 헷갈려도 결과가 같다. 헷갈리는 곳과 결과가 갈리는 곳이 겹치지 않는다.
  3. 기록에 형태가 남는다. 나중에 관대 문항 목록을 바꿔도 판정을 다시 돌리지 않고 서버 표시만 바꾸면 된다.
- 대가: 출력 칸이 늘어 형식 검사와 회귀 확인이 조금 늘어난다. 조건부 규칙을 지시문에 넣고 sol이 지키는지 시험하는 것보다는 가볍다고 본다.
- K 시험에서 볼 것: "결론만" 근거가 `CHOICE_RESTATED`로, "핵심" 근거가 `SOURCE_ANCHORED`로 기록되는지(관대 아닌 문항에서 특히). 관대 문항에서의 형태 오분류는 결과에 영향이 없으니 관찰만 한다.

## 2. 관대 문항 기준: 정답 선지의 성질 (웹 권고)

- Ghootae 원리를 그대로 옮기면, 기준은 발문이 아니라 **정답 선지**의 성질이다. 규칙은 학생이 정답을 골랐을 때만 쓰이므로 정답 선지 하나만 보면 된다.
  > 정답 선지가 원문의 한 곳과 거의 같은 말이라서, 추론 없이 그 한 곳으로 확인되는가?
- 발문 기준의 한계 예:
  - "윗글을 이해한 내용으로" 같은 일치형 발문이어도, 정답 선지가 여러 문장을 이어야 나오면 근거가 선지와 같을 필요가 없다.
  - 반대로 추론형 발문인데 정답 선지가 원문을 그대로 옮긴 경우도 있을 수 있다.
- **세트 E는 choice-link 골드에서 바로 뽑힌다.** `docs/experiments/sns-diagnostic-gold-2026-11-05/choice-link/frozen-3runs/<passage>.json`의 `questions[].choices[].parts[].operation`과 `inferenceBasisIds`.
- 제안 규칙: **정답 선지의 모든 part가 `RESTATE`이거나 `INFER`(근거 문장 1개)이면 관대 문항.**
- "적절한 것" 발문 정답 선지에 적용한 결과(웹 스레드가 작업 브랜치에서 직접 뽑음):

| 문항 | 정답 | parts (operation, 근거 문장 수) | 관대 |
|---|---|---|---|
| 오디오 15 | ③ | RESTATE | 예 |
| 경마 4 | ⑤ | INFER 1 | 예 |
| 오디오 16 | ⑤ | INFER 2 | 아니오 (어차피 관찰만) |
| 의식 15 | ② | INFER 3 | 아니오 |
| 경마 6 | ② | INFER 3 | 아니오 |
| 의식 12 | ① | INFER 3 + RESTATE | 아니오 |
| 의식 14 | ① | RESTATE + INFER 3 | 아니오 |
| 오디오 17 | ⑤ | APPLY | 아니오 |
| 플라 10 | ③ | APPLY | 아니오 |

- 결과는 브리프 4절의 발문 기준 표와 경마 4·오디오 15에서 같고, 오디오 16에서만 다르다(발문 기준은 일치형, 골드 기준은 아님).
- 절차:
  1. 규칙으로 후보를 뽑는다.
  2. Ghootae가 22문항(진단 16 + lab 6)을 훑어 확정한다.
  3. 확정 표시를 문항 자료(진단 runtime 자료 등)에 저장한다. 서버가 그것을 읽는다.
- 새 세트: 골드를 만들 때 choice-link가 같이 나오므로 별도 호출 없이 같은 규칙 + 사람 확인으로 표시한다(Ghootae 질문 "골드 만들 때 같이 해도 되나"에 대한 답). choice-link 골드가 없는 문항(lab 6문항 등)은 있는지 먼저 확인한다. 없으면 준비 단계에서 sol에게 문항당 1회 "정답 선지가 원문 한 곳으로 추론 없이 확인되나, 그곳은 어디인가"를 묻고 사람이 확정한다.

## 3. 브리프 7절 질문별 답

1. **목적과 맞나:** 관대 문항에서 시험하는 것은 "원문에서 찾아 확인하기"다. 되풀이만으로는 확인했다는 증거가 없지만 틀린 것도 아니다. 그래서 이것은 판정 문제가 아니라 "억울하지 않게 보여 주기" 문제로 본다. 기록은 구분하고(1절), 화면은 너그럽게 한다.
   - 사고 진단 대상(`maybeStartDiagnosis`)은 화면 표시가 아니라 판정 기록 기준으로 정하는 편이 일관적이다. 다만 되풀이 근거의 사고 진단은 얻는 것이 적다. 어느 쪽으로 할지는 코드 에이전트가 정한다.
2. **발문 기준 사람 표시:** 사람 표시에는 동의한다. 기준은 발문 대신 2절의 정답 선지 성질을 권한다. 발문은 처음 거르는 참고로만 쓴다.
3. **의식 15:** 골드상 3문장 추론(INFER 3)이라 관대 아님. 결론은 코드 에이전트 추천(가)과 같고, 이유는 "이유 발문이라서"가 아니라 "정답 선지가 여러 문장을 이어야 나와서"다. 사람 확인 때 한 번 더 본다. 웹 스레드는 처음에 브리프 설명만 보고 이 문항을 관대 쪽으로 말했다가, 골드를 보고 정정했다.
4. **붙여 넣기 구별:** 서버가 선지 문장과의 글자 겹침으로 **표시만 기록**하고, 지금은 화면에 반영하지 않는 것을 권한다. 베끼기 유인이 작기 때문이다. 근거 쓰기가 귀찮은 학생은 "확실해요" 버튼을 누르면 되니(D-0213), 굳이 붙여 넣을 이유가 적다. 실제 비율은 SNS 자료로 보고 정한다.
5. **별도 범주:** 1절 구조가 이 안을 일반화한 것이다. 기록에는 형태가 남고, 화면은 서버가 문항 표시로 정한다.

## 4. Ghootae 확인이 필요한 것

- 1절 구조(판정기는 형태만, 서버가 최종 판정)를 채택할지
- 2절 기준(골드 operation 규칙)과 그 결과(경마 4·오디오 15만 관대)
- 붙여 넣기는 기록만 할지
