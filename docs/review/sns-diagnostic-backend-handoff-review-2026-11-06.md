# 검토: SNS 진단평가 백엔드 인계(인계 A) 초안

- 대상: `docs/handoffs/2026-11-06-sns-diagnostic-backend.md`, `memory/decisions/D-0208-sns-diagnostic-skip-item-review-rationale-prompt.md`
- 검토: 웹 에이전트, 2026-11-06. 코드는 직접 보지 않았고 문서끼리, 그리고 앞선 결정(D-0204 첫 응답 원칙 등)과 대조했다.
- 결론: 구조와 범위는 좋다. executor에 넘기기 전에 **1~3은 문서에 정해 주는 게 좋고**, 4~6은 짧게 적어 두면 된다.

## 넘기기 전에 정할 것

### 1. 지문 안에서 답을 바꿀 수 있는가

(6)-3에서 문항 답을 내자마자 `createFeedbackSession` → `SELECT` → 백그라운드 판정을 시작한다. 그런데 `answers-done` 전에 같은 문항을 다시 내면 어떻게 되는지가 없다. 실제 시험처럼 3번을 읽다가 1번 답을 고치는 일은 흔하다.

- 지금 문서대로 두면 executor가 `first`를 덮어쓸지, 거부할지, 판정을 두 번 돌릴지 임의로 정하게 된다.
- 선택지:
  - (가) 한 번 내면 잠금. 구현이 가장 단순하다. 화면에서 "제출하면 바꿀 수 없어"를 알려야 한다.
  - (나) `answers-done` 전까지 고칠 수 있고, 판정은 `answers-done` 때 한꺼번에 시작. 시험 경험에 가장 가깝다. 판정 대기 시간이 지문 끝으로 몰린다.
  - (다) 고칠 수 있고, 고치면 진행 중 판정을 버리고 다시 시작. 비용이 새고 경합이 생긴다.
- 의견: (나). "첫 응답"을 "지문을 다 풀었다고 낸 시점의 답"으로 정의하면 원칙과도 맞다. 판정은 문항당 수십 초라 지문 결과 정리 대기가 조금 늘어나는 정도다. (가)도 괜찮지만 화면 안내가 필요하다.

### 2. 참가자 파일 동시 쓰기

(7)은 참가자 상태를 파일 하나에 통째로 쓴다. 그런데 한 참가자에게 판정 4개, 사고 진단, 문단 판정(노드·관계마다 1회)이 동시에 백그라운드로 끝난다. 각 작업이 "읽기 → await → 고쳐 쓰기"를 하면 나중에 쓴 쪽이 앞의 결과를 지운다(rename은 파일 깨짐만 막고 덮어쓰기는 못 막는다).

- 문서에 한 줄 필요: 참가자마다 메모리 상태 하나를 기준으로 두고, 저장은 참가자 단위로 차례대로(직렬 큐) 한다. 백그라운드 작업은 끝난 뒤 그 메모리 상태에 결과를 반영하고 저장을 요청한다.
- 완료 조건에 "판정 여러 개가 거의 동시에 끝나도 결과가 모두 남는다" 테스트를 더한다.

### 3. 문항 검토 문항의 정답이 결과 화면에서 드러남

D-0208 2는 문항 검토 문항에서 "정답은 공개하지 않는다"고 했다. 그런데 `GET …/result`의 `items[]`는 모든 문항에 `answerPosition`, `correct`, `evidence.source`를 넣는다.

- 선택지: 결과에서도 그 문항은 `answerPosition`·`evidence`를 빼고 `reviewFlag: 'BOUNDARY'`만 둔다 / 결과 화면에서는 공개해도 된다고 D-0208에 명시한다.
- 의견: 앞쪽. 정답 충돌이 의심되는 문항에서 "공식 정답은 ②"를 단정해 보이는 건 피하는 게 맞다. `correct`(첫 선택 기준 정답 수)는 D-0208대로 남긴다.

## 짧게 적어 두면 되는 것

### 4. `RESUME`으로 판정이 나중에 성공하면

판정이 `FAILED` → 피드백 차례에 `RESUME`으로 성공하면, 그 결과는 첫 응답에 대한 판정이므로 분석에 써도 된다. 그런데 문서에는 `firstJudgment`를 갱신하는지가 없다. "첫 선택 판정이 RESUME으로 성공하면 `firstJudgment`를 READY로 바꾸고 `checking`에서 뺀다(지문 결과 정리를 이미 보였어도 최종 결과에는 반영)"를 적어 두면 된다. 사고 진단 대상 판단도 그때 다시 한다.

### 5. 풀이 시간의 정의

"문항이 보인 때부터 선택 확정까지"는 지문 단위 화면에서 모호하다.

- 4문항이 한 화면에 함께 보이면 모든 문항의 시작 시각이 같아져, 지문 읽는 시간이 다 섞인다.
- 근거를 쓰고 나서 선택을 확정하는 화면이면 근거 입력 시간이 풀이 시간에 들어간다. 사용자 결정은 "풀이 시간에서 입력 시간을 뺀다"였다.
- 제안: 백엔드는 화면이 보낸 값을 그대로 저장만 하고, 정의는 인계 B(화면)에서 정한다고 적는다. 그리고 `solveMs`에 근거 입력 시간이 들어가지 않는다는 것만 이 문서에 계약으로 남긴다. 결과 화면에 시간을 쓰지 않으니(시간×정오 삭제) 급하지 않다.

### 6. 비용 측정 때 볼 곳: 문단 판정 호출 수

문단 판정은 노드·관계마다 1회라, 4지문을 모두 요약하면 참가자 한 명에 **259회**다. 문제 판정(16회)과 사고 진단(많아야 16회)보다 훨씬 많다. 이 인계는 외부 전송이 없어 문제가 아니지만, 별도 비용·대기 시간 측정 과제에서 가장 먼저 볼 곳으로 적어 두면 좋다. 재시작 때 `PENDING` 요청을 다시 보내는 규칙도 이 호출 수에서는 중복 비용이 커질 수 있다.

## "질문 없이 정한 것" 다섯 가지

모두 동의한다.

- 자동 재시도 2회(최대 3회): 적절하다. 실패가 몰리면 비용이 3배가 되는 점만 측정 때 본다.
- 정답 문항의 사고 진단은 첫 선택 판정을 기다림, 최종 실패면 돌림: 적절하다.
- 시간 두 칸: 방향은 동의. 정의는 5번 참고.
- 지문 결과·결과 API는 숫자와 코드만: 동의한다. 문장 책임을 인계 B로 모으는 게 맞다.
- 요약의 새 시도 막기: 첫 차례 원칙을 지키는 데 필요하다. 동의한다.

## 그 밖에 좋았던 점

- 판정기·지시문을 바꾸지 않고 `SKIPPED` 정의 한 문장만 더한 것, 동치 테스트로 옮긴 지시문을 고정한 것.
- 골드·선지 연결을 결과 자료에만 쓰고 판정 입력에 넣지 않는다는 제약을 공통 규칙에 다시 적은 것.
- `participantId` 경로 조작 검사, `CSAT_DIAGNOSTIC_ENABLED`로 본 서비스와 분리한 것.
