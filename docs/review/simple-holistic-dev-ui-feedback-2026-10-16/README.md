# 단순 형식 문단 개발자 모드 사용감 피드백 (2026-10-16)

- 대상: `/dialogue/dev/simple` ([D-0140](../../../memory/decisions/D-0140-paragraph-simple-holistic-dev-mode.md), [인계](../../handoffs/2026-10-16-paragraph-simple-holistic-dev-mode.md))
- 상태: 1~6 구현 완료(2026-10-16, [D-0142](../../../memory/decisions/D-0142-paragraph-simple-v2-restated-summary-attempts.md), [인계](../../handoffs/2026-10-16-paragraph-simple-holistic-v2-feedback.md)). 재구성 응답 = 학생 누적 발화만 합친 요약, 판정마다 갱신, "지금까지 내 요약" 칸.
- 출처: 사용자 메모(2026-10-16, 대화로 전달)

## 수정 사항

1. **한 문단 반복 시도와 시도별 메모** (설계 확인 완료)
   - 문단마다 [새 시도] 버튼. 누르면 그 문단을 처음 상태로 되돌려 첫 응답부터 다시 쓴다. 대화 중간에도 누를 수 있고, 그 시도는 "중단"으로 기록한다.
   - 이전 시도는 지우지 않는다. 서랍에서 시도 1, 2…를 골라 대화와 단계별 판정을 다시 본다. 로그의 모든 단계에 시도 번호를 붙인다.
   - 메모칸은 세 종류다.

     | 메모칸 | 단위 | 용도 |
     |---|---|---|
     | 단계 인상 | 시도 안의 단계마다 | 지금과 같음 |
     | 시도 인상 | 시도마다 하나 | 새로 추가 |
     | 문단 전체 인상 | 문단마다 하나(시도 번호 없음) | 전체 인터랙션에 대한 인상 |

2. **학생이 자기 '재구성된 응답'을 볼 수 있게**
   - Claude 이해(미확인): 보여 주기 모드 피드백·[D-0137](../../../memory/decisions/D-0137-boundary-show-effective-response-restatement.md)의 "재구성된 응답"과 같은 뜻으로, 학생의 누적 발화(첫 요약과 질문에 답한 내용)를 합쳐 다시 쓴 요약이다. 단순 형식 출력에는 이 필드가 없으므로 모델 출력에 추가해야 한다(V4의 `effectiveResponse`에 해당).
   - 구현 전에 정할 것: 언제 보여 주는가(칭찬·마무리 때만인지, 매 단계인지), 어디에 보여 주는가(튜터 메시지 안인지, 별도 "내 요약" 칸인지).

3. **오류 설명과 핵심 내용은 별도 대화풍선으로**
   - 오류를 바로잡는 문장과 문단 핵심 내용을 제시하는 문장을 각각 다른 말풍선으로 보인다.
   - Claude 메모: 지금은 CLOSE_ERRORS의 `message` 하나에 둘이 함께 들어간다. 출력에는 이미 `coreSummary`가 따로 있으므로, 프롬프트에서 `message`에는 오류 바로잡기만 쓰게 바꾸고 화면은 `coreSummary`를 두 번째 말풍선으로 보이면 된다(프롬프트 v2 필요).

4. **재구성된 응답은 별도 칸에서** (2번의 "어디에" 확정)
   - 재구성된 응답은 대화창이 아닌 별도 칸에 보인다. 대화창에는 실제로 오간 대화만 둔다.
   - 남은 것: 언제 갱신해 보이는가(매 단계인지, 마무리 때만인지).

5. **말풍선 상단의 작은 상태 표시** (사용자 원문에서는 이 항목도 4번)
   - 문제 풀이 화면처럼 말풍선 위에 작게 단계 이름을 보인다. 명칭은 Claude 제안을 사용자가 수정해 확정(2026-10-16: "함께 확인하기"→"확인하기", "함께 생각해 보기"→"생각해 보기"):

     | 말풍선 | 표시 |
     |---|---|
     | 학생 첫 요약 | 나의 요약 |
     | 학생 다시 쓴 요약 | 다시 쓴 요약 |
     | 학생이 질문에 한 답 | 나의 답 |
     | PRAISE | 피드백 |
     | RETRY_PROMPT | 다시 써 보기 |
     | CORRECTION_QUESTION | 확인하기 |
     | GAP_QUESTION | 생각해 보기 |
     | CLOSE_GAP | 빠진 내용 |
     | CLOSE_ERRORS 첫 말풍선(3번) | 바로잡기 |
     | CLOSE_ERRORS 둘째 말풍선·CLOSE_NO_RESPONSE | 문단 핵심 |

6. **(검토) 지문 안 표시가 너무 작음**
   - 지금까지 로그(`.omc/logs/dialogue-experiment/simple-holistic/sessions.jsonl`)의 표시 구절 6개: 24~83자. 문장 일부만 칠한 경우가 있다(공손룡 p5 "달명은 천지 만물을 총괄하여 지시하는 것으로" 24자, "유명은 … 지시하는 이름" 42자).
   - Claude 추정 원인: 프롬프트가 `sourceQuote`를 "짧게, 한 문장 이내로" 지시한다. 색은 문제 풀이 화면과 같은 `#fff3d6`.
   - 검토안(Claude 권고): 서버가 인용 위치를 찾은 뒤 표시 범위를 그 인용이 걸친 문장 전체로 넓힌다(마침표 기준). 모델 인용은 검증용으로 그대로 두고 표시만 넓히므로 프롬프트 변경 없이 일관된다. 다른 안: 프롬프트에서 "해당 내용이 담긴 문장 전체를 인용"으로 바꾸기.
   - **확정(사용자, 2026-10-16):** 프롬프트에서 `sourceQuote`를 "해당 내용이 담긴 문장 전체를 인용"으로 바꾼다(프롬프트 v2, 3번과 함께). 서버의 문장 단위 확장은 쓰지 않는다. 모델이 지키지 않는 경우는 사용하며 관찰한다.

## v2 사용 메모 (2026-10-16)

- 상태: 1~5 구현 완료(2026-10-17, 프롬프트 v3, [D-0144](../../../memory/decisions/D-0144-paragraph-simple-v3-closing-bubbles-highlights.md), [인계](../../handoffs/2026-10-17-paragraph-simple-holistic-v3.md)). 6은 루나로 관찰 중(프롬프트 v2.1 보류).

1. **바로잡기 뒤 문단 핵심 말풍선이 부자연스러움** ([화면](./images/v2-memo-1-close-errors.png), 공손룡 문단 1)
   - 지금: "바로잡기" 말풍선(“명실 문제의 변화 방향은 반대야. …”) 다음에 "문단 핵심" 말풍선이 앞말 없이 `coreSummary`만 보인다.
   - 사용자 수정 예시:
     > 내가 판단한 이 문단의 핵심 내용은 이거야.
     >
     > [명실 문제는 전국 시대 중엽 이후 독립적인 철학 주제로 자리 잡았다. 이를 전문적으로 다룬 공손룡과 후기 묵가 사이에서는 철학적 논쟁이 펼쳐졌다.]
   - 확정(사용자, 2026-10-16):
     - 바로잡기 말풍선은 그대로 둔다. 문단 핵심 말풍선 앞에 도입 문장을 붙인다.
     - 도입 문장은 모델이 쓴다(표현에 변화가 있도록). 예시 문장은 그 예다.
     - 예시의 대괄호는 자리 표시다. 핵심 내용은 기호 없이 옅은 배경 상자로 보인다.
   - 확정(Claude 권고를 사용자가 수락, 2026-10-16):
     - 도입 문장은 `coreSummary`에 섞지 않고 별도 필드 `coreIntro`(한 문장, 문단 내용 미포함)로 받는다. 서버는 비어 있지 않음·길이를 검사한다. 화면은 한 말풍선 안에 도입 문장, 그 아래 옅은 배경 상자 속 `coreSummary`.
     - CLOSE_NO_RESPONSE의 문단 핵심 말풍선도 같은 형식(도입 문장 + 상자). 지금 `message`와 `coreSummary`가 같은 내용으로 중복되는 것을 없애고, `message`가 도입 문장 역할을 하도록 정리한다(필드 배치 세부는 프롬프트 v3 작성 때 정한다).
   - 구현: 나중에(사용자 "일단 기록"). 프롬프트 v3 필요.

2. **지문 표시 범위가 너무 넓음** ([화면](./images/v2-memo-2-highlight-too-wide.png), 공손룡 문단 2, CLOSE_GAP)
   - 지금: v2 지시("근거가 두 문장 이상에 걸치면 이어진 문장들을 함께 인용")대로 세 문장이 한꺼번에 칠해졌다. v1(문장 일부, 너무 작음)의 반대 문제.
   - 사용자 제안(2026-10-16): 걸치는 문장이 여러 개면 가장 관련 깊은 문장 하나에만 표시.
   - 확정(사용자, 2026-10-16 "좋아, 기록해둬"). Claude 의견: 동의. 표시는 "여기를 다시 보라"는 손가락이고, 빠진 내용 설명은 말풍선이 이미 한다. 프롬프트 `sourceQuote` 지시를 "그 내용을 가장 직접 담은 문장 하나 전체"로 바꾼다(문장 일부 금지는 유지). 오류가 여럿인 CLOSE_ERRORS는 오류마다 한 문장이라 표시가 여럿일 수 있다.
   - 구현: 나중에(프롬프트 v3, 메모 1과 함께).

3. **빠진 내용(CLOSE_GAP) 코멘트가 불분명함** (공손룡 문단 2, 메모 2와 같은 대화)
   - 대화: 나의 요약 "공손룡은 명가 사상가" → 생각해 보기 "공손룡이 무엇과 무엇의 관계를 설명하며, 왜 그것이 중요하다고 보았는지 말해 볼래?" → 나의 답 "명과 실의 관계. 소통의 혼란을 줄이기 위해서." → 빠진 내용 "명과 실의 관계가 소통과 관련된다는 점은 잘 짚었어. 공손룡은 하나의 명이 하나의 실만, 하나의 실이 하나의 명으로만 가리켜져야 한다고 보았어. 그래야 서로 다른 대상을 같은 이름으로 불러 생기는 혼란을 막을 수 있다고 생각했지."
   - 사용자 평: 내용은 정확한데 코멘트가 불분명하다.
   - 사용자 수정 예시: "명과 실의 관계가 소통과 관련된다는 점은 잘 짚었어. 하지만 이 문단에서 가장 중요한 정보는 그 관계가 '일대일'이라는 점이야. 이 부분에 대한 캐치가 충분하지 않았어." (원문 '일대잉'은 오타로 보고 '일대일'로 적음)
   - 2차 출력 분석: `message` 세 문장 중 ① 인정("소통과 관련된다는 점은 잘 짚었어"), ② 일대일(학생 답에 없음), ③ 혼란 방지(학생 답 "소통의 혼란을 줄이기 위해서"에 이미 있음). 불분명한 원인은 ②가 빠진 것이라는 말이 없고, 이미 말한 ③이 나란히 붙어 무엇이 빠졌는지 흐려진 것.
   - 확정(사용자 동의, 2026-10-16):
     - 기준: 학생 답에 없는 것만 말하고, 그것이 빠졌다고 분명히 말한다. 학생이 이미 말한 내용은 인정 말고는 다시 들려주지 않는다.
     - CLOSE_GAP `message` 구성: 잡은 것 인정 → 학생 답에 없는 핵심 하나를 짧게, 모델의 판단임을 드러내며 짚기(예: "내가 보기엔 이 문단에서 가장 중요한 건 ~라는 점이야") → 그 부분이 빠졌다고 말하기.
     - 골드가 없으므로 질문 때 고른 구멍(`targetGap`)을 AFTER_GAP 판정 입력에 넘기고, CLOSE_GAP은 그 구멍을 짚는다(답을 보고 좁히는 것은 허용, 다른 곳으로 옮기는 것은 금지). 지금은 `targetError`만 넘기고 `targetGap`은 넘기지 않는다(`packages/app/src/server/dialogue-simple.ts` evaluate). 실제로 1차 gap "관계와 이유"가 2차에서 "일대일 대응"으로 다시 골라졌다.
   - 구현: 나중에(프롬프트 v3, 서버 입력 필드 추가).

4. **지문 표시 규칙이 사용자에게 느껴지지 않아 노이지함**
   - 지금: 문단이 끝날 때 CLOSE_GAP(구멍 근거)·CLOSE_ERRORS(오류마다 근거)만 표시. PRAISE·CLOSE_NO_RESPONSE는 표시 없음. 질문 중에는 표시 없음(D-0140).
   - 사용자 원래 생각: 빠진 내용, 교정 질문(확인하기 질문 중), 응답 없음에서 모두 표시.
   - Claude 의견: 확인하기 질문 중 표시는 답 누출(칠해진 곳을 옮겨 적으면 됨)이고, 생각해 보기와 규칙이 갈려 다시 복잡해진다. 대신 "문단이 칭찬이 아닌 방식으로 끝나면 항상 근거 문장을 칠한다"를 권고.
   - 확정(사용자, 2026-10-16 "가로 일단 정해서 해보자"): 권고안으로 시도. 달라지는 곳은 CLOSE_NO_RESPONSE에도 표시하는 것 — 이를 위해 문단 핵심의 근거 문장 필드(가칭 `coreSourceQuote`, 메모 2 기준대로 가장 직접 담은 문장 하나 전체)를 추가한다. 질문 중 표시(사용자 원안)는 사용해 본 뒤 다시 검토할 수 있는 대안으로 남긴다.
   - 노이즈의 일부는 메모 2(세 문장 표시)일 수 있어 함께 관찰한다.

5. **오류가 여럿일 때 바로잡기를 하나씩** (공손룡 문단 2, MULTI_ERROR → CLOSE_ERRORS)
   - 지금: 바로잡기 말풍선 하나에 오류 세 개의 정정을 이어 쓰고, 다음에 문단 핵심 말풍선.
     - 나의 요약: "실로부터 물이 파생. 명은 물을 지시해서 소통을 가능하게 함. 공손룡은 명과 물 사이의 관계가 불분명할 수 밖에 없다고 주장함."
     - 바로잡기: "물에서 실이 파생되는 것이지, 실에서 물이 파생되는 것은 아니야. 명은 물이 아니라 각각의 실을 가리켜. 공손룡은 관계가 불분명할 수밖에 있다고 본 것이 아니라, 혼란을 막기 위해 명과 실이 하나씩 대응해야 한다고 봤어."
   - 사용자 수정 예시(순서대로):
     1. 응답에 지문 내용과 다른 점들이 있어서 하나씩 검토해볼게.
     2. "실로부터 물이 파생." 실제로는 반대야 …
     3. "명은 물을 지시해서 소통을 가능하게 함." 명은 물을 지시하는 게 아니라 실을 지시하는 거야 …
     4. "공손룡은 명과 물 사이의 관계가 불분명할 수 밖에 없다고 주장함." 공손룡은 …
     5. 내가 보는 이 문단의 핵심 내용은 이래. [문단 핵심]
   - 예시 문장은 형식을 보이는 예시일 뿐 문구를 그대로 쓰라는 뜻이 아니다(사용자, 2026-10-16). 문구는 모델이 상황에 맞게 쓴다(오류가 하나뿐인 교정 실패에서도 자연스럽게).
   - 확정(사용자, 2026-10-16 "따로 분리해줘"): 말풍선을 나눈다.
     1. 도입 한 문장(모델 작성, 상황에 맞게) — 표시 "바로잡기"

6. **이미 말한 관계를 구멍으로 판정해 불필요한 질문** (공손룡 문단 2, 시도 4) — 중요
   - 대화: 나의 요약 "명과 실이 일대일이 아니면 혼란이 생길 수도 있음." → 생각해 보기 "혼란이 생길 수 있다는 점은 잘 짚었어. 공손룡이 그 혼란을 막기 위해 무엇을 주장했는지도 연결해 볼래?" → 나의 답 "명과 실이 일대일로 대응되어야 한다." → 피드백 "… 이를 막기 위한 공손룡의 주장을 잘 연결했어"
   - 로그 1차 판정: GAP, reason "공손룡이 이를 막기 위해 어떤 입장을 주장했는지는 분명히 드러나지 않는다", gap "혼란을 막기 위해 공손룡이 주장한 바가 빠져 있다".
   - 진단: 첫 요약의 조건문("일대일이 아니면 혼란")에 "일대일이어야 한다"는 주장이 이미 담겨 있다. 관계 누락이 아니라 같은 관계를 다른 형태로 말한 것을 구멍으로 봤다. 학생은 자기 말을 뒤집어 다시 했고, 칭찬은 질문으로 새로 연결한 것처럼 말해 어색하다. 일반 유형: 같은 관계를 조건문·대우·이유-결과 등 다른 형태로 말하면 GAP 판정.
   - 확정(사용자, 2026-10-16 "기록. 이 건은 중요한 문제니까 수정해서 api로 1회 테스트해보자"): 판정 기준 보강(학생 말에서 곧바로 따라 나오는 관계는 이미 말한 것) + 질문 전 점검("제대로 답하면 지금 말에 없던 새 관계가 생기는가? 아니면 CAPTURED"). 프롬프트 v2.1로 바로 수정해 API 1회 시험.

   - 결정(사용자 승인): 개발자 모드 판정 모델을 `PARAGRAPH_SIMPLE_OPENAI_MODEL=gpt-6-luna`로 바꿔 계속 사용(코드 기본값은 테라 그대로). 프롬프트 v2.1 수정은 루나에서 같은 실패가 보일 때 적용(지금 고치면 모델 효과와 구분 불가). `paragraph-simple-holistic-prompt-v2.1.md`는 v2 복사본(제목만 변경) 상태. 반대 위험: 이 요약은 문단 앞부분(물→실, 명의 지시)이 빠져 있어 CAPTURED가 관대할 수 있음 — 사용 중 관찰.
