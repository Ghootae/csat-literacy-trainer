# 문단 이해 대화 시스템: 작업 경과와 합의된 기준선

상태: 문단 요약·분석 구조 일단락

기준일: 2026-08-26

현재 런타임: `axis-dialogue-v2`

## 1. 문서 목적

이 문서는 문단의 중심 내용을 분석하고, 학생의 자유 응답을 판정하고, 필요한 후속 질문을 만드는 구조가 어떤 문제를 거쳐 현재 형태에 도달했는지 설명한다. 이후 변경에서는 이 문서를 현재 기준선으로 삼는다.

현재 구조의 핵심은 다음 세 층을 분리하는 것이다.

1. `centralStory`: 문단에서 무엇이 중심인지 결정한다.
2. `centralAxes`: 중심 이야기를 이루는 독립적인 거시 의미 구조를 통과 단위로 삼는다.
3. `coreRelations`: 학생의 세부 표상과 명시적 오류 위치를 원자적으로 기록한다.

축은 관계 체크리스트가 아니며, 관계는 질문 순서표가 아니다. 최종 PASS는 모든 관계의 개별 충족이 아니라 모든 중심축의 포착 여부로 결정한다.

## 2. 작업 흐름과 주요 결정

### 2.1 관계 중심 판정기와 출력 계약 정리

초기 판정기는 문단의 핵심 관계마다 `explicit`, `entailed`, `contradicted`, `unknown` 상태를 부여했다. 이 과정에서 다음 출력 계약을 정리했다.

- PASS에는 `targetIssue`와 질문이 없다.
- ERROR는 명시적으로 충돌한 관계를 교정 대상으로 삼는다.
- UNCLEAR는 아직 확인되지 않은 내용을 진단 대상으로 삼는다.
- `explicitErrors`는 모델이 별도로 작성하지 않고 `contradicted` 관계에서 코드가 파생한다.
- DIAGNOSTIC 질문과 CORRECTIVE 질문 모두 정답의 관계·방향을 먼저 알려 주지 않는다.

헤겔 문단의 5건 회귀 테스트와 성격이 다른 문단의 교차 검증을 거쳐 관계 상태, `targetIssue`, 질문 유형의 기본 계약을 안정화했다. 다만 이 단계의 일치는 특정 테스트셋에 대한 회귀 통과이지 일반적 정확도 검증으로 간주하지 않았다.

### 2.2 골드 v2와 `required/error_only`

나열식 문단에서 모든 관계를 질문하는 문제를 줄이기 위해 골드 분석 v2에서 관계 역할을 나눴다.

- `required`: 확인되지 않으면 질문 후보가 되는 관계
- `error_only`: 미언급만으로 질문하지 않지만 반대로 말하면 오류로 추적하는 관계

8개 문단의 수준별 응답과 누적 실험을 통해 누락과 명시적 오류를 분리하는 데에는 효과가 있었다. 53건에서 판정·대상·질문 계약이 일관되게 작동했고, v2는 사람 검토형 골드 후보의 기준선으로 사용할 수 있다고 판단했다.

그러나 후속 실험에서 `required`가 문단 중심성, 관계의 중요성, 질문 필요성을 다시 결합하는 문제가 드러났다. 중심 이야기에 포함된 관계가 곧 `core`, 다시 곧 `required`로 해석되면서 질문 수가 늘어났다.

따라서 현재 축 기반 경로에서는 `required/error_only`를 생성하거나 사용하지 않는다. 기존 필드는 회귀 자료로만 보존한다.

### 2.3 중심 이야기와 관계 체크리스트의 분리

법인 첫 문단에서 학생이 문단의 중심 구조를 충분히 표현했는데도 재단·사단, 영리·비영리 같은 세부 구분을 계속 질문하는 사례가 발생했다. 원인은 두 가지였다.

1. `centralStory`가 상세 내용을 병렬적으로 담은 압축 요약에 가까웠다.
2. 한 호출에서 PASS와 모든 관계 상태를 함께 판정하여 관계가 자연스럽게 통과 체크리스트가 됐다.

이를 해결하기 위해 판정을 다음 두 단계로 분리했다.

1. 중심 이야기 게이트: 중심 의미의 충분성만 판정한다.
2. 관계 진단: 게이트 결과를 바탕으로 세부 표상과 오류 위치를 기록하고 질문을 만든다.

게이트에는 `coreRelations`를 제공하지 않는다. 이로써 세부 관계의 unknown 상태가 PASS를 자동으로 막지 못하게 했다.

### 2.4 단일 중심 이야기 게이트에서 중심축 게이트로

법인 세 번째 문단에서는 전체 `centralStory`를 하나의 덩어리로 판정한 결과, 학생이 두 독립 방향 중 하나만 설명했는데도 PASS가 되는 문제가 나타났다.

이 사례에서 다음 중간 단위가 필요하다는 결론에 도달했다.

- 전체 중심 이야기: 너무 뭉뚱그리면 부분 이해를 PASS할 수 있다.
- 원자 관계: 너무 잘게 쓰면 다시 체크리스트가 된다.
- 중심축: 빠지면 중심 이야기가 훼손되는 독립적인 거시 의미 구조다.

이에 `centralAxes`를 도입했다. PASS를 위해서는 모든 독립 중심축이 포착돼야 하지만, 각 축 안의 모든 세부 관계를 학생이 열거할 필요는 없다.

질문 단위도 함께 바뀌었다.

- 폐기: 한 관계 = 한 질문
- 채택: 한 질문 = 하나의 중심축

관계는 축 안에서 학생이 무엇을 맞게 또는 틀리게 표현했는지 기록하는 하위 자료로 남는다.

### 2.5 누적 응답의 담화 합성

정보 비대칭 문단의 실제 대화에서 학생이 최초 응답과 후속 답변에 의미를 나눠 표현했는데, 판정기가 각 답변을 독립적으로 읽어 같은 내용을 반복 질문하는 문제가 나타났다.

이에 최초 응답과 모든 질문–응답을 `effectiveResponse` 하나로 합성하도록 수정했다.

- 질문은 학생 지식의 증거가 아니다.
- 질문은 짧은 답변의 지시 대상, 생략된 주어·서술어, 답변이 채운 의미 슬롯을 해석하는 담화 문맥이다.
- 학생이 실제로 쓴 표현만 증거로 기록한다.
- 여러 턴에 나뉜 학생 표현이 안정적으로 연결되면 하나의 인과·대조·귀속 관계로 합성한다.
- 새 답변이 이전 주장을 명확히 수정하면 수정된 의미를 사용한다.

중심축 게이트와 관계 진단기는 같은 `effectiveResponse`를 공유한다.

### 2.6 중심 이야기 생성 규칙 v3.1

완료된 골드들을 검토한 결과, 기존 생성기는 틀린 요약보다 “문단의 주요 내용을 빠짐없이 담은 압축 요약”을 만드는 경향이 있었다. 반대로 일부 문단에서는 결과는 남기면서 이를 성립시키는 상위 분류나 인과 연결을 생략하기도 했다.

6개 경계 문단을 세 차례씩 비교한 결과 다음 규칙을 채택했다.

- 중요한 정보를 최대한 많이 담는 요약을 만들지 않는다.
- 문단을 조직하는 독립 중심 방향을 보존한다.
- 결론뿐 아니라 결론을 성립시키는 핵심 분류·대조·인과 연결을 보존한다.
- 사례·적용·조건·예외는 문단의 중심 기능을 수행하거나 중심 방향을 바꿀 때만 포함한다.
- 문단 전체가 원리의 적용을 설명한다면 `원리 → 적용 사례` 연결 자체를 보존한다.
- 반복 사례, 중간 단계, 부가 논평은 독립 중심 주장으로 전개되지 않는 한 제외한다.

이 규칙은 `paragraph-analysis-prompt-v3.1`에 반영됐다. 중심 이야기 품질은 개선됐지만, 같은 단계에서 관계 역할까지 정하려 하면 다시 과잉 `required`가 발생했다. 따라서 중심 이야기 생성, 축 생성, 관계 매핑을 별도 단계로 분리했다.

### 2.7 축과 관계의 생성 순서 분리

중심축을 원자 관계에서 만들면 관계가 많이 분해될수록 축도 함께 늘어나는 문제가 있었다. 현재 순서는 다음과 같이 고정한다.

```text
문단 원문과 지문 맥락
  → centralStory와 coreRelations 후보 생성
  → centralStory 사람 검토
  → centralStory만으로 centralAxes 무손실 분해
  → 확정된 축에 coreRelations 매핑
  → 사람 검토 후 골드 승격
```

축 생성 단계는 중요도를 다시 판단하지 않는다.

- `centralStory`의 의미를 삭제하지 않는다.
- 새로운 의미를 추가하지 않는다.
- 문장 경계가 아니라 독립 의미 구조에 따라 나눈다.
- 인과·대조·종합처럼 함께 있어야 하나의 의미가 되는 내용은 한 축으로 묶는다.
- 모든 중심 이야기 의미는 하나 이상의 축에 포함돼야 한다.

관계는 `한 관계 = 한 상태·한 오류` 원칙을 따른다. “한 질문” 조건은 관계 단위에서 제거했다.

### 2.8 명시적 오류 우선순위 수정

법인 두 번째 문단에서 학생이 법인격 구조 일부를 누락하면서 기본 재산 외 자산의 활동을 “영리 추구”라고 잘못 표현했다. 중심축 게이트는 누락 때문에 UNCLEAR를 반환했고, 관계 진단은 명시적 오류를 `contradicted`로 기록했다. 기존 계약은 `UNCLEAR + contradicted`를 허용하지 않아 사용자에게 내부 예외가 노출됐다.

이 사례로 최종 상태 합성 규칙을 코드에 고정했다.

1. `contradicted` 관계가 하나라도 있으면 ERROR
2. 오류가 없고 모든 중심축이 포착됐으면 PASS
3. 오류가 없고 미포착 또는 부분 포착 축이 있으면 UNCLEAR

관계 진단은 게이트의 CAPTURED 또는 UNCLEAR를 명시적 오류가 발견된 경우 ERROR로 승격할 수 있다. 누락 질문보다 명시적 오류 교정이 우선한다.

## 3. 현재 골드 생성 방식

### 3.1 1단계: 중심 이야기와 원자 관계 후보 생성

입력은 전체 지문 맥락과 타겟 문단이다. `paragraph-analysis-prompt-v3.1`이 다음을 생성한다.

- 문단의 중심 대상 `centralObject`
- 중심 설명 구조 `centralStory`
- 명제와 명제 간 관계
- 기능적 의미 영역
- 원자적인 `coreRelations`
- supporting 정보와 불확실성

이 단계는 `centralAxes`와 `diagnosticRole`을 만들지 않는다. 출력은 자동 확정 골드가 아니라 검토 후보이다.

### 3.2 2단계: 중심축 무손실 분해

`central-axis-decomposition-prompt-v2`에는 `paragraphId`와 확정된 `centralStory`만 제공한다. 원문이나 `coreRelations`로 중요도를 다시 판단하지 않는다.

출력은 다음을 포함한다.

- 중심 이야기 의미 단위 `centralStoryMeanings`
- 독립 중심축 `centralAxes`
- `READY` 또는 `NEEDS_REVIEW`
- 모호한 중심 이야기나 축 경계 문제

### 3.3 3단계: 축–관계 매핑

`axis-relation-mapping-prompt-v1`은 확정된 축을 수정·분할·병합하지 않고 `coreRelations`를 관련 축에 연결한다.

다음 문제가 있으면 `NEEDS_REVIEW`로 남긴다.

- 중심축에 필요한 관계가 없음
- 관계가 중심 이야기 범위 밖에 있음
- 어느 축에 속하는지 모호함

### 3.4 사람 검토와 골드 승격

현재 합의된 지위는 다음과 같다.

- 모델 분석은 골드 후보 생성기로 사용한다.
- 모델 출력만으로 골드를 자동 확정하지 않는다.
- 사람이 `centralStory`, 독립 중심축, 관계 입도와 매핑을 검토한 뒤 골드로 승격한다.
- 대량 생산 단계에서는 별도 검토 API를 추가할 수 있지만, 현재의 사람 승인 경계를 없애는 것은 별도 검증 과제다.

최종 판정 골드는 최소한 다음을 가진다.

- 문단 원문
- `centralObject`
- `centralStory`
- `centralAxes`와 각 축의 `relationIds`
- 원자적 `coreRelations`

## 4. 현재 판정 방식

### 4.1 입력과 누적 상태

판정기는 최초 자유 응답, 이전 질문–응답 기록, 이전 학생 표상 스냅샷을 받는다. 후속 질문은 문단마다 최대 3회다.

이전 턴에서 확인된 관계 상태는 새 답변이 수정하거나 반박하지 않는 한 unknown으로 되돌리지 않는다. 마지막 답변에서 새롭게 확인되거나 수정된 관계를 갱신한 뒤 이전 상태와 병합한다.

### 4.2 1단계: 중심축 게이트

`central-story-gate-prompt-v1`은 다음만 입력받는다.

- 문단 원문
- `centralStory`
- 사람이 검토한 `centralAxes`
- 학생의 누적 응답과 이전 축 상태

`coreRelations`는 입력하지 않는다.

각 축의 상태는 다음과 같다.

- `captured`: 축의 최소 인과·대조·조건·귀속·역할 연결이 표현됨
- `partial`: 일부 대상이나 결과는 있으나 축의 연결이 불충분함
- `unknown`: 축을 판단할 학생 표현이 없음
- `distorted`: 방향, 귀속, 주체, 원인·결과 또는 대조를 명시적으로 잘못 말함

게이트의 전체 상태는 다음과 같이 계산한다.

- 왜곡된 축이 있으면 `DISTORTED`
- 모든 축이 포착되면 `CAPTURED`
- 그 밖에는 `UNCLEAR`

질문 대상 축의 우선순위는 다음과 같다.

1. 왜곡된 축
2. 완전히 빠진 축
3. 부분적으로 표현된 축

같은 상태의 축이 여러 개면 ID 순서가 아니라 질문 하나로 중심 이야기의 빈 구조를 가장 크게 복원할 축을 선택한다.

### 4.3 2단계: 관계 진단과 질문 생성

`axis-diagnostic-prompt-v2`는 게이트가 합성한 `effectiveResponse`와 모든 `coreRelations`를 사용해 각 관계에 상태를 정확히 하나씩 부여한다.

- `explicit`: 학생이 직접 표현함
- `entailed`: 학생 표현들을 결합하면 안정적으로 도출됨
- `contradicted`: 학생이 명시적으로 뒤집거나 잘못 연결함
- `unknown`: 누적 응답으로 판단할 수 없음

관계 상태의 목적은 학생의 내적 표상을 더 세밀하게 기록하고 오류 위치를 찾는 것이다. unknown 관계의 수나 비율은 PASS 점수가 아니다.

`explicitErrors`는 모델 출력이 아니라 모든 `contradicted` 관계에서 코드가 결정적으로 파생한다.

### 4.4 최종 상태 합성

최종 상태의 권한은 코드에 있다.

```text
contradicted 관계가 하나 이상인가?
  예 → ERROR
  아니오 → 게이트가 CAPTURED인가?
             예 → PASS
             아니오 → UNCLEAR
```

따라서 다음 조합은 허용하지 않는다.

- PASS + contradicted 관계
- UNCLEAR + contradicted 관계
- ERROR + contradicted 관계 없음

게이트가 `DISTORTED`라면 관계 진단은 그 왜곡에 대응하는 `contradicted` 관계를 찾아야 한다.

### 4.5 PASS의 의미

PASS는 학생이 원문의 모든 명제나 모든 core 관계를 말했다는 뜻이 아니다.

PASS는 다음을 뜻한다.

- 모든 독립 중심축의 최소 충분 의미 구조가 누적 응답에 복원됐다.
- 중심 이야기를 훼손하는 명시적 관계 오류가 없다.

전문 용어, 예시, 중간 단계, 부수 조건이 빠져도 중심축이 자기 말로 정확히 복원됐다면 PASS할 수 있다.

## 5. 질문 생성 방식

### 5.1 질문 단위

한 질문은 선택된 중심축 하나를 확인한다. 축 내부의 서로 연결된 귀속·주체·대조 요소는 한 질문에서 함께 물을 수 있다. 축 안의 모든 원자 관계를 순서대로 캐묻지 않는다.

### 5.2 UNCLEAR의 진단 질문

- 선택된 unknown 또는 partial 축만 확인한다.
- 축의 정의 구조를 확인하는 데 필요한 최소 범위만 묻는다.
- 정답 관계, 방향, 원인, 결과, 조건 또는 목적을 질문 안에서 알려 주지 않는다.
- 질문을 읽는 것만으로 학생의 unknown 관계가 확인된 것으로 처리하지 않는다.

### 5.3 ERROR의 교정 질문

- 명시적으로 충돌한 관계를 누락 축보다 먼저 다룬다.
- 학생의 오류 지점은 가리키되 올바른 답 자체를 제시하지 않는다.
- 중심 이야기를 가장 크게 훼손하는 오류 하나를 우선한다.
- 질문 유형은 `CORRECTIVE`다.

## 6. 실제 UI 대화 흐름

```text
지문 선택
  → 첫 문단 제시
  → 최초 자유 응답
  → 누적 응답 합성
  → 중심축 게이트
  → 관계 표상 갱신 및 최종 상태 합성
     ├─ PASS: 다음 문단으로 이동 가능
     ├─ UNCLEAR: 중심축 진단 질문
     └─ ERROR: 명시적 오류 교정 질문
  → 후속 답변 누적
  → 같은 판정 사이클 반복
```

후속 질문은 최대 3회다. 세 번째 후속 답변 뒤에도 PASS하지 못하면 문단 상태는 `UNRESOLVED`로 종료된다.

개발자용 UI에서는 응답 여부와 관계없이 이전·다음 문단이나 지문 선택 화면으로 이동할 수 있다. 방문한 문단의 상태는 해당 런타임 세션 안에서 보존된다.

## 7. 검증 과정에서 확인한 사항

지금까지의 검증은 다음 성격을 가진다.

- 헤겔 문단 5건 회귀 테스트
- 분야가 다른 8개 문단의 수준별 응답 평가
- v2 계약에 대한 누적 53건 점검
- 중심 이야기 v3/v3.1 경계 문단 6개 × 3회 비교
- 승인된 축 골드 6개 검토 및 승격
- 기존 실제 자유 응답 10개 세션의 축 기반 재실행
- 법인·도파민·정보 비대칭 등 실제 다회 대화의 과잉 질문 점검
- 명시적 오류와 누락이 함께 있는 법인 2문단 응답의 실제 API 회귀 확인

이 결과는 현재 구조가 여러 문단 유형에서 일관되게 작동한다는 근거다. 그러나 특정 테스트셋의 통과를 일반적 정확도 검증으로 과장하지 않는다. 실제 인간 참가자가 전체 지문을 순차적으로 수행하는 검증은 계속 별도 과제로 남는다.

## 8. 현재 한계와 운영 원칙

### 8.1 자동 골드 확정 금지

문자열·ID·스키마 검사는 코드로 수행하지만 다음 의미 검증은 아직 모델과 사람 검토에 의존한다.

- `centralStory`가 문단의 중심 기능을 정확히 선별했는가
- 중심축이 중심 이야기의 의미를 손실 없이 덮는가
- 축이 배경·사례·중간 단계까지 과도하게 승격하지 않았는가
- core 관계가 독립적인 상태·오류 단위인가

따라서 현재 골드 생성기는 사람 검토형 후보 생성기다.

### 8.2 관계 상태는 표상이지만 완전한 인지 모형은 아님

`relationStates`는 학생이 문단의 핵심 관계를 어떻게 표현했는지 보여 주는 유용한 내적 표상 근사치다. 하지만 학생의 전체 인지 구조나 잠재 지식을 직접 측정하는 것은 아니다. 명제 단위 분석은 골드 생성과 오류 위치 확인에 사용하되, 대화 판정을 불필요하게 원자화하지 않는다.

### 8.3 모델 변동성과 실패 처리

- 호출별 제한시간은 60초다.
- 연결 오류, 타임아웃, 429, 5xx만 한 번 재시도한다.
- 계약·스키마 오류는 재시도하지 않고 파싱 결과와 실패 로그를 보존한다.
- 판정 시간과 토큰 사용량은 단계별 메타데이터에 기록한다.

## 10. 일단락 시점의 최종 합의

1. 중심 이야기는 문단의 주요 정보를 모두 담은 축약본이 아니라 문단을 조직하는 중심 방향과 핵심 연결이다.
2. 중심성 판단은 `centralStory` 생성 단계에서 한 번 수행한다.
3. 중심축은 확정된 `centralStory`를 중요도 재판단 없이 무손실 분해한다.
4. PASS 단위는 중심축이며 모든 독립 중심축이 포착돼야 한다.
5. core 관계는 학생 표상과 오류 위치를 기록하는 원자 단위이지 PASS 체크리스트나 질문 순서표가 아니다.
6. 현재 축 기반 경로는 `required/error_only`를 사용하지 않는다.
7. 최초 응답과 질문–응답은 담화 문맥을 반영한 하나의 누적 응답으로 합성한다.
8. 한 질문은 관계 하나가 아니라 중심축 하나를 확인한다.
9. 정답을 먼저 알려 주는 유도 질문은 만들지 않는다.
10. 명시적 오류는 누락보다 우선하며, `contradicted` 관계가 있으면 최종 판정은 ERROR다.
11. 골드 생성 결과는 사람이 검토하고 승인하기 전까지 자동 확정하지 않는다.
12. 이후 구조 변경은 기존 프롬프트를 덮어쓰지 않고 새 버전으로 분리해 비교 가능성을 보존한다.
