## 1. 문제: 지금 코드로는 진단평가가 돌지 않는다

코드 조사(2026-11-06, 하위 에이전트 읽기 전용 조사) 결과, 막히는 곳은 다섯 군데다.

### 1-1. 문항마다 바로 피드백하는 흐름을 지문 단위로 바꿔야 한다 (논의 뒤 고침, 2026-11-06)

- 정정: 첫 판은 "판정기 v5가 교정 대화에 묶여 있어 떼어 내야 한다"였다. 코드를 다시 보니 묶인 것은 컨트롤러
  (`packages/app/src/server/problem-feedback.ts:56`)뿐이다. 판정에 쓰는 함수(`createFeedbackSession`,
  `submitFeedbackCommand`, `evaluate`, `applyFeedbackAssessment`)는 모두 따로 부를 수 있다. 판정기는 고치지 않는다.
- 방향 변경(사용자, 2026-11-06, [D-0204](../memory/decisions/D-0204-sns-diagnostic-keeps-service-feedback.md)):
  진단평가도 본 서비스의 피드백(교정 대화·요약 대화)을 유지한다. 다만 지문의 문항을 모두 답한 뒤 문항을 하나씩
  피드백한다. 분석은 첫 응답만 쓴다.
- 지금 코드와 다른 점은 세 가지다.
  - 제출하자마자 정오를 알려 준다("정답이 아니야…", `problem-feedback.ts:139`). 진단평가는 지문의 답 입력이 끝날 때까지 숨긴다.
  - 교정 질문 도중 빠져나갈 명령이 없다(`packages/pipeline/src/problem-solving/feedback.ts:13`). 진단평가는 "이 문항 건너뛰기"가 필요하다.
  - 지문 결과 정리("4문항 중 3개를 맞혔어…")가 없다.
- 판정이 끝난 풀이 상태는 교정 질문 대기(`AWAITING_CORRECTION`)로 멈춰 학생 입력을 기다린다(`feedback.ts:523`). 그래서 뒤 문항을 푸는 동안 앞 문항 판정을 끝내 두고, 지문 끝에 그 상태로 돌아가 교정을 이어 갈 수 있다.

### 1-2. 사고 진단 v0.1과 문단 판정이 앱에 없다

- 사고 진단 v0.1(D-0111, 무너진 단계 판정)은 오프라인 스크립트만 있다(`scripts/test-thought-diagnosis-v01.mjs`). 검증 자료는 가상 풀이 36개다.
- 문단 요약 판정(D-0183 2단계)도 오프라인 스크립트만 있다(`scripts/run-analysis-judge-gongsun.mjs`, 모델 luna). D-0183은 2단계 구현을 범위 밖으로 두었다.
- 결과 화면의 ② 무너진 단계와 ③ 독해 패턴은 이 두 판정의 출력이 있어야 그릴 수 있다.

### 1-3. 지문 파일이 문항 하나만 연결한다

- `problemQuestionId`는 문자열 하나다(`packages/app/src/server/content.ts:61`, `shared/contract.ts:174`). 주석은 "현재 MVP는 지문당 하나만 노출"이다.
- 세트 E 지문 파일도 첫 문항만 넣었다. 나머지 문항은 `notes`에 글로만 적혀 있다. 예: 의식과 인지는 12번만 넣고 13~16번은 "연결 문항 전체: …"로 적었다.
- 문제 묶음 경로는 `packages/pipeline/fixtures/experiments/problem-solving`으로 고정이다(`content.ts:35`). 그래서 앱이 세트 E 폴더(`fixtures/experiments/sns-diagnostic/`)를 읽지 못한다.

### 1-4. 익명 참가자와 기록 저장이 없다

- 세션은 서버 메모리 `Map`에 있다(`problem-feedback.ts:57`). 소유자는 `'local'` 고정이다(`packages/app/src/server/index.ts:75`).
- 서버를 다시 켜면 진행 중인 세션이 사라진다. 그래서 "지문 단위 저장"을 할 수 없다.

### 1-5. 결과 화면이 없다

- 가장 가까운 기존 화면은 두 가지다.
  - 마지막 설명 말풍선: `ProblemLabApp.tsx`.
  - 개발자용 분석 수형도: `AnalysisViewApp.tsx`, `/dialogue/lab/analysis`.
- "내 위치", "걸린 함정" 같은 화면은 없다.
- D-0202에 따라 지금의 학생용 화면(`/problem`, `/dialogue`)은 바탕으로 쓰지 않는다. 확정된 개발자용 화면을 고쳐 새로 만든다.

## 2. 전략

### 2-1. 백엔드

**(1) 진단 세트 목록 파일로 지문당 여러 문항을 푼다**

- 지문 파일의 `problemQuestionId`는 바꾸지 않는다. 훈련 서비스 계약을 건드리지 않기 위해서다.
- 대신 세트 목록 파일 하나를 새로 둔다: `packages/pipeline/fixtures/experiments/sns-diagnostic/diagnostic-set-e.json`. 이 파일이 지문 순서, 지문별 문항 목록, 문항별 메가스터디 수치를 갖는다.

```json
{
  "schemaVersion": "sns-diagnostic-set-v1",
  "setId": "set-e",
  "passages": [
    { "passageId": "consciousness-cognition", "questionIds": ["consciousness-cognition-q12", "…", "consciousness-cognition-q16"],
      "exam": { "label": "2024학년도 6월 평가원", "megastudySeq": 0 } }
  ],
  "items": {
    "consciousness-cognition-q15": {
      "megastudy": { "correctRate": [70, 80], "choicePercents": [[4, 70, 9, 11, 5], [2, 80, 6, 8, 3]],
                     "subjects": ["화법과작문", "언어와매체"], "source": "메가스터디 이용자 기준" },
      "rasch": { "b": null }
    }
  }
}
```

- `megastudySeq: 0`과 `b: null`은 자리 표시다. 값은 인계 실행 때 `candidates.json`과 2-2절 계산으로 채운다.
- 메가스터디 수치는 `docs/experiments/sns-diagnostic-candidates-2026-11-05/candidates.json`에 이미 있어서 새로 수집하지 않는다.
  예를 든 의식과 인지 15번 값이 그 파일의 실제 값이다.
- 공용 읽기 함수(`content.ts`)와 `problemQuestionId`는 고치지 않는다(문제점 3 논의, 2026-11-06). 두 컨트롤러가 읽기를 밖에서
  받으므로(`problem-feedback.ts:59` `loadSource`, `dialogue-simple.ts:72` `passages`) 세트 E 폴더를 읽는 함수를 넣는다.
  요약 대화는 골드를 읽지 않아(`dialogue-simple.ts:55`) 세트 E 지문 파일을 그대로 쓴다.

**(2) 문항 풀이: 본 서비스 상태기계를 그대로 쓰고 순서만 바꾼다(D-0204)**

- 문항마다 본 서비스와 같은 풀이 상태(`FeedbackSession`)를 하나씩 둔다. 판정기·지시문·모델 배분(정답 luna·오답 sol)은 바꾸지 않는다.
- 한 지문의 흐름:
  1. 답 입력: 문항마다 선택 + 근거. 근거는 문항마다 "근거 생략"을 고를 수 있다(`rationale: OMITTED`). 근거를 쓴 문항은
     제출 즉시 뒤에서 선택 판정을 시작한다. 정오·교정 질문은 화면에 보이지 않는다.
  2. 지문 결과 정리: 그 지문 판정이 모두 끝나면 보인다. 규칙은 아래 표.
  3. 문항별 피드백: 첫 문항부터 "첫 번째 문항으로 돌아가 볼게. ①을 골랐네…"로 본 서비스 피드백을 이어 간다. 근거를 생략한
     오답은 본 서비스처럼 이때 근거를 묻는다(`feedback.ts:321`). 이 근거는 첫 응답이 아니므로 분석에 쓰지 않는다.
  4. 다음 지문.
- 지문 결과 정리 규칙(사용자 동의, 2026-11-06):

| 칸 | 규칙 |
|---|---|
| 정답 수 | 첫 선택 기준 |
| 적절한 근거 | 근거를 쓴 문항만 분모. 판정 `contentAssessment = SUPPORTED`만 적절. `INSUFFICIENT`·`ERROR`·`UNKNOWN`은 적절 아님 |
| 근거 생략 | 수를 따로 말함("1개는 근거 생략") |
| 판정 실패(재시도까지) | 분모에서 빼고 "1개는 확인 중이야" |
| 오답 + `SUPPORTED`(문항 검토 `ITEM_REVIEW`로 감, `feedback.ts:498`) | 적절로 세지 않고 개발자용 검토 목록에 올림 |

  예: "이 지문의 4문항 중 3개를 맞혔어. 근거를 쓴 3개 중 2개가 적절했어(1개는 근거 생략)."
- 건너뛰기: 교정 질문마다 "이 문항 건너뛰기". 새 명령 `SKIP`을 공용 명령 목록에 더한다. 누르면 교정을 그만두고 마지막 설명
  확인("설명 볼래?", `END_START`)으로 간다. 기존 명령은 바꾸지 않으므로 본 서비스 동작은 그대로다. 버튼은 진단평가 화면에만 보인다.
  지문 전체 건너뛰기는 두지 않는다.
- 근거 생략 문항: 판정·사고 진단을 부르지 않는다(비용 0). 결과 화면에서는 "운"이 아니라 "근거 생략"으로 센다.
- 골드·선지 연결 층은 판정 입력에 넣지 않는다(D-0002·D-0003·D-0162). 결과 화면 표시에만 쓴다.

**(2′) 문단 요약: 본 서비스 요약 대화를 그대로 쓴다(D-0204)**

- 지문 시작 때 "문단별 요약" 또는 "요약 안 하기"를 고른다. 고른 값은 기록한다.
- 요약을 고르면 본 서비스 요약 대화(개발자용 단순 문단 대화 `dialogue-simple`)를 그대로 하고, 그 뒤 문항을 푼다.
- 요약 도중 다음 문단으로 넘어갈 수 있다. 지금 코드로 이미 된다(`dialogue-simple.ts:85` `navigate`). 진단평가 화면에는 "요약 마치고 문제 풀기" 버튼을 둔다.
- 분석(독해 패턴·수형도)은 문단별 첫 차례만 쓴다. D-0183 수형도는 마지막 차례를 쓰지만, 진단평가는 첫 차례로 바꾼다.
- 요약 대화가 문항보다 먼저라서, 요약을 고른 참가자의 문항 첫 응답에는 요약 피드백이 섞인다. 사용자가 알고 골랐다(D-0204). 요약 선택 여부로 두 집단의 위치를 나눠 비교할 수 있게 기록한다.

**(3) 사고 진단과 문단 판정을 파이프라인 모듈로 옮긴다**

- 사고 진단 v0.1:
  - `scripts/test-thought-diagnosis-v01.mjs`의 지시문·출력 스키마를 그대로 `packages/pipeline/src/thought-diagnosis/`로 옮긴다.
  - 모델은 sol로 고정한다(D-0115).
  - 대상: 첫 응답이 오답인 문항과, 근거 판정이 `SUPPORTED`가 아닌 정답(사용자 선택 (나), 2026-11-06). `SUPPORTED` 정답과
    근거 생략 문항은 돌리지 않는다.
  - 입력은 문제 묶음 + 선택 + 근거로, 세트 E 묶음 형식과 같다(`docs/experiments/thought-diagnosis-v01-2026-10-10/sources.json`).
    검증은 가상 풀이 36개(sol 36/36)뿐이다.
- 문단 판정:
  - `run-analysis-judge-gongsun.mjs`의 v3 지시문을 옮긴다(입력: 동결 지도 + 학생 요약, 모델 luna).
  - 요약을 고른 지문에서만, 문단별 첫 차례에 대해 노드마다 1회 호출한다(`run-analysis-judge-gongsun.mjs:219`).
    세트 E 지도는 소리 62·의식과 인지 (가) 52·(나) 33·플라스틱 71노드로, 모두 요약하면 약 300회(luna, 약 $0.07 추정, 미측정).
  - 첫 차례가 들어오면 바로 시작한다. 요약 대화와 문항 풀이 동안 끝나므로 대기는 거의 드러나지 않는다. 결과 화면에서
    못 끝난 칸은 "분석 중"으로 둔다.
  - v3 지시문은 공손룡·도파민 대화로만 검증했다. 세트 E 지도로는 측정(4절) 때 처음 돌린다.
  - 세트 E 분석 골드 위치: `docs/experiments/sns-diagnostic-gold-2026-11-05/<passageId>/frozen-map.json`. 의식과 인지는 (가)와 (나) 두 개다.
- 옮긴 뒤에는 스크립트와 모듈이 같은 입력에 같은 요청 본문을 만드는지 대조하는 테스트를 둔다. 외부 전송 없이 할 수 있다.

**(4) 실행 시점: 지문을 끝낼 때마다 뒤에서 돌린다**

| 사건 | 바로 하는 일 | 뒤에서 돌리는 일 |
|---|---|---|
| 요약 대화(선택) | 본 서비스와 같음 | 문단마다 첫 차례 분석 판정 |
| 문항 답 제출(선택 + 근거) | 기록 저장, 다음 문항으로 | 선택 판정 1회(근거 생략이면 없음) |
| 지문 답 입력 끝 | 위치 범위 갱신(정오만으로 계산) | 첫 응답 사고 진단 |
| 그 지문 판정 모두 끝 | 지문 결과 정리, 문항별 피드백 시작 | 교정 판정·마지막 설명(본 서비스와 같음) |
| 마지막 지문 끝 | 결과 화면 진입, 끝나지 않은 일은 진행 표시 | 남은 일 |

- 위치 범위는 정오만으로 계산하므로 판정을 기다리지 않는다.
- 지문 결과 정리는 그 지문의 선택 판정을 기다린다. 마지막 문항 판정이 늦으면 대기가 생긴다(4절 측정 항목).
- 결과 화면은 판정이 오는 대로 칸을 채운다. D-0183이 수형도에서 정한 "구조 먼저, 판정 오면 켜기"와 같은 방식이다.

**(5) 저장: 참가자 파일 + 사건 기록**

- 참가자 id는 `randomUUID()`로 만들고, 브라우저에는 그 id만 둔다.
- 서버 저장은 두 가지다.
  - `CSAT_DIAGNOSTIC_ROOT/<participantId>.json`: 현재 상태.
  - `events.jsonl`: 사건 기록.
- 이번 단계는 로컬 시연·소규모 시범이다(사용자 선택 (가), 2026-11-06). 저장은 로컬 파일로 하고, 저장 부분은 인터페이스
  하나로 감싼다(`JsonlStudentEvidenceStore`와 같은 방식). 공개 배포용 저장소(DB)는 개인정보(4절)와 함께 출시 전에 정한다.
- 기록하는 것:
  - 지문마다 요약 선택 여부.
  - 문항마다 선택, 근거 원문, 풀이 시간과 근거 입력 시간(따로), 판정·진단 원출력과 호출 메타데이터.
- 서버를 다시 켜도 참가자 파일에서 이어 간다(지문 단위 저장).

### 2-2. 위치 추정과 보정

**(1) 문항 난이도: 메가스터디 정답률로 정한다**

- 문항 i의 메가스터디 정답률을 p_i라 하자. 선택과목 두 값은 D-0201처럼 평균을 쓴다.
- 이용자 능력이 평균 0, 표준편차 σ인 정규분포라고 두면 근사식은 b_i ≈ −logit(p_i) × √(1 + πσ²/8)이다.
- σ는 정답률만으로 정해지지 않는다. 그래서 기본값 1로 두고, 0.8과 1.5로 바꿔 보는 민감도 확인을 한다.
- 사례: 플라스틱 문항의 정답률 범위는 30~79.5%다(D-0201).
  - p=30%이면 σ=1일 때 b ≈ +1.00이다. 어려운 문항이다.
  - p=79.5%이면 b ≈ −1.60이다. 쉬운 문항이다.

**(2) 참가자 능력: 지문마다 범위로 좁힌다**

- 정오 자료로 사후분포를 구한다(EAP, 사전분포 N(0, σ²)). 80% 구간을 범위로 쓴다.
- 지문을 끝낼 때마다 다시 계산한다. 그래서 범위가 1지문 → 4지문으로 갈수록 좁아진다(D-0200).
- 문항 수가 적어서 범위가 넓다. 16문항이면 표준오차가 0.5 logit 안팎이다(D-0200 조건 3, 미측정 추정). 실제 폭은 인계 실행 때 문항 난이도를 넣어 계산해 보고한다.

**(3) 전국 기준으로 옮기기: 시험 단위 보정(D-0203)**

- 생각: 참가자 능력 θ를 "그 시험 전체(45문항)를 봤다면 받았을 예상 점수"로 바꾼 뒤, 평가원 공식 분포에서 그 점수의 위치를 찾는다.
  - 메가스터디 표에는 그 시험 45문항 전체의 정답률이 있다. 그래서 예상 점수를 계산할 수 있다.
  - 예상 점수는 집단과 무관하다. 그래서 메가스터디 이용자 쏠림이 위치에 직접 묻어나지 않는다.
- 세트 E는 시험 4개(2024 6월, 2024 수능, 2025 6월, 2026 9월)에서 왔다. 시험마다 전국 위치를 구해 평균 내고, 구간 끝도 같은 방법으로 옮긴다.
- 화면 표기: "수능 기준 환산 추정 2~4등급"처럼 범위로 쓰고, 분포 곡선 위에 등급 띠를 깐다(웹 에이전트 제안 채택).
- **이 방법이 서려면 확인할 것(첫 확인 항목)**
  1. 평가원 원자료에 표준점수 도수분포(누적 비율)가 있는지. 언론 보도로만 확인했고 원자료는 확인하지 못했다(D-0203).
  2. 원점수를 표준점수로 바꾸는 표를 어디서 구하는지. 국어는 선택과목 조정이 있어서 원점수와 표준점수의 대응이 선택과목마다 다르다.
     공통과목(독서·문학) 점수만으로 옮기는 근사가 가능한지 본다.
  3. 세트 E 네 시험의 메가스터디 45문항 표. 후보 추리기 때 받은 자료(`docs/experiments/sns-diagnostic-candidates-2026-11-05/`)에 있는지 확인한다.
- 확인이 늦어지거나 안 되면 임시로 "메가스터디 이용자 중 위치(보정 전)"를 표기와 함께 보인다. 이 임시안은 D-0203과 달라서, 쓰기 전에 사용자 승인을 받는다.
- 참가자 자료로 다시 맞추기: 이번에는 저장 형식만 맞춘다(문항별 정오, 시간 조건). 계산은 하지 않는다.

### 2-3. 화면

- 경로는 새로 `/diagnostic`을 둔다. 학생 경로이고 개발자 모드와 분리한다.
- 문항 풀이 칸(지문 + 문항 + 선지 + 근거 입력)은 `ProblemLabApp.tsx`의 문제 표시 부분을 떼어 다시 쓴다(D-0202).

**(1) 흐름**

1. 시작 안내: 익명, 시간 제한 없음, "PC·태블릿 강력 권장", 동의 칸(4절 조건이 정해질 때까지는 시연용 문구).

## 4. 열린 항목과 확인 계획

1. **추천 최소 근거(6).**
   - 임시 규칙 제안: 같은 비틂에 2번 이상 걸렸을 때만 "자주 걸린 함정"이라고 말한다. 1번뿐이면 "이번에 걸린 함정"으로 낮춰 말하고, 오답이 없으면 "어려운 문항으로 더 풀어 보기"를 권한다.
   - 대응표(비틂 14종 → 세트 1~2개)는 사람이 고른다. 이번에는 형식만 만든다.
2. **비용·대기 시간(7).**
   - 측정 방법: 세트 E 16문항에 가상 참가자 풀이 몇 명분을 만들어 실제로 보낸다. 참가자 1명당 총비용과 마지막 지문 끝 → 결과 화면 완성까지의 시간을 잰다.
   - 외부 전송이라 인계 실행 전에 범위(인원·요청 수·상한)를 따로 승인받는다.
   - 기존 자료 재활용(D-0168): 세트 E에 대한 판정 출력은 아직 없다. 재활용할 수 있는지는 승인 요청 때 다시 확인해 적는다.
3. **개인정보(8).** 법정대리인 동의 방식, 근거 원문 저장 기간·범위, 공개 배포용 저장소. 출시 전 조건이며 이번 인계 범위 밖이다.
   **공유 기능**(위치 카드 이미지·결과 링크)도 여기에 묶는다. 공유 링크가 결과 접근 권한이 되므로 공개 배포 때 함께 정하고,
   시범 단계는 화면 캡처로 둔다(PC로 이어 하기 링크와 같은 이유).
4. **위치 보정 원자료 확인.** 2-2 (3)의 세 가지. 백엔드 인계 실행 전에 코드 에이전트가 먼저 확인한다.
