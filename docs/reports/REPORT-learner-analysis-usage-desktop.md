# 학생 사고 패턴 분석 결과의 활용 방향: 웹 에이전트 논의용 인계 (2026-11-05)

상태: **논의 전 인계 문서**. 채택된 정책이 아니다. 코드 에이전트 세션(2026-11-04~05)에서 사용자와
논의 범위만 합의했고, 방향 논의는 웹 에이전트와 한다. "사실"로 적은 내용에는 저장소 근거를 달았다.
"코드 에이전트 의견"은 미합의 제안이다.

## 1. 논의 목적과 범위

### 사용자 문제 제기 (2026-11-05, 원문 요지)

- 문단 요약·문제 풀이 두 파트에 걸쳐 학생의 사고 패턴 분석을 여러 방식으로 만들었다. 이 결과를
  **실제로 어떻게 쓸지** 논의하고 싶다.
  - 분석 결과를 **UI에 어떻게 보여 줄지**
  - 문제 풀이 분석 결과를 **백엔드에서 어떻게 쓸지**(사용자 예시: 오류 패턴 분석으로 유사 문제 추천)
- 동기: EBS 단추 진단평가를 직접 해 보니 결과 분석이 아주 거친 수준이었다. 이런 분석은 EBS 단추나
  학생이 직접 쓰는 범용 AI 서비스가 하기 어려운 부분이다. 그래서 이 분석 서비스를 잘 활용하는 것이
  **우리 서비스의 해자**가 될 수 있다고 본다.

### 합의된 범위

- 이번 논의의 결과물은 **(가) 방향 논의까지**다(사용자 선택, 2026-11-05). 활용 방안 후보를 비교해
  방향을 정하고 결정 기록으로 남긴다.
- 화면 구성과 백엔드 구조를 인계 문서 수준으로 정하는 **(나) 설계 확정은 다음 단계**이고 별도로 한다.
- 논의 대상은 아래 2절 표의 분석 장치 전부다(사용자 확인, 2026-11-05).
- **아직 정하지 않은 것**: 분석 결과를 **누가 보는지**(학생·교사·학부모·개발자). 코드 에이전트가
  확인 질문으로 준비했지만 묻기 전에 웹 에이전트 논의로 넘어갔다. 논의의 첫 질문으로 둔다(5절 Q1).

**직접 쓴 말**(요약문, 선택 이유, 교정 답변)을 근거로 하므로, 같은 오답이라도 원인을 나눌 수 있다.

## 4. 이미 정해진 제약 (논의 때 지켜야 할 것)

- **골드의 런타임 사용 금지**: 구조화 문제 골드는 별도 비교와 사용자 결정 없이 학생용 런타임 입력에
  넣지 않는다(D-0002, D-0003). 선지 연결 층도 피드백 런타임에는 넣지 않는다(D-0162). 분석 결과를
  **세션 뒤 보여 주기·추천**에 쓰는 것과 **판정 입력**으로 쓰는 것은 구별해야 한다.
- **합성 실험은 효과의 증거가 아님**: 사고 진단·정답 경로는 가상 풀이로만 검증했다. 실제 학생
  데이터는 없다(`memory/CURRENT_STATE.md` 금지선·잔여 위험). 학생에게 진단을 단정적으로 보여 줄
  근거가 아직 없다.
- **표본 규칙**: 칸 N<10은 "표본 적음". 학생별 표는 층·갈래까지만 보인다(D-0160).
- **문단 분석 화면 방향은 이미 있음**: 수형도(마지막 차례, 시각적 보상)와 관계 유형 그래프(첫 차례,
  진단, 비율이 아닌 개수)(D-0183). 이번 논의는 이 결정을 넓히거나 바꿀 수 있지만, 바꾸면 D-0183을
  대체하는 기록이 필요하다.
- **사고 진단은 주기 실행**: 실시간 피드백이 아니라 묶어서 돌린다(D-0115).
- **문항 풀이 작다**: 동결 자료가 있는 문항은 UI 6지문, 선지 연결 기준 24문항이다(D-0170). 고1 학평
  지문 확장은 합의만 있고 작업은 미정이다(`memory/CURRENT_STATE.md` 프로젝트 단계).

    같은 읽기 과정 중 무엇인가?
  - 24문항으로 추천이 성립하는가, 문항 확장이 먼저인가?
- **Q4. 검증 전 노출 수준**: 실제 학생 데이터로 정확도를 확인하기 전에 무엇까지 보여 줄 수 있는가?
  교사 시연(D-0198)이나 첫 실제 학생 확인에서 분석 정확도도 함께 잴 것인가?
- **Q5. 분류 통일 시점**: 세 분류 목록(D-0181)을 두 축으로 통일하는 일을 활용 설계 전에 할지, 재검증
  때까지 미룰지. 추천·리포트가 한 좌표계를 요구하면 앞당길 이유가 생긴다.
- **Q6. 학생 기록의 형태**: 분석 결과를 학생 단위로 어떻게 쌓는가(Q-0037). 세션 로그에 붙이는가, 별도
  학생 원장을 두는가? 학생 식별·로그 저장은 얇은 학생판 범위 설계(`memory/CURRENT_STATE.md` 우선순위
  3)와도 겹친다.

## 6. 코드 에이전트 의견 (미합의, 참고용)

- 논의 순서는 Q1 → Q4 → Q2·Q3을 권한다. 보는 사람과 노출 수준이 정해져야 화면·추천의 모양이 정해진다.
- 해자는 "더 많은 지표"보다 **"같은 오답을 원인별로 나눠 다르게 대응한다"**를 학생이 체감하는 데서
  생긴다고 본다. 그래서 추천의 첫 형태는 "같은 원인을 다시 시험하는 문항·선지"가 자연스럽다. 이미
  동결된 선지 연결 층(비틂 종류)과 출제자 전략 글이 좌표로 쓸 수 있는 자산이다.
- 24문항이라는 문항 수 한계 때문에, 당장의 추천은 문항 단위보다 **선지 단위**(같은 비틂의 다른 선지)가
  현실적일 수 있다. 문항 확장이 필요해지면 지도·선지 연결 동결 절차의 비용도 함께 따져야 한다.
- 사고 진단·정답 경로는 가상 풀이로만 검증했으므로, 학생 화면에 단정형으로 올리기보다 교사·개발자
  쪽 집계에 먼저 쓰고, 실제 학생 데이터로 맞는지 확인한 뒤 학생 화면에 올리는 순서가 안전하다고 본다.
