## 1부. 학습자 분석 활용 방향 (2026-11-05)

출발 문서: `docs/reports/REPORT-learner-analysis-usage-desktop.md` (Q1~Q6).

### 1.1 누가 보는가 (Q1)
- [사용자 결정] 첫 대상은 **SNS 독해력 테스트 참가자**. 교사 시연도 **같은 UI**로 충분하다.
- [웹 제안] 화면 기준은 SNS 쪽(익명, 한 번 참여, 결과를 바로 기대, 공유할 만해야 함). 교사용 반 단위 집계는 학생이 모인 뒤 붙인다.
- [사용자 결정] 참가 동기는 "내가 어느 위치에 있는지 검증해 보고 싶다".

### 1.2 테스트 구성
- [사용자 결정] EBS 단추식 **진단평가** 형식. 28문항은 이탈이 크므로 **4지문, 약 16문항**. EBS 28문항에 사용자는 약 1시간이 걸렸다.
- [웹 제안, 철회] 근거를 지문당 1~2문항에만 받자는 제안은 현재 구조(문항마다 선택 + 근거)와 맞지 않아 철회했다.
- [사용자 결정] 문제 풀이는 **현재 구조 유지**: 문항마다 선택 + 근거.
- [사용자 결정] 기기: "PC·태블릿에서 하는 걸 강력 권장" 안내. **모바일용 UI는 따로 둔다.**
  - [웹 제안] 모바일을 막지 말고, "PC로 이어 하기 링크 받기"와 지문 단위 저장, 기기 정보 기록.
- [사용자 결정] 풀이 시간에서 **근거 입력 시간을 뺀다.**
  - [웹 제안] 둘 다 따로 기록(입력 시간도 확신 정도의 신호).
- [사용자 결정] 문단 요약은 **처음부터 선택 사항.** (중간안 "지문 1~2는 풀이만, 3~4에서 선택"을 사용자가 스스로 대체.)
  - [웹 제안] 지문마다 시작할 때 선택을 묻고, 선택 여부를 기록(선택 편향 확인용).
- [사용자 결정] 시간 제한 없음.

### 1.3 결과 화면 (Q2·Q4)
순서: ① 내 위치 → ② 문제 풀이 결과 → ③ 독해 패턴(요약한 경우).

**① 내 위치**
- [사용자 결정] 수능 기출로 구성(필요하면 새 지문 세트). **IRT로 고3 수험생 모집단 중 위치(%)**를 보인다. 지문 하나로는 어려우므로 지문마다 분포상 위치를 **범위**로 보이고, **세트를 풀수록 범위가 좁아지는 시각화.**
- [사용자 결정] 문항별 정답률, 선지별 선택률 자료를 이미 보유(메가스터디).
- [웹 제안] 평가원은 문항 모수를 공개하지 않으므로 정답률로 Rasch 근사 → 자체 응답으로 재보정. 시간 압박이 없고 근거를 쓰는 조건이라 "수능 기준 환산 추정"으로 표현. 등급 띠를 깔기. (이후 D-0207 위치 보정으로 구체화됨.)
- [웹 제안] 문항 카드 예: "전국 정답률 41% · 너는 ④를 골랐어, 전국 27%도 ④ · ④는 조건을 원인으로 바꾼 선지 · 네 근거 ↔ 원문". 위 두 줄은 EBS도 가능하지만 아래 두 줄은 학생 근거가 있어야만 나온다(해자).

**② 문제 풀이 결과**
- [사용자 결정] 기본 제시: **정답의 질**(근거 있는 정답 vs 약한 정답), **무너진 단계**(사고 진단), **걸린 함정**(선지 비틂 14종).
- [사용자 결정] 출제자 전략 글은 이미 풀이 과정에서 선택 사항으로 보이므로 결과 화면에 따로 두지 않는다.
- [사용자 결정] 시간 × 정오는 시간 제한이 없으므로 **삭제.**
- [웹 제안, 반영됨] 정답 경로(READ·LINK·APPLY)는 사고 진단과 겹치므로 학생 화면에서 빼고 개발자용으로만.
- [웹 제안, 사용자 동의] 무너진 단계는 실제 학생으로 검증 전이므로 **개수로 말하는 "경향" 표현**("틀린 5개 중 3개가 근거 해석 단계에서 어긋났어"). 유형 단정 금지.

**③ 독해 패턴 (요약한 경우)**
- [웹 정리] 20~24문단이면 문단 안 관계 약 90~110개(D-0160 기준 문단당 약 4.5개). 개인 단위로 믿을 수 있는 건 층·갈래까지, 18유형은 표본 부족.
- [사용자 결정] 바로 보여 주기: **층별 패턴, 4갈래 강약, 요약에서 놓친 관계 ↔ 틀린 문항 연결.** 더 보기: 틀린 이해(`CONTRADICTS`) 실제 사례, 문단 순번·분야별 추이.
- [웹 제안] 원문 복사 걸러내기, 판단엔 포착률보다 오류율 우선.

### 1.4 별도 규칙인 이유
- [사용자 결정] 지금까지는 실제 서비스를 고려해 만들었지만, SNS 진단평가는 특별한 경우라 **규칙이 달라져야 한다.**
- [웹 정리] 훈련 서비스 결정은 그대로 두고 "SNS 진단평가 모드" 범위로 예외를 묶는다. 영향을 받는 결정: D-0115(사고 진단 주기 실행), D-0176(학생 확인 전 노출), D-0183(요약 판정 노출 단계). 골드·선지 연결을 판정 입력으로 쓰지 않는 제약(D-0002·D-0003·D-0162)은 유지하고 결과 표시에만 쓴다.
- [사용자 결정] 사고 진단을 결과 화면 전에 돌리는 것 동의(참가자당 약 $0.2 추정).

### 1.5 추천 (Q3, SNS 한정)
- [사용자 결정] SNS 추천의 목적은 "구독하면 이런 서비스까지 받는구나"라는 인상. 진단에 쓴 16문항·약 80선지의 비틂 분석만으로 "너는 대체로 ○○ 비틂에서 함정에 빠지는 경향이 있어. 비슷한 구조의 지문 세트로 '…'를 추천해"까지만. **추천 대상 세트는 분석하지 않는다.** DB 전체에 선지 연결 층을 넓히지 않는다.
- [웹 제안] 비틂 14종 → 추천 세트 1~2개의 작은 대응표를 사람이 고른다.

## 2부. 피드백 유지와 첫 응답 원칙 (2026-11-06)

### 2.1 판정기와 교정 대화 (CLI 메시지 설명)
- [확인한 사실, CLI] 판정기 자체는 교정 대화에 묶여 있지 않다. 교정 흐름에 묶인 건 컨트롤러다. 진단평가는 `createFeedbackSession` → `submitFeedbackCommand(SELECT)` → `evaluate` → `applyFeedbackAssessment`까지만 부르면 된다.
- 근거 생략 처리: CLI가 (나) "근거 칸 + 버튼" 안을 추천했고 웹도 동의. 이후 D-0208에서 버튼 이름은 **[근거 미제출]**로 정해졌다.

### 2.2 피드백을 유지할 것인가
- [사용자 결정] SNS 진단평가의 진짜 목적은 **본 서비스에 대한 실제 사람들의 응답·평가 수집**, 부차 목적은 **본 서비스 유입**. 일반 진단(정답만 입력 → 분석만)으로 만들면 서비스 매력이 크게 준다. 그래서 **메인 서비스의 피드백 과정을 유지**한다.
- [사용자 결정] 그 경우 **분석 결과는 첫 응답에 국한**한다.
- [웹 제안, 이후 D-0204에 반영] 같은 지문 안에서 앞 문항의 교정 대화가 뒤 문항의 답을 알려 주면 첫 응답이 오염된다. 그래서 **지문 단위로 답을 다 낸 뒤 교정**한다.
- [사용자 결정] 문단 요약을 선택한 경우 **본 서비스 요약 과정(요약 대화 포함)을 그대로 유지**, 분석은 문단별 첫 요약만.
- 결과 보고서의 첫 판 "교정 대화 없이 판정만", "요약 대화 없이 1회 판정"은 폐기했다.

### 2.3 인계 A(백엔드) 검토
- 검토 문서: `docs/review/sns-diagnostic-backend-handoff-review-2026-11-06.md`.
- [웹 제안] 넘기기 전에 정할 것 셋: (1) `answers-done` 전 답 수정 가능 여부(추천: 고칠 수 있고 판정은 그때 한꺼번에), (2) 참가자 파일 동시 쓰기(참가자 단위 직렬 저장), (3) 문항 검토(`ITEM_REVIEW`) 문항의 정답이 결과 API에서 드러남(D-0208 2와 충돌). 그 밖: `RESUME` 성공 시 첫 판정 갱신, 풀이 시간 정의, 문단 판정이 참가자당 259회라 비용 측정 때 우선 확인.
- CLI가 "질문 없이 정한 것" 다섯 가지에는 모두 동의.

### 2.4 학생용 표현 (D-0209 이전 초안 검토)
- [웹 제안] 학생용 문장은 **반말**(D-0116)로 맞추기. 정도 바꾸기 예시 교체, "글에 없는 서술 방식" 예시·이름 개선, "내용끼리의 연결" 이름 개선, 화면 문장은 개수로("6곳 중 2곳").
- [웹 제안] 헷갈리는 쌍: "원인·근거 바꿔치기 / 맞는 사실을 엉뚱한 이유로"는 지금 설명으로 안 갈림. 뒤쪽을 "상관없는 두 사실 잇기"로. "'모두·반드시'로 단정하기 / 적용 범위 넓히기"도 첫마디에 차이를 넣기.
- [웹 제안] ★ 이름 4개 사용. 기타 숨기기 동의. "바뀐 내용" 문장은 세트가 고정이니 약 60문장을 한 번 생성 후 사람이 손보기.
- 사용자가 이후 D-0209로 확정했다(내용은 D-0209 참고).

### 2.5 화면 인계 B의 빈칸 J1~J7
- [웹 제안] J1·J3·J4·J5는 추천대로. J4("바뀐 내용" 문장)와 J5(추천 세트·"훈련 서비스 알아보기")는 공개 전 필수로 남기기.
- [웹 제안] J2(요약 ↔ 틀린 문항 연결): 바로 빼기 전에 세트 E 선지 연결 동결본 `parts[]`에 지도 노드·관계 id가 있는지 확인. 있으면 "비튼 부분이 이어진 지도 단위가 첫 요약에서 ABSENT/CONTRADICTS였나"로 간단히 구현 가능.
- [웹 제안] J6(원문 복사): 화면에서는 빼되 겹침 비율을 저장. (2026-11-07 추가: v4.8 출력에 이미 `sourceCopyDetected` 칸이 있다.)
- [웹 제안] J7 문장: [근거 생략] → D-0208의 **[근거 미제출]**과 통일. "옮긴 추정이야" → "환산해 본 추정치야". "이 칸은 만들지 못했어" → "이 부분은 분석하지 못했어". "정답이지만 근거는 더 볼 곳이 있어" → "정답이야. 근거는 조금 더 다듬을 수 있어".
- 사용자의 최종 선택은 CLI 쪽 기록을 따른다.

## 3부. 첫 완주 뒤 판정 문제 (2026-11-07)

### 3.1 코드 에이전트 보고서 검토
- 대상: `docs/reports/REPORT-sns-diagnostic-judgment-strictness-2026-11-07-desktop.md` (의식과 인지 14·16번).
- [웹 의견] 14번은 규칙이 지나치게 엄격, 16번은 판정 오류. lab과 모델·지시문은 같다.
- [웹 의견] P2(뜻이 같은 다른 표현 인정)·P4(교정 질문 형식 서버 검사)는 바로, P3(M4 내용으로 말하기, 학생 말 인용 허용)도 찬성, P1(선지에 적힌 연결은 다시 말 안 해도 됨)은 방향은 맞지만 "정답의 질" 정의를 바꾸므로 조건을 걸고 회귀로 확인.
- [웹 제안] 사례 2개에 맞춰 고치지 말고 나머지 지문도 풀어 본 뒤 원칙 단위로 고치기(과적합 경계). 정답 쪽 거짓 판정을 오답 쪽보다 우선(SNS 참가자에게 "맞혔는데 근거 부족"이 가장 나쁜 경험).

### 3.2 정답 판정과 오답 판정을 따로?
- [사용자 생각] 정답 판정과 오답 판정을 따로 하는 편이 좋겠다.
- [확인한 사실] **지금은 따로 하지 않는다.** 정답·오답 모두 같은 지시문 `source-direct-problem-feedback-v5.8.md`(41KB)를 쓰고, 차이는 모델(`FEEDBACK_SELECTION_MODELS = { correct: 'gpt-6-luna', incorrect: 'gpt-6.1-sol' }`, `feedback-evaluator.ts`)과 몇 개 조항(158행 정답 충족 순서, 332행 읽기 오류는 오답에서만)뿐이다.
- [웹 의견, 찬성] 오답 판정은 "무엇에 속았나"를 찾는 일이라 엄격해야 하고, 정답 판정은 "핵심을 짚고 맞혔나"를 확인하는 일이라 기본값이 인정이어야 한다. 한 지시문에서 정답 쪽을 느슨하게 하면 오답 쪽도 흔들린다.
- [웹 제안] 오답 쪽은 v5.8 그대로, **정답 쪽만 새 지시문**. 기준: 근거가 이 선지만 가르는 원문 사실을 짚었나, 판정을 바꾸는 모순이 있나. 공통 규칙(자료 경계·근거 기록)은 한 곳에서 공유. 정답이지만 이유가 틀린 경우(회사법 같은 사례)도 교정으로 보낼 수 있게 오류 판정은 남긴다. 대가: 정답 쪽 회귀를 새로 쌓아야 함.

### 3.3 사용자 첫 완주 코멘트 ↔ 기록 대조
