## 1. 왜 하나

- 수리 검사 e3는 선지마다 "〈보기〉 없이 지문 한 사실만으로 정오가 정해지나"를 본다.
- 1단계에서 평가자가 지름길이라 했는데 e3는 통과시킨 '놓침'이 나왔다. 오답형만 4건·3편이다.
- 수리 문턱과 생성 규칙이 서로 다르다.
  - 수리 문턱: 오답 넷이 모두 지름길이어야 수리하고, 셋이면 경고만 한다.
  - 생성 규칙 C23: 〈보기〉 없이 풀리는 선지는 많아야 1개다.
- 규칙 검토에서 문턱과 C23을 고치려면, **기출에서 실제로 〈보기〉 없이 풀리는 오답이 갈래별로 몇 개인지**가 기준이 되어야 한다(Ghootae 23:09 지적).
- C23의 "1개"가 기출을 세어 정한 숫자인지는 기록에서 찾지 못했다. `set-pattern-2026-11-18/BOGI-ANATOMY.md`(기출 9문항 해부)는 반대 방향인 "〈보기〉**만으로** 풀리는 선지"를 셌다.

## 3. 설계에서 정할 것 (새 창에서 논의)

1. **문항 고르기:** suneung_db(2023~2026, `~/Projects/suneung_db/output/`)에서 갈래별(사례·관점·과학 표)로 기출 3점 〈보기〉 문항 5~8개씩 고른다. 위 6개를 넣을지, 학평·모평을 섞을지, 갈래를 어떻게 판정할지(SET-PATTERN.md 갈래 기준)를 정한다.
2. **e3 실행:** 기출을 `passages/<id>/`에 등록하고 `eval-repair.mjs`를 REPAIR 없이 돌린다(calib 방식). 이전 calib를 어떻게 돌렸는지는 `deep-item-v5-2026-11-18/RESULT.md`·`README.md`의 보정 기록에서 확인한다.
3. **코덱스 질문문:** 선지마다 "〈보기〉의 자료를 봐야 정오가 정해지나(예/아니오, 근거 한 줄)". 블라인드 평가와 달리 출처(기출)를 숨길지는 정한다. 숨기지 않으면 "기출이니 좋다"는 쏠림이 생길 수 있다.
4. **집계:** 갈래별로 문항당 "〈보기〉 없이 풀리는 오답 수"의 분포(e3 / 평가자 4명 다수결), 그리고 e3와 평가자가 선지 단위로 얼마나 일치하는지
5. **판정에 쓸 기준을 실행 전에 정한다**(예: 갈래별 기출의 최댓값이나 중앙값을 문턱 후보로 삼는다).

## 4. 지켜야 할 것 (두 작업이 서로 섞이지 않게)

| 무엇 | 규칙 |
|---|---|
| 파일 | 태깅 산출물은 새 폴더(예: `docs/experiments/bogi-distractor-tagging-2026-11-22/`)에만 쓴다. `PLAN-repair-direction.md`, `deep-item-v5-2026-11-18/blind/`, 규칙·기준 파일(rules-*, kind-*, eval-repair.mjs 등)은 건드리지 않는다. 기출 지문 등록이 `deep-item-v5-2026-11-18/passages/`에 필요하면 새 id만 더한다(기존 id는 고치지 않는다) |
| git | 수리 방향 집계 2단계 커밋이 끝날 때까지 태깅 쪽은 커밋하지 않는다(동시에 git을 쓰면 index.lock이 부딪힌다). 커밋할 때는 태깅 파일만 넣는다 |
| 코덱스 | 2단계 코덱스 8회(사례 4 → 관점 4)가 끝난 뒤에 태깅의 코덱스를 돌린다(계정 한도). e3(API) 쪽은 언제 돌려도 된다 |
| CLI | 태깅 CLI는 2단계 CLI와 다른 세션으로 연다. 지시문 첫 줄에 "수리 방향 집계와 별개 작업"이라고 적는다 |
| 결정 | 태깅 결과는 여기서 판정하지 않는다. 규칙 검토(PLAN-repair-direction 6.2절 묶음 1)에서 2단계 결과와 함께 본다 |
