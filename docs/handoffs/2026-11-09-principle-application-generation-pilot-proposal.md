# 제안: 원리 적용형 문항 생성 파일럿 (P1)

- 날짜: 2026-11-09
- 작성: 웹 스레드 "원리 적용 구조 이슈 검토" (Ghootae 요청)
- 받는 쪽: 코드 에이전트(설계 확정·실행), Ghootae(승인)
- 관련: D-0210(E1 닫음, 원리 적용형을 새 설계로), `docs/experiments/principle-application-structure-2026-11-09/WEB-BRIEF-...md`(분류 검토), 웹 의견 `docs/handoffs/2026-11-09-principle-application-structure-review-web.md`
- 성격: 제안서. 실행 전 Ghootae 승인 필요(외부 API 호출 있음).

## 0. 한 줄 요약

기출 분류를 다 끝낸 뒤 만드는 대신, **재료가 분명한 지문 4개로 원리 적용 문항 8개를 바로 만들어 본다.** 그리고 "어디서 막히는지"를 확인한다. 생성은 세 단계로 나눈다. 규칙 뽑기 → 상황에 대입해 결과 계산 → 계산 단계를 하나씩 비틀어 오답 만들기.

## 1. 왜 이 순서인가

- 분류 검토는 "깊은 문항이 어떻게 생겼는가"는 알려 주지만 "만들 수 있는가"는 알려 주지 않는다.
- E1에서 생성기는 지문에 **이미 쓰인 연결**만 골랐다. 규칙에 값을 넣어 새 결론을 내는 일은 한 번도 시도하지 않았다. 지시문으로 시키지 않았기 때문일 수도 있고, 모델이 못 하는 것일 수도 있다. 이건 만들어 봐야 갈린다.
- 원리 적용 문항이 막힐 수 있는 지점은 세 군데다. 파일럿은 이 셋을 따로 관찰하게 설계한다.
  1. **재료:** 지문에 변수가 있는 규칙과 적용할 상황이 있는가
  2. **계산:** 모델이 규칙에 값을 넣어 지문에 없는 결과를 맞게 도출하는가
  3. **오답:** 같은 상황에서 "그럴듯하게 잘못 적용한" 오답을 만드는가

## 2. 대상

E1의 4지문을 그대로 쓴다. 기출 문항과 E1 생성물을 바로 옆에 놓고 비교할 수 있기 때문이다.

| 지문 | 쓸 만한 규칙(예비 확인) | 성격 |
|---|---|---|
| 표면 장력 | 라플라스 식(압력 차 ∝ 표면 장력 / 반지름), 오네소르게 수(점도↑ → 수↑, 표면 장력·밀도·노즐 지름의 곱↑ → 수↓), 안정 범위 0.1~1.0과 범위 밖 결과 | 식·변수가 분명함. 기준 사례(기출 15번) |
| 오디오 지각 부호화 | 임계대역 안 차폐, 고음일수록 임계대역 넓음, 소리 크기와 차폐 문턱값 차이↑ → 비트 많이 할당, 문턱값 아래 소리 제거 | 조건·대소 규칙 |
| 플라스틱 중합 | 공유 전자쌍↑ → 결합력↑, 개시제·사슬 성장·종결 메커니즘, 결정 영역 비율↑ → 유연성↓·불투명·밀도↑·단단함·열 변형↓ | 메커니즘·성질 대응 |
| 법인 | 자본금 = 발행 주식 수 × 액면가, 무상 증자는 자산 총 규모 불변, 재단·사단 / 영리·비영리 구분에 따른 통제 차이 | 비과학. 정의·제도 규칙이 원리 적용에 쓰이는지 시험 |

지문마다 문항 2개를 만들어 총 8문항이다.

- **문항 a (〈보기〉 없음, "㉠ 이해"형):** 상황을 지문 안에서 고른다. 지문에 나오지만 그 규칙의 결과가 쓰이지 않은 대상이다. 표면 장력 15번과 같은 형태다.
- **문항 b (〈보기〉 있음):** 지문 밖의 새 사례를 〈보기〉로 만든다. 수치나 조건이 들어간 짧은 상황이다.

## 3. 생성 흐름 (3단계, 각 단계 출력은 JSON, 코드 검증)

### 단계 1: 규칙 뽑기

- 입력: 지문 원문
- 출력: 규칙 목록. 규칙마다 다음을 적는다.
  - `ruleQuote`: 원문 그대로의 구절. 코드가 부분 문자열인지 검사한다.
  - `variables`: 변수와 방향(예: 반지름↑ → 압력 차↓)
  - `scope`: 규칙이 성립하는 조건(예: 구형 방울, 크기 유지 시)
  - `statedApplications`: 지문이 이미 결과를 말한 적용 대상. 이것은 피해야 할 목록이다.
  - `openSlots`: 지문에 나오지만 이 규칙의 결과가 쓰이지 않은 대상(예: 기포 합체)
- 골드 지도는 주지 않는다. E1에서 골드 이점이 없었고, 지문 직접 추출이 되는지가 먼저 궁금하다. 지도 대조(H4)는 실행 뒤 따로 한다.

### 단계 2: 상황 설계와 계산표

- 입력: 지문, 단계 1 규칙 목록, 문항 형태(a 또는 b)
- 출력: 상황 하나와 **계산표**
  - `situation`: 문항 a는 `openSlots` 중 하나, 문항 b는 새 사례
  - `usedRules`: 규칙 1~2개. 2개를 엮으면 더 좋다(15번은 라플라스 식 + 공기 이동 원리).
  - `steps`: 값 대입 → 중간 결론 → 최종 결론. 각 단계에 근거 `ruleQuote`를 붙인다.
  - `derivedFacts`: 이 상황에서 참인 결론 3~5개. **지문에 그대로 쓰인 문장은 안 된다.** 코드로 원문과 겹침을 검사한다.
- 핵심 제약: 결론이 지문 문장의 복사·뒤집기면 탈락시킨다. 계산 단계가 최소 1개는 있어야 한다.

### 단계 3: 선지 설계와 집필

- 입력: 지문, 계산표
- 정답: `derivedFacts` 중 하나(발문 극성에 따라 참 또는 거짓 하나)
- 오답: **계산표의 단계 하나를 비틀어** 만든다. 선지마다 `breaksStep`과 `twistType`을 적는다.
  - `DIRECTION`: 비례·반비례나 증감 방향을 뒤집음
  - `WRONG_VARIABLE`: 결과를 정하는 변수를 다른 변수로 바꿈
  - `HOLD_CONSTANT_ERROR`: 같아야 할 값을 다르다고 봄(예: 같은 물질인데 표면 장력이 다르다고 봄)
  - `SCOPE`: 규칙이 성립하지 않는 조건에 적용함
  - `SWAP_OBJECTS`: 비교 대상 두 개의 결과를 맞바꿈
- 선지 5개 가운데 4개 이상이 같은 상황 위에 서야 한다(`onSituation: true`).
- 집필은 E1과 같이 별도 호출로 하고, 계산표를 그대로 넘긴다.

### 모델

- 생성: `gpt-6.1-sol` (E1과 같음. 비교를 위해 바꾸지 않음)
- 단계 1~3을 각각 다른 호출로 한다. 지문당 a·b 2문항이라 지문당 호출은 약 5회(규칙 1 + 상황 2 + 집필 2), 전체 약 20회다. 비용은 E1 v3 실측을 기준으로 코드 에이전트가 실행 전에 추정해 적는다.

## 4. 검증 (생성과 다른 판정자, 블라인드)

1. **풀이 검증:** opus 하위 에이전트에게 지문과 문항만 주고 풀게 한다. 정답이 키와 맞아야 한다. 풀이에 계산표 단계에 해당하는 대입이 나타나는지도 기록한다.
2. **구조 판정:** 분류 검토의 기준표(웹 의견의 수정안 반영)를 그대로 쓴다. 정답 선지가 `APPLIED`(값을 대입해 안 쓰인 결과를 도출)로 판정되는지 본다. 기출 15번과 E1 v3 생성 문항을 같은 묶음에 섞어 블라인드로 판정한다.
3. **오류 검사:** 사실 오류, 정답 복수, 정답 없음, 지문으로 판단 불가를 표시한다.
4. **Ghootae 직접 검토:** 8문항을 기출 15번, E1 생성 문항과 나란히 놓은 비교표로 본다. 판단은 "기출 15번만큼 생각하게 만드는가" 하나다.

## 5. 성공·실패 기준 (실행 전 고정)

문항마다 통과 조건은 넷이다.

- (가) 풀이 검증에서 키와 일치하고 오류 표시 없음
- (나) 정답 선지 또는 정답 아닌 참 선지 중 2개 이상이 `APPLIED`
- (다) 선지 4개 이상이 같은 상황 위
- (라) Ghootae가 "깊다"고 봄

해석은 이렇게 한다.

- 8문항 중 5개 이상 통과: 이 방식으로 원리 적용형 생성기를 본설계한다.
- 2~4개 통과: 어느 단계에서 떨어졌는지 본다(아래 표). 그 단계만 고쳐 2차를 돈다.
- 1개 이하: 모델이 계산·오답 설계를 못 하는 것인지 확인하고, 사람이 계산표를 주는 반자동 방식을 검토한다.

| 떨어진 곳 | 뜻 | 다음 수 |
|---|---|---|
| 단계 1 `openSlots`가 비거나 엉뚱함 | 지문 재료 문제 또는 추출 문제 | 지문 선별 기준을 만들거나, 상황은 〈보기〉로만 만든다 |
| 단계 2 결론이 지문 복사 | 모델이 "새 결론"을 안 냄 | 계산표 형식을 더 강제하고, 예시를 넣는다 |
| 단계 2 계산 틀림 | 모델 추론 한계 | 검산 호출을 추가하거나 모델을 바꾼다 |
| 단계 3 오답이 단순 뒤집기뿐 | 오답 설계 약함 | `twistType` 배분을 고정한다 |
| 법인만 실패 | 비과학 지문엔 다른 방식 필요 | 정의·제도형은 따로 설계한다 |

## 6. 분류 검토와의 관계

- 분류 검토(WEB-BRIEF)는 내부 하위 에이전트라 외부 비용이 없으니 **병행**한다. 분류 결과는 "8지문 세트에서 원리 적용 문항이 어느 자리에 몇 개 있는가"를 알려 준다. 그 결과로 파일럿의 문항 a/b 배분이 맞았는지 사후 확인한다.
- 기준표는 두 작업이 같은 것을 쓴다. 그래야 기출, E1 생성, P1 생성을 같은 눈금으로 비교할 수 있다.

## 7. 범위 밖

- 학생 앱 연결, 운영 반영은 하지 않는다.
- 골드 지도 입력 조건(B)과의 비교는 하지 않는다. 필요하면 2차에서 한다.
- E2(지문 대체 생성)는 손대지 않는다. 다만 단계 1의 `openSlots`가 지문마다 얼마나 나오는지는 기록한다. 이 값은 "원리 적용 문항을 만들려면 지문 쪽에 적용 자리가 있어야 하는가"를 판단할 근거가 되고, E2 재검토 때 쓴다.

## 8. Ghootae가 정할 것

1. 이 파일럿을 분류 검토와 병행할지 (추천: 병행)
2. 대상 4지문과 지문당 a·b 2문항 구성 (추천: 그대로)
3. 성공 기준의 "8개 중 5개" (추천: 그대로. 표본이 작으니 숫자보다 떨어진 단계 표를 더 중시)

## 9. 중단·보고 조건

- 외부 API 호출 전, 호출 수와 비용 추정을 적고 Ghootae 승인을 받는다.
- 단계 1에서 4지문 중 2개 이상이 `openSlots` 0개면 단계 2로 가지 않고 보고한다.
- 이 문서와 결정 기록이 충돌하면 멈추고 선택지를 보고한다.
