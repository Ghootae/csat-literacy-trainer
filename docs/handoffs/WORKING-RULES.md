# Ghootae 작업 규칙 (웹·데스크탑 스레드)

- 2026-11-21에 처음 만들었다. 규칙이 생기거나 바뀔 때마다 이 문서를 고친다.
- 새 스레드는 인수인계서와 함께 이 문서를 먼저 읽는다.
- 원본은 Mac 저장소 `docs/handoffs/WORKING-RULES.md`이고, CSAT 프로젝트 `handoffs/WORKING-RULES.md`에 사본을 둔다.

## 1. 설명 방식 (2026-11-21)

- 설명이 여러 섹션에 걸치면 **한 번에 한 섹션만** 보낸다. Ghootae가 이해했다고 하면 다음 섹션으로 넘어간다.
- 첫 메시지에서 섹션 목록(제목만)을 먼저 보여 줘서 전체 길이를 알 수 있게 한다.
- 쉬운 말로 쓴다. 용어는 처음 쓸 때 풀어 준다(예: 충실도 검사, 읽기 판).

## 2. CLI 지시문 (2026-11-21, 앞 규칙과 합침)

지시문 바로 뒤에 짧은 설명을 붙인다.
- **목적:** 이 지시로 무엇을 알아내거나 얻으려는가
- **방법:** 무엇을 어떻게 하는가
- **다음 스텝:** 결과에 따라 다음에 무엇을 하는가

앞 인수인계서에서 정한 규칙도 그대로 지킨다.
- **추정 비용:** 호출 수 × 단가로 적는다. 코드만 바꾸면 "API 비용 없음"이라고 적는다. 수리 단계가 돌면 문항당 약 $0.8이다(r3 실측).
- **최소 실행 검토:** 전부 돌려야 하는지 먼저 따진다. 판정에 필요한 지문·문항만 돌리고 앞 단계 결과를 재사용한다.
- **커밋 시점과 CLI 전환 알림:** 커밋할 때와 CLI로 넘어갈 때를 먼저 알린다. 지시문은 붙여 넣을 수 있게 준다.
- **폐기된 지시문:** 앞서 준 지시문이 바뀌거나 폐기되면, 어느 지시문의 어느 단계가 무효인지 분명히 알린다.

## 3. 규칙 수정 절차 (2026-11-21)

생성 규칙의 범위: rules-*, kind-*, polish-checklist, readability-guide, 수리 단계 기준.

1. 규칙을 추가하거나 고치는 논의는 웹 스레드에서 한다.
2. 수정안이 나오면 웹 스레드 Claude가 충돌과 모순을 검토한다.
   - 그 규칙과 함께 읽히는 규칙 묶음 전체(실행 조합 A/B × 갈래마다)와 대조한다.
   - 대조용 기출 문항이 묶음 전체를 지키는지도 본다.
   - 한 갈래에서 생긴 규칙을 다른 갈래로 넓힐 때는, 넓히는 갈래마다 그 갈래의 기출 2문항 이상과 대조한다(2026-11-23).
   - 결과는 `REVIEW-rules-<날짜>-<주제>.md`로 남긴다.
3. 검토 결과를 보고 다시 논의한다.
4. Ghootae가 결정한다.
5. CLI가 결정된 문안을 그대로 반영하고, grep으로 들어갔는지 확인한다. CLI는 규칙 파일을 직접 고치지 않고, 보고서에 후보만 적는다.

첫 적용: `experiments/set-pattern-2026-11-18/REVIEW-rules-2026-11-21-graph.md`.

## 4. 세션 관리 (2026-11-21)

**CLI 세션 리셋**
- 웹 스레드 Claude가 알맞은 시점을 먼저 알린다.
- 알맞은 시점: 작업 단위(칸 하나, 또는 지시문 묶음 하나)가 커밋으로 끝나고 `memory/CURRENT_STATE.md`가 갱신된 직후, 다음 칸을 시작하기 전.
- 리셋 전에 확인할 것: CURRENT_STATE의 '다음 할 일'이 웹 결정과 맞는가. CLI는 웹 결정을 모르면 폐기된 안을 적는다(2026-11-21에 실제로 그랬다).
- 이런 신호가 보이면 앞당긴다: CLI가 이전 결정과 다른 말을 할 때, 큰 실행·판정을 여러 번 마친 뒤.

**웹 대화창 교체**
- 웹 스레드 Claude가 알맞은 시점을 먼저 알린다.
- 알맞은 시점: 한 주제(칸 하나의 논의 등)의 결정이 기록된 직후, 다음 작업이 새 파일 묶음을 읽어야 할 때.
- 이런 신호가 보이면 앞당긴다: 큰 보고서·평가·생성 파일을 많이 읽어 대화가 길어졌을 때.
- 교체 전에 Claude가 인수인계서를 쓴다. Mac `docs/handoffs/`와 CSAT 프로젝트 `handoffs/` 두 곳에 둔다.
- 새 대화창은 인수인계서와 이 문서를 먼저 읽는다.

## 4-1. 판정 읽기 (2026-11-23)

- 칸 판정에서 두 판의 평균 차이: 0.5 미만 = 차이 없음, 0.5~1.0 = 약한 차이, 1.0 이상 = 차이. 근거: 같은 판 재평가 9쌍 중 8쌍이 0.5 이하, 1쌍 1.00.

## 4-2. 칸 판정 기준 (2026-11-24, Ghootae "가로 결정", `PROPOSAL-cell-judging-criteria.md`)

- 점수: 평가자 등급 수능 같음 2 / 중 1 / 수능 아님 0의 평균. 칸 = 생성 A·B 2문항.
- D = 칸 평균 − 같은 블라인드 기출 평균. 블라인드는 지문 하나씩, 같은 문항 묶음을 순서만 바꿔 2회(codex, 무료) 돌려 두 회차 평균으로 판정한다.
- 순서: ① 기출 평균 1.0 이하 → 멈춤(1.25면 '대조 기출 낮음' 주의) ② 생성 문항 중 '수능 아님' 2회 이상 → 미달 ③ D > −0.5 그리고 칸 평균 ≥ 1.25 → L2 통과 / D > −0.5지만 칸 평균 < 1.25, 또는 −1.0 < D ≤ −0.5 → 거의 통과 / D ≤ −1.0 → 미달.
- '수능 같음' 횟수는 보고만 하고 판정에 쓰지 않는다. 거의 통과 → 그 칸 1회 재생성 → 결과와 상관없이 기록. 미달 → 멈추고 웹 검토.
- ①·② 칸에 소급했다(② 사회 표·그래프 = 통과(소급, 대조 기출 낮음 주의)).

## 5. 앞 인수인계서에서 옮긴 규칙

출처: 11-15 인수인계 6절, 11-19 인수인계 6절.

- **문서:** 한국어 .md만 쓴다. 원문 밑줄은 굵은 글씨로 표시한다.
- **저장:** 결과물은 CSAT 프로젝트와 Mac 저장소 두 곳에 둔다. 웹 스레드는 커밋하지 않는다.
- **규칙 쓰기:**
  - 원칙과 점검 질문으로 쓴다. 예시는 시험 지문과 다른 소재로 든다.
  - 사람이 중간에 끼어드는 단계는 넣지 않는다.
  - 한 번 본 실패로 문구 규칙을 더하지 않는다(과적합 경계).
- **평가:**
  - 사람 판정 대신 코덱스 평가자 블라인드 판정을 쓴다.
  - Claude가 Ghootae 평가를 들은 뒤에 평가를 쓰면, 독립 평가가 아니라고 밝힌다.
- **개인 정보:** 사용자의 이메일을 외부 요청에 쓰지 않는다.
