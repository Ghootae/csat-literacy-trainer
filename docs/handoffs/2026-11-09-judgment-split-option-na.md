- 날짜: 2026-11-09
- 작성: 웹 스레드 "정답·오답 판정 구조 논의 이어가기"
- 받는 쪽: 코드 에이전트(Mac CLI)
- 먼저 읽을 것: `memory/checkpoints/2026-11-09-web-judgment-structure-discussion.md`(웹 논의 전문), `memory/checkpoints/2026-11-07-feedback-overfitting-candidates.md`(코드 에이전트 쪽 마지막 상태)
- 성격: 결정 전달 + 작업 제안. 이 스레드는 코드·지시문을 바꾸지 않았다. 결정 기록(D-NNNN)은 코드 에이전트가 쓴다.

> **코드 에이전트 검토 반영(2026-11-09):** 결정 기록 [D-0213](../../memory/decisions/D-0213-diagnostic-judgment-split-option-na.md). 이 문서와 다른 점: 정답+선택–근거 불일치는 범주 3 + 리뷰, 판정 불가 정답은 '확인 못 함'(범주 1 아님), 확신 정답은 화면에서도 합치지 않음, 정답 판정 sol은 **진단에서만** 시험(lab·본 서비스는 나중에 결정), 대기 줄이기는 문항별 피드백 열기 + 결과 카드 즉시 표시 먼저(미리 판정은 대기 측정 뒤).

## 1. Ghootae 결정 (2026-11-09)

1. **진단 오픈: 2026년 11월 안.** 큰 구조 개편(sol이 문항별 판정·질문·가이드를 쓰고 luna가 가이드대로 리뷰만 맡는 안, 체크포인트 2.8절)은 다음 버전으로 미룬다.
2. **(나)로 먼저 간다.** 결과 화면의 "정답의 질"은 3단계(근거 있는 정답 / 근거 약한 정답 / 근거 오류 정답)를 유지하고, 충분/부족 판정은 sol이 맡는다.
3. **(가)는 대비책이다.** Ghootae가 (나)로 직접 풀어 보고 짜증이 나면 (가)로 바꾼다. (가)는 정답을 "정답 / 정답이지만 근거 오류" 두 단계로만 나누고, 부족은 근거 있는 정답에 합친다.
4. **가장 중요한 기준(Ghootae 원문 요지):** "정답과 근거를 냈는데 다시 고치라고 하면 짜증나서 나가 버린다." 모든 설계 선택은 이 기준을 먼저 따진다.

## 2. 판정 흐름 (나)

| 학생 응답 | 판정 | 리뷰(교정 대화) | 결과 화면 |
|---|---|---|---|
| 오답 | sol | 연다 | 오답 |
| 정답 + 근거 충분 | sol | 열지 않는다 | 근거 있는 정답 |
| 정답 + 근거 부족 | sol | **열지 않는다** | 근거 약한 정답 |
| 정답 + 근거 오류(CONTRADICTED) | sol | 연다 | 근거 오류 정답 |
| 정답 + 판정 불가(UNKNOWN) | sol | 열지 않는다(제안) | 근거 있는 정답으로 표시, 기록에 보류 표시(제안) |
| "감으로 골랐어요" | 판정 안 함 | 열지 않는다 | 감으로 고른 문항(기존 안) |

- 코드로 정답·오답을 먼저 나누고, 정답에서 "부족"이면 리뷰를 열지 않는 것은 서버가 정한다. 지시문에 맡기지 않는다(원칙: 출력 필드 + 서버 검증).
- **정답 판정 모델 = sol.** 이전 논의의 "luna 먼저, 오류일 때만 sol"은 (나)에서는 이점이 거의 없다. 충분/부족 때문에 어차피 근거를 쓴 정답을 모두 sol로 판정해야 하고, 진단은 뒤에서 판정하므로 luna의 속도 이점도 작다. 그러니 정답 판정 모델 설정을 sol로 바꾸는 쪽이 단순하다(D-0104 재검토). **스레드 권고이며, Ghootae가 명시적으로 확인하지는 않았다.** 다르게 갈 이유가 있으면 Ghootae에게 물을 것.
- 모델은 "마지막 선택이 정답인가"로 고른다(`feedback-evaluator.ts`, `FEEDBACK_SELECTION_MODELS`). 그래서 `correct`를 sol로 바꾸면 **정답 재선택의 판정과 그 뒤 마지막 설명도 sol**이 된다. Ghootae 확인(2026-11-09): 재선택도 sol이 맡는다.
- 교정 판정(`FEEDBACK_REPAIR_MODEL`, luna 상수)은 이번 범위에서 그대로 둔다. 오디오 17 "26 대 25"(P2의 교정 적용)는 범위 밖 목록에 남긴다.
- 기존 보고서의 제안 "근거가 약한 정답도 교정 대화로 돌아간다"(`REPORT-learner-analysis-usage-web-result.md` 3절)는 이 결정으로 **폐기**한다.

## 2-1. "확실해요" 버튼 (Ghootae 결정, 2026-11-09)

- **모든 문항에 같은 버튼을 띄운다.** 문항별로 고르지 않는다. 이유(Ghootae): 학생 실력마다 쉬움의 기준이 다르고, 상위권이 짜증 내면 안 된다.
- 근거 입력 없이 "답이 확실하다"를 알리는 버튼이다. 기존 "감으로 골랐어요"와는 다른 버튼이다.
- 정답 + 확실: Ghootae 원안은 "근거 충분으로 자동 처리". 판정 호출, 사고 진단, 정답 마지막 설명을 모두 하지 않는다. 문항당 약 $0.06~0.07 절약.
- 오답 + 확실: Ghootae 원안은 "기록만".
- 스레드 제안, **Ghootae 동의(2026-11-09)** — 위 원안을 아래로 바꾼다:
  - 기록은 "확신 정답"으로 따로 남기고, 결과 화면에서만 근거 있는 정답에 합쳐 보여 준다(감으로 맞힌 학생도 누를 수 있어서).
    - **정정(2026-11-09, 코드 에이전트 검토 뒤 Ghootae 확정):** 결과 화면에서도 합치지 않는다. 2-2절을 따른다(합치면 근거를 쓴 학생만 "근거 약한 정답"을 받을 수 있어 근거 쓰기가 손해가 된다).
  - 오답 + 확실이면 기존 "근거 없이 고른 오답" 흐름처럼 근거를 한 번 묻는다. 확신 오답은 오개념 신호로 가장 가치가 크다.
- 나중 과제(Ghootae): 근거 입력 유도. 근거를 쓰면 보상을 주거나, 근거 없이 틀리면 감점한다. 본 서비스에는 이미 "근거 없이 고른 오답 감점" 문구와 `penaltyEligible` 기록이 있다(`feedback.ts`, 개발 버전에서는 실제로 깎지 않음).

## 2-2. 근거 없는 응답 버튼과 학생이 보는 범주 (Ghootae 결정, 2026-11-09)

지금 진단의 "근거 미제출" 버튼(`AnswerScreen.tsx`, `FeedbackScreen.tsx`) 하나를 버튼 두 개로 나눈다: **"확실해요"** / **"잘은 모르겠지만 정답 같음"**. 기존에 말로만 나온 "감으로 골랐어요" 버튼은 구현된 적이 없고, 이 두 버튼으로 대신한다.

| # | 범주 | 들어오는 길 | 리뷰 |
|---|---|---|---|
| 1 | 근거 있는 정답 | 근거 작성 + sol 충분 | 없음 |
| 2 | 근거 약한 정답 | 근거 작성 + sol 부족 | 없음 |
| 3 | 근거가 틀린 정답 | 근거 작성 + sol 오류 | 있음(기존 교정 질문) |
| 4 | 확신 정답 | 근거 없이 "확실해요" + 정답 | 없음(지금의 `unknown()` → `UNVERIFIED_CORRECT` 종료와 같음) |
| 5 | 확신 없이 맞힘 | 근거 없이 "잘은 모르겠지만 정답 같음" + 정답 | **있음, 새 방식** |
| 6 | 오답 | 모든 길("확실해요" 오답은 근거를 한 번 묻는다) | 있음(기존 리뷰) |

- 4·5는 학생이 스스로 고른 것이라 정답의 질 숫자(1~3)에서 빼고 개수만 보여 준다. 화면에서 4를 1에 합치지 않는다. 합치면 근거를 쓴 학생만 "약한 정답"을 받을 수 있어서, 근거를 쓰면 손해 보는 구조가 된다.
- 5의 결과 범주는 리뷰 결과와 상관없이 5로 남는다(첫 응답 원칙). 리뷰 결과는 서비스 반응 자료로 따로 기록한다.

**5번 리뷰 흐름 (Ghootae 안):**
1. 질문 대신 정답 설명의 일부를 먼저 보여 준다.
2. 학생에게 근거를 채워 보게 한다.
3. sol이 근거를 판정한다.
4. 충분하면 넘어가고, 아니면 정답 설명 전체를 보여 준다.

구현 메모와 정할 것:
- 상태기계에는 오답 + 근거 없음에 쓰는 `AWAITING_RATIONALE` 단계가 이미 있다. 정답 + "잘은 모르겠지만"도 `unknown()`으로 끝내지 말고 "힌트 보여 주기 → AWAITING_RATIONALE → SELECTION 판정"으로 보내면 새 단계 없이 재사용할 수 있다(확인 필요).
- **힌트 = sol이 따로 만드는 힌트 하나 (Ghootae 결정, 2026-11-09).** 코드가 5번(정답 + "잘은 모르겠지만")을 거르면, "답 입력 마침" 때 다른 문항 판정과 함께 sol 힌트 호출을 뒤에서 시작한다. 그러면 피드백 차례가 왔을 때 기다리지 않는다.
  - 이 시점에는 학생 근거가 없어서 판정 호출도 사고 진단도 돌지 않는다. 그러니 기존 호출에 얹을 수 없고 **독립된 짧은 호출**이다.
  - v5.8 전체 지시문이 아니라 짧은 전용 지시문을 쓰면 입력비가 작다(추정 호출당 약 $0.01, 미측정).
  - 힌트 규칙(제안): 정답 선지가 왜 맞는지(결론)는 말하지 않는다. 원문의 어느 곳과 선지의 어느 말을 맞대 볼지만 가리킨다. 정답 번호도 말하지 않는다.
  - 학생이 근거를 쓰면 sol SELECTION 판정(v5.8)을 한다. 충분하면 넘어가고, 부족하거나 오류면 마지막 설명을 생성해 공개한다. 마지막 설명은 이때만 만든다.
- (참고, 채택 안 됨) 다른 후보였던 것: 후보: (a) 원문 근거 위치만 칠해서 보여 주기, (b) 마지막 설명(layout v2 문단)을 먼저 생성해 첫 문단만 공개하기, (c) sol이 힌트 한 줄을 따로 생성하기. (b)는 실패 시 나머지를 바로 공개할 수 있고 호출이 늘지 않는다. 진단 자료에 문항별 근거 위치 표지가 있는지는 확인하지 못했다.
- 힌트를 본 뒤 쓴 근거라서 sol 판정의 "충분" 기준이 첫 근거와 같아도 되는지 정해야 한다. 힌트를 그대로 베낀 근거를 어떻게 볼지도 함께 정한다.
- "건너뛰기"를 둔다(짜증 기준).
- 비용: 5번 문항마다 sol 판정 약 $0.048 + 설명 약 $0.020.

## 2-3. 판정 시작 시점 앞당기기 (Ghootae 제안, 2026-11-09)

- 지금: 지문 단위 "답 입력 마침"(`answersDone`) 때 판정, 사고 진단을 한꺼번에 시작하고, 지문 판정이 **모두** 끝나야 1번 문항 피드백이 열린다(`checkPassageReady`). 11-07 실측 대기 19~103초.
- 제안: 문항의 답 + 근거가 저장될 때(draft 저장) 그 문항의 판정을 바로 시작한다. 판정 대상은 확정 전 답이다.
- 스레드 보완:
  1. 첫 응답은 그대로 "답 입력 마침" 시점의 답으로 정한다. 그때 답이 미리 판정한 답과 같으면 결과를 쓰고, 다르면 버리고 다시 판정한다. 선택과 근거 글이 완전히 같을 때만 재사용한다.
  2. 학생이 답을 고칠 때마다 판정하면 sol 호출이 낭비된다. 그래서 "다음 문항으로 넘어갈 때"처럼 한 번 정한 시점에만 시작한다. 낭비된 호출 수는 기록해 둔다.
  3. 피드백 여는 조건도 "지문 전체 판정 끝"에서 "그 문항 판정 끝"으로 바꾼다. 둘을 같이 해야 대기가 거의 0이 된다(11-07 보고서 7절 제안 2와 같은 방향).
  4. 힌트(C1)와 사고 진단도 같은 시점에 시작할 수 있다. 다만 C1인지는 정답 여부를 알아야 하는데, 이건 코드가 바로 안다.

## 3. (가)로 바로 바꿀 수 있게 만들기

- 결과 화면의 정답 구분을 **표시 설정 하나**로 둔다. 예: `correctQualityTiers: 3 | 2`. 2이면 부족을 근거 있는 정답에 합친다.
- 판정 기록에는 언제나 충분/부족/오류를 모두 남긴다. 그래야 (가)로 바꿔도 자료가 남고, 다시 (나)로 돌아갈 수도 있다.
- (가)로 가면 171행 수정은 급하지 않다. 171행은 부족 판정에만 작동하기 때문이다.

## 4. 오픈 전 할 일 (제안 순서)

1. **v5.9 질문 규칙 시험: sol만.** 사용자에게 보이는 질문은 모두 sol이 쓴다(오답 + 정답-오류). 기존 계획 "luna·sol 둘 다"를 sol만으로 줄인다. 초안 검토 1(문장 3곳, 예시 교체)의 사용자 답은 아직 대기 중이다.
2. **171행 수정 시험: sol만.** (나)에서는 꼭 필요하다. sol도 의식 14에서 6/6 부족으로 판정했다.
   - 기대 판정은 실행 전에 양방향으로 정한다.
   - 관대 반례(결론만 쓴 근거, 맞는 사실이지만 정답을 가르지 못하는 근거)를 넣는다.
   - 고칠 때 보는 문항과 확인할 때 보는 문항을 나눈다.
   - 방향 제안: 정답 판정기는 선지가 참이라는 걸 이미 안다. 그러니 "모든 주장 지지"를 "학생 근거가 이 선지를 고르고 다른 선지와 구별하는 이유로 성립하나"로 바꾼다(체크포인트 1.2절, 후보 2).
3. **정답 판정 모델을 sol로 바꾸고 판정 경로를 구현한다.** 리뷰는 오답과 정답-오류에만 연다.
4. **결과 화면에 정답의 질 3단계와 2단계 전환 설정을 넣는다.**
5. **Ghootae 직접 풀이 점검.** 4지문을 직접 풀며 "다시 고치라고 해서 짜증났다"와 "근거 약한 정답 표시가 억울했다"를 문항별로 표시한다. 짜증이 나면 (가)로 전환한다.

## 5. 비용 (추정, 다시 볼 조건 포함)

- 11-07 비용 실측(`docs/experiments/sns-diagnostic-cost-2026-11-07/REPORT-desktop.md`, 캐시 할인 제외)에서 호출당 값을 역산했다: 선택 판정 sol 약 $0.048 / luna 약 $0.003, 마지막 설명 sol 약 $0.020 / luna 약 $0.003(H·M·L 세 사람 값으로 연립해 추정), 사고 진단 sol $0.012, 교정 luna 약 $0.0015.
- 정답 판정과 정답 마지막 설명이 모두 sol로 바뀌므로 정답 1문항당 약 +$0.062다. 앞서 말한 "1인 약 +$0.5"는 마지막 설명을 빼고 계산한 값이라 낮았다.
- 지문 1세트(4문항, 문단 요약 제외) 추정: 현재 정답 3·오답 1 약 $0.13 → 약 $0.31, 2·2 약 $0.19 → 약 $0.31, 1·3 약 $0.26 → 약 $0.33. 바꾼 뒤에는 실력과 상관없이 세트당 약 $0.31~0.33이다. 1인(4세트)은 현재 약 $0.55~1.15 → 약 $1.25~1.35이고, 상위권일수록 많이 오른다.
- 줄일 자리: 정답 마지막 설명을 학생이 원할 때만 생성(정답 1문항당 약 $0.02 절약), 프롬프트 캐시(지시문이 커서 sol 입력비 비중이 크다, 미측정). 정답 sol 판정이 오답보다 출력이 짧아 쌀 수 있지만 미확인이다.
- 결정 기록에 다시 볼 조건을 적는다. 예: 참가자 수가 일정 규모를 넘거나, 1인 비용이 일정 금액을 넘을 때. 기준값은 Ghootae와 정한다.
